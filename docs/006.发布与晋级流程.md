# 006. 发布与晋级流程

Status: **current CI / promotion / release authority**

本文档只描述长期有效的执行流程和门禁，不维护历史 Phase checkpoint。

## 1. 正式 workflow

仓库正式 GitHub Actions workflow：

```text
CI
Promote validated dev to main
Real qB Full Frozen Matrix
Real qB Current Stable Locale Matrix
Release
Virtual qB Pages
Virtual qB Pages Source
```

删除或新增 workflow 时，必须同步检查 tests/contracts/docs 中的引用。

## 2. 分支职责：绝不跳过 dev

```text
dev   唯一开发/修复/文档/验证入口
main  稳定晋级分支，只接收 validated dev fast-forward
```

永久规则：

```text
产品改动 -> dev
installer 改动 -> dev
workflow 改动 -> dev
test/fixture 改动 -> dev
docs 改动 -> dev
红灯修复 -> dev
```

**禁止直接修改 main。** 包括：

```text
不要在 main 直接 update_file/create_file/delete_file
不要在 main 创建修复 commit
不要 cherry-pick 独立 main-only 产品修复
不要 force push main
不要用 connector update_ref 手工跳过 promotion gate
```

即使 `main == dev`，下一次修改仍然先进入 `dev`。

main 只允许从一个已经完成正式门禁的 final dev exact SHA 做 fast-forward promotion。

## 3. Normal CI

`.github/workflows/ci.yml` 在 dev push 上执行 normal/smoke 验证；candidate 模式负责发布候选的重型 source/product/browser/deployment 链。

普通 docs/tests/tooling 维护不应无理由触发 65-version real-qB Full Frozen Matrix，也不应无理由触发 current-stable 全语言真实矩阵。

**Real qB Full Frozen Matrix 不是日常 CI。** 普通开发 commit、修复 commit、docs-only commit 都不得自动启动这套 65-version 重矩阵。

任何新 commit 都产生新的 exact SHA。旧 evidence 只能证明旧 SHA。

## 4. Release candidate

准备发布时，先完成所有计划改动，再冻结一个 **final dev exact SHA**。

Candidate 必须至少覆盖：

```text
smoke
exact stable source catalog generation
all admitted stable source audit
12-way locale/source enrichment
merged exact catalog
Settings translation LKG
full stable PRODUCT compatibility
Linux hosted Chrome candidate
Windows hosted Chrome candidate
release candidate package
candidate deployment/rehearsal evidence
```

关键 artifact 绑定 exact SHA：

```text
qb-release-catalog-<SHA>
release-candidate-<SHA>
candidate-deployment-<SHA>
```

Candidate artifact 当前必须包含：

```text
WeiG-qB-WebUI.zip
weigg-install.sh
weigg-install.ps1
SHA256SUMS
CANDIDATE_SHA
```

checksums 覆盖 ZIP 与两个 installer。

## 5. Candidate deployment acceptance

最终 candidate acceptance 必须在 official qB 上真实验证，不允许只做 fixture/simulator：

```text
qB 4.6.7
qB 5.2.3
```

至少证明：

```text
Release tag -> exact commit identity
checksum PASS
package VERSION == resolved tag version
package GIT_SHA == resolved tag commit
installer syntax PASS
real app/preferences PASS
locale write/read/reload PASS
canonical Settings PASS
promotion/release rehearsal PASS
remoteWrites = 0
```

生产 installer identity gate 不得因为 candidate test harness 问题而放松。测试桩必须模拟真实 GitHub API shape，而不是修改生产 parser 去迁就错误 mock。

## 6. Full Frozen Matrix（G-FM）

`.github/workflows/real-qb-full.yml` 是发布前重型真实 qB 门禁。

```text
workflow_dispatch only
65 exact stable versions
1 version / matrix job
fail-fast: false
max-parallel: 16
per-version exact-SHA evidence
aggregate exact-SHA evidence
```

### 6.1 成本纪律：只跑 final exact SHA

这套矩阵耗时、runner 数和历史 runtime 成本都很高，因此永久规则是：

```text
日常 dev push                 -> 不跑
普通修复 / tests / docs       -> 不跑
中间阶段 checkpoint           -> 不跑
final dev SHA 尚未冻结        -> 不跑
准备最终验证 / 准备发布       -> 手动 workflow_dispatch 跑一次
Frozen/runtime/harness 重大变更且明确需要全量重新认证 -> 可手动跑
```

**不要为了每个开发 commit 都取得 65/65。** 先用 normal CI、source/product contracts、focused acceptance 把工作收敛；只有已经决定作为最终候选的 exact SHA 才支付 Full Matrix 成本。

如果 Full Matrix 跑完后又有任何会进入最终发布历史的新 commit，则旧 aggregate 只证明旧 SHA。需要发布时，应在新的 final exact SHA 上重新做最后一次 Full Matrix，而不是频繁在中间 SHA 上补跑。

发布前同一个 final dev exact SHA 必须取得：

```text
expected_stable_count = 65
executed_runtime_count = 65
PASS = 65
FAIL = 0
BLOCKED = 0
missing_versions = []
duplicate_versions = []
unexpected_runtime_versions = []
```

Candidate、Pages、Locale 与 G-FM 可以在冻结后的 final SHA 上并行，但 promotion 必须等待全部正式 evidence 成功。

**Candidate 的 `Full qB Release compatibility audit` 不等于 G-FM。** 前者是 source/product aggregate，后者是真实 65-version runtime matrix。不能混淆。

### 6.2 Full Matrix 手工启动防误触

即使进入最终验证阶段，也不能“点一下 Run workflow 就直接展开 65 jobs”。`Real qB Full Frozen Matrix` 的手工输入固定为：

```text
ref/branch = dev
candidate_sha = <已冻结 final dev 的 40 位 exact SHA>
confirmation = RUN-FULL-FROZEN-65
```

Plan job 在生成 matrix 前必须验证：

```text
workflow event == workflow_dispatch
GITHUB_REF == refs/heads/dev
candidate_sha 是 40 位 hex
candidate_sha == GITHUB_SHA
confirmation == RUN-FULL-FROZEN-65
```

如果 ref、SHA 或确认词任一不匹配，必须在展开 65-version matrix 前 fail closed。这个 guard 的目的就是防误触、防在错误 branch/SHA 上浪费整套真实 qB runner。

### 6.3 Current Stable Locale Matrix

`.github/workflows/real-qb-locale.yml` 是语言 owner / handoff 的 focused real-qB acceptance，不是第二套 G-FM。

workflow 仍保留条件触发能力，但 release-grade evidence 必须来自 final dev exact SHA 的显式 `workflow_dispatch`。Promotion / Release 不接受普通 push 的 skipped/conditional run 代替手工 final evidence。

矩阵身份必须从 target exact SHA 的 `tools/data/qb-locale-lkg.json` 派生：

```text
latestAdmittedStable -> exact current stable profile -> exact localeSet
1 locale / matrix job
fail-fast: false
max-parallel: 16  # 当前 operational 配置
```

当前 Frozen LKG 的 latest admitted stable 是 qB 5.2.3，其 WebUI locale surface 为 61 个 locale；这是当前 operational fact，不提升为长期固定数量。

每个 locale 的真实 acceptance 至少证明：

```text
runtime self-report == exact current stable
locale exists in running qB native LANGUAGE_OPTIONS
app/setPreferences(locale) succeeds
app/preferences verified reread == target locale
native locale surface remains available after write
original locale is restored in finally
per-locale evidence == same WeiG exact SHA
```

Aggregate 必须拒绝 missing / duplicate / unexpected locale，并要求全部 locale `PASS`、`restored=true`、`liveLocalePresent=true`。

最终 release candidate 的 promotion/release gate 会消费：

```text
real-qb-current-locale-aggregate-<SHA>
```

它用于证明 current-stable 全语言行为，不替代 Candidate、G-FM、Pages 或 promotion 的 exact-SHA evidence。未来 latest stable admission 更新时，应更新 immutable runtime provider pin/acceptance，而不是把版本号写进 first-party filename 或复制一个新版本 workflow。

## 7. Virtual qB Pages exact-SHA 规则

Pages 两层：

```text
Virtual qB Pages Source
-> ref-bound workflow_dispatch
-> Virtual qB Pages
```

`Virtual qB Pages` 是唯一 build/deploy/verify owner。

禁止恢复 default-branch `workflow_run` deployment trigger。final validated SHA 上 `event=workflow_run` 应为 0。

### dev

```text
checkout exact dev SHA
-> materialize exact runtime/source/locale evidence
-> validate contracts
-> publish virtual-qb-pages-site-<SHA>
-> fresh-head gate
-> deploy pages_build_version == exact SHA
-> live browser verify
```

Concurrency：

```text
group: virtual-qb-pages-dispatch
cancel-in-progress: false
```

原因：不能取消已经可能进入 deploy-pages 外部写入阶段的旧 owner。旧 owner 必须在 deploy 前通过 fresh-head gate 自己 fail closed。

### main

main 不重建：

```text
find successful dev artifact virtual-qb-pages-site-<SHA>
-> reuse/repackage main alias
-> fresh-main gate
-> deploy
-> verify live metadata/main/dev alias == exact SHA
```

如果同 SHA dev artifact 不存在，main Pages 必须失败。

## 8. Pages live readiness

`catalogReady` 与 `catalogBusy` 独立。允许短暂：

```text
catalogReady = true
catalogBusy  = true
```

Live acceptance 正确等待：

```text
catalogError || (catalogReady && !catalogBusy)
```

不能删除 busy 断言，也不能为了测试绿灯改变正确产品 lifecycle。

## 9. 正式 promotion

正式 promotion authority：

```text
Promote validated dev to main
```

输入：

```text
candidate_sha = current final dev 40-char SHA
confirmation = PROMOTE-VALIDATED-DEV
```

Promotion 必须自己验证：

```text
candidate_sha == current dev HEAD
main can fast-forward safely
successful exact dev candidate exists
release-candidate-<SHA> exists and not expired
candidate-deployment-<SHA> exists and not expired
successful manual same-SHA G-FM exists
real-qb-full-aggregate-<SHA> == 65/65 exact PASS
successful manual same-SHA Current Stable Locale Matrix exists
real-qb-current-locale-aggregate-<SHA> == all current-stable locales PASS
central release-compat-evidence verifier PASS
```

最终只允许 fast-forward：

```text
<current main> -> <validated dev exact SHA>
```

禁止 merge commit、cherry-pick rebuild、force push。

### 9.1 2026-09-12 复盘警告

`ba8ee49886fad159e76014514b5a0a4ba803bc29` 的 candidate/Pages 都全绿，main 也曾被 direct fast-forward 到该 SHA；但该 SHA 没有同 SHA G-FM run，且这次没有通过 formal promotion workflow 强制检查 G-FM。

因此这件事形成永久教训：

```text
main 与 dev 同 SHA != formal release gate complete
direct fast-forward success != promotion workflow success
candidate PASS != G-FM 65/65 PASS
```

后续 AI 不得复制这种捷径。

## 10. Tag / Release

只有 formal promotion 与 main Pages exact reuse 都确认成功后，才允许创建：

```text
v<VERSION>
```

必须满足：

```text
tag SHA == current main SHA == validated dev candidate SHA
```

Release workflow 会对 exact release SHA 重新解析并验证全部发布级 evidence：

```text
verify tag/version identity
verify release SHA == current main SHA
find exact successful dev candidate run
reuse release-candidate-<SHA>
reuse candidate-deployment-<SHA>
resolve successful manual real-qb-full-aggregate-<SHA>
resolve successful manual real-qb-current-locale-aggregate-<SHA>
run central release-compat-evidence verifier
verify G-FM == exact 65/65 PASS
verify Locale == current-stable all-locale PASS
verify CANDIDATE_SHA
verify SHA256SUMS
verify installer bytes == exact source tree
verify ZIP embedded GIT_SHA / VERSION
publish existing validated assets
```

Release 不得重新 build 产品，也不得用 Fast、旧 SHA、普通 push/skipped run 替代最终手工 compatibility evidence。

正式 assets：

```text
WeiG-qB-WebUI.zip
weigg-install.sh
weigg-install.ps1
SHA256SUMS
```

## 11. 推荐发布顺序

```text
1. all changes go to dev
2. 先完成代码 / workflow / tests / docs，不运行 Full Frozen Matrix
3. freeze final dev exact SHA
4. normal CI PASS
5. run CI candidate on that exact SHA
6. ensure dev Pages exact artifact/live verify PASS
7. manually run Current Stable Locale Matrix on the exact final SHA
8. 最后手动 run Real qB Full Frozen Matrix：branch=dev，candidate_sha=<final SHA>，confirmation=RUN-FULL-FROZEN-65
9. require G-FM 65/65 on that same exact SHA
10. run Promote validated dev to main
11. verify main == dev == exact SHA
12. verify main Pages exact reuse/live identity PASS
13. create tag v<VERSION> on exact main SHA
14. let Release workflow reuse candidate + G-FM + Locale evidence
15. verify 4 Release assets + digests + identities
```

5、6、7、8 在 **final SHA 已冻结之后** 可以并行；但 Full Frozen Matrix 应尽量作为最后的重型验证执行，不要在开发过程中反复跑。第 10 步以后不能跨 SHA。

## 12. Docs-only 规则

Docs-only 改动：

```text
先 dev
不 bump VERSION
不直接同步 main
不需要立即跑 G-FM/candidate
```

等待下一次正式 release 时，把 docs commit 作为 final dev history 的一部分，再对最终 SHA 建立完整 evidence。

不要因为“只是文档”就直接提交 main；这会破坏分支职责，并制造 main-only history。

## 13. Red gate discipline

红灯分类：

```text
product bug
source/profile misunderstanding
stale test/fixture/simulator
workflow choreography bug
runtime infrastructure problem
artifact identity problem
promotion/ref race
```

规则：

```text
完整日志优先
确定性 bug 修代码/contract
不降低断言
不放松 exact-SHA identity
不把 FAIL 改成 SKIP
仅明确瞬时基础设施故障才考虑同 SHA rerun
```
