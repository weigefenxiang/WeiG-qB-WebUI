# 006. 发布与晋级流程

Status: **current validation / promotion / release contract**

当前仓库只维护现行开发/发布链。历史 WeiG runtime、tests、tools、deploy scripts 不保留兼容副本；Git commits / tags / Releases 是历史恢复入口。

## 1. Version discipline

产品 patch VERSION 的唯一 bump trigger 是正式 `webui/**` 产品内容变化。仅修改 simulator、tests、tools、workflow、docs、DESIGN、installer、CI/gate 时保持当前产品 VERSION。

一旦 `webui/**` 变化，以下四处必须在同一最终 tree 同步：

```text
VERSION
webui/VERSION
package.json.version
package-lock.json root package version
```

exact Git SHA 始终是 code/cache/test/Pages/LIVE/candidate/artifact 的证据身份。新 commit 不继承旧 SHA 的 evidence。

## 2. Normal dev validation

普通 `dev` 不使用 `[candidate]`/`[ui]` 前缀作为正常验证前提。

```text
formal dev change
-> exact dev SHA
-> CI smoke / contracts / syntax
-> Upstream Compatibility Audit
     representative floor starts at qB 4.1.0
     representative modern generation dynamically follows current test policy
-> relevant Virtual qB Pages Source
-> Formal Virtual qB Pages
     exact triggering source checkout
     simulator contracts
     exact dev/main build
     deploy
     Hosted Chrome verify
-> normal dev delivery
```

Browser representative coverage 与 full stable source audit 是不同职责；official stable 数量和 latest patch 不在文档硬编码。

## 3. Owner migration validation

新增 canonical owner / tool 时必须遵守 `OWNER-CUTOVER`。

### Dormant validation

新 owner 可以先作为 isolated/test-only artifact 存在，此时旧 owner 仍是唯一 active runtime path。Direct contracts 必须先验证新接口的 semantic resolution。

### Atomic cutover

新接口验证成功后，下一变更必须同时完成：

```text
all affected callers -> new owner
remove superseded old version branches/helpers/files/tests
repo-wide zero-reference audit
DESIGN/docs Current Owner sync
CI / Upstream / relevant Pages exact-SHA validation
```

禁止把 old/new 双路 fallback、compat shim、runtime alias 当作迁移阶段长期提交到 Current architecture。

若 cutover 只修改 simulator/tests/docs/tools，不改 `webui/**`，产品 VERSION 不升；若正式产品内容同时变化，按第 1 节升版。

## 4. Upstream compatibility

WebAPI v2 正式 stable floor：**qBittorrent 4.1.0**。

普通 dev upstream audit 使用代表性 refs；full candidate audit 动态枚举从 `release-4.1.0` 到 latest official stable 的全部支持 tag。不得硬编码 stable 数量或当前 latest patch。

Structural compatibility 与 semantic evolution 分开验证：

- source catalog / parser / release audit：endpoint/Preference/Torrent surface existence；
- Endpoint Contract + WebAPI Evolution Audit（目标架构）：同 endpoint request/response/status/mutation evolution。

未来 `UNCLASSIFIED` semantic delta 必须 fail closed。

## 5. Virtual qB Pages validation

Virtual qB Pages 是 normal dev 的持续 exact-source 浏览器验收面，不是 release candidate artifact。

```text
dev/main relevant push
-> Virtual qB Pages Source
-> default-branch workflow_run
-> exact triggering source SHA
-> validate simulator contracts
-> generate exact upstream stable catalog
-> build exact dev/main snapshots
-> deploy
-> verify metadata/source identity
-> Hosted Chrome live acceptance
```

Workflow UI 的 run-level `head_sha` 可能显示默认分支 `main`；实际 source identity 只能以 triggering source SHA、`WEIGG_PAGES_SOURCE_SHA`、exact checkout、deployed metadata、`WEIGG_EXPECTED_SIMULATOR_SHA` 为准。

Pages green 证明 Virtual backend + formal WebUI snapshot + current Chrome 的 normal dev state，不冒充真实 qB binary LIVE。

## 6. Exact-SHA real qB LIVE gate

只有准备晋级 `main` 时，冻结 final `dev` SHA 后执行真实 qB4/qB5 LIVE。最低真实 qB4 target 必须属于当前正式 floor **4.1.0+**；modern target 使用当时维护的当前 stable generation，不在文档硬编码 patch。

统一脚本：

```text
tests/live.sh
tests/live-api.sh
```

脚本从 exact SHA 自身读取产品版本；文件名不编码 WeiG/qB revision。若 LIVE 后 tree 又变化，旧 LIVE evidence 作废。

## 7. Promote dev to main

必须满足 current dev exact SHA、safe fast-forward、对应 CI/upstream evidence、operator LIVE confirmation、显式 maintainer authorization。

只允许：

```text
main -> exact validated dev SHA
```

禁止 merge commit 或 force-overwrite 未知 main-only commit。

## 8. Main-only candidate / Release

main 指向 validated SHA 后，才运行 main-only full candidate：

```text
full stable-tag source audit from 4.1.0
Linux Hosted Chrome representative matrix
Windows Hosted Chrome representative matrix
exact-SHA candidate artifact
```

Artifact 必须携带 source-derived `qb-releases.json`，并以 SHA / checksum / `CANDIDATE_SHA` 绑定。

Tag Release 只验证并发布同一 candidate artifact；Tag 阶段禁止重新 build/package source。

## 9. Canonical chain

```text
normal dev
-> exact SHA CI/upstream/Pages
-> normal delivery

when maintainer promotes
-> freeze final dev SHA
-> real qB LIVE
-> explicit authorization
-> safe fast-forward main
-> main-only full stable/browser candidate
-> artifact
-> tag same SHA
-> verify/publish same artifact
```

普通 dev validation、owner migration validation 与 main-only candidate 不得混为一谈。
