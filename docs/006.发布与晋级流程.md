# 006. 发布与晋级流程

Status: **current CI / candidate / promotion / release authority**

本文描述长期有效的执行流程、exact-SHA 门禁与当前 operational 边界，不维护历史 Phase checkpoint。数字型 matrix 规模、某次 SHA/run 只作为当前事实，不提升为永久架构常量。

## 1. 正式 workflow

仓库正式 GitHub Actions workflow：

```text
CI
Promote validated dev to main
Real qB Full Frozen Matrix
Real qB Current Stable Locale Matrix
Release
Virtual qB Pages
Virtual qB Pages Source
```

新增、删除、重命名或改变 workflow 职责属于显式架构变更，必须同步检查 `.github/workflows/**`、tests/contracts、package scripts、permissions、concurrency 与 docs 引用。

## 2. 分支职责：所有工作先进入 dev

```text
dev   唯一开发 / 修复 / docs / validation 入口
main  稳定晋级结果，只接收 validated dev safe fast-forward
```

产品、installer、workflow、test、fixture、docs、CI 修复都先进入 dev。未经用户明确授权禁止直接修改 main、promotion、tag 或 GitHub Release；禁止 force push。未经用户明确批准不得手动触发 Candidate。

main 只能从已经完成正式门禁的 final dev exact SHA 做 safe fast-forward，`force:false`；禁止 merge commit、cherry-pick rebuild、main-only fix 或重新构造 release identity。

仓库中即使存在历史/临时/误建 branch，也不得形成第二开发线。正式开发只从 fresh-read 的 `dev` 接手。

## 3. CI 按风险分层

`.github/workflows/ci.yml` 的职责：

```text
ordinary dev push             -> classify + normal/smoke as applicable
explicit UI validation        -> UI/browser lane
candidate validation          -> complete source/product/browser/package/deployment chain
```

Candidate 可通过 `workflow_dispatch: validation_mode=candidate` 或既有正式 push gate触发，但**当前用户明确要求未经批准不运行 Candidate**。AI 不得自行添加 `[candidate]`、造空提交或手动 dispatch。

普通 docs/tests/tooling-neutral maintenance 不应自动启动 real-qB Full Frozen Matrix 或 current-stable 全 Locale matrix。

任何新 commit 都产生新的 exact-SHA evidence identity。旧 candidate、browser、Pages、Locale、G-FM artifact不能自动证明新 SHA。

## 4. Release candidate

只有用户明确进入最终验证/准备发布阶段，并且所有计划内产品/workflow/tests/docs已经完成后，才冻结 final dev exact SHA并建立 Candidate。

Candidate 至少覆盖适用的：

```text
smoke
representative fixture compatibility
exact stable source catalog generation
all admitted stable upstream source audit
locale/source enrichment shards
merged exact source + recovery evidence
Settings/source certified LKG
full stable PRODUCT compatibility
Linux hosted Chrome candidate
Windows hosted Chrome candidate
release candidate package
candidate deployment / official-qB rehearsal acceptance
```

关键 artifact包括：

```text
qb-release-catalog-base-<SHA>
qb-release-enriched-<SHA>-<shard>
qb-release-catalog-<SHA>
qb-settings-translation-lkg-<SHA>
release-candidate-<SHA>
candidate-deployment-<SHA>
```

Release candidate artifact至少包含：

```text
WeiG-qB-WebUI.zip
weigg-install.sh
weigg-install.ps1
SHA256SUMS
CANDIDATE_SHA
```

checksums、VERSION、CANDIDATE_SHA、ZIP 内 `GIT_SHA` 必须与 target exact SHA 一致。

Candidate CI 的 `Full qB Release compatibility audit` 是 source/product/evidence aggregate，**不等于** Real qB Full Frozen Matrix。

## 5. Candidate deployment acceptance

Candidate deployment必须在official qB runtime上验证真实安装/运行，不允许只用fixture/Virtual qB。

当前 representative official-qB acceptance至少覆盖floor-era与latest stable代表；具体代表版本可随source/evidence policy调整，不提升为永久硬编码。

至少证明：

```text
candidate package exact identity
checksum / VERSION / GIT_SHA
installer syntax and lifecycle
real app/preferences
canonical Settings
locale write/read/reload semantics where exercised
source-proven product actions
promotion/release rehearsal invariants
no unexpected remote writes
```

生产 identity/security gate不得因为candidate harness/mock不完整而放松。错误mock应修测试桩，不应修改正确生产parser来迁就。

## 6. Virtual qB Pages exact-SHA 规则

Pages 两层 owner：

```text
Virtual qB Pages Source
-> ref-bound workflow_dispatch
-> Virtual qB Pages
```

`Virtual qB Pages` 是 build/deploy/live-verify owner；禁止恢复 default-branch `workflow_run` duplicate deployment path。

### 6.1 Dev Pages

```text
resolve target dev ref/SHA
-> source/materialization evidence as required
-> exact-SHA site artifact
-> fresh-head stale-deploy gate
-> deploy
-> live browser verify
```

Pages source/build消费 frozen/hash-bound source/LKG facts，不应在普通deployment上重新clone/re-parse全部qB history。

### 6.2 Docs-only / public-payload-irrelevant nuance

Dev installer 与 Pages stale classifier允许在GitHub compare明确证明只有public-payload-irrelevant diff时复用最近已验证materialized payload。这是日常Dev distribution成本优化，不是release evidence继承。

`Virtual qB Pages Source` 不能只检查“本次 push before -> current”。对 `dev`，当本次push看起来只是docs/test等public-payload-irrelevant变化时，还必须读取当前公开 `downloads/dev/GIT_SHA`，比较：

```text
published materialized payload SHA
-> current dev SHA
```

如果整段历史存在 `webui/**`、`VERSION`、installer、Pages workflow或materialization input等Pages-relevant变化，必须dispatch当前exact dev Pages owner；公开SHA读取失败、格式非法、无法证明为current dev祖先时也必须fail closed重新materialize。

Materialization relevance matcher必须只有一个canonical owner，不能复制第二份路径表。

因此：

```text
old materialized product SHA may represent unchanged runtime bytes
!=
new docs SHA has exact-final-SHA release-grade Pages evidence
```

准备promotion/release时，最终dev exact SHA必须拥有正式gate要求的exact Pages identity；不能因为docs-only classifier允许复用旧payload，就把旧SHA Pages artifact写成新SHA release evidence。

### 6.3 Main Pages

Promotion后main不重新full-build另一份产品；应复用同一个已验证final dev artifact/bytes，并验证main/dev/build metadata/live deployment identity一致。若required exact artifact不存在，必须fail closed。

## 7. Current Stable Locale Matrix

`.github/workflows/real-qb-locale.yml` 是 focused real-qB language acceptance，不是第二套Full Frozen Matrix。

Release-grade Locale evidence必须来自 final dev exact SHA 的显式 manual dispatch。矩阵身份由target exact-SHA locale LKG派生：

```text
latestAdmittedStable
-> exact current stable profile/source identity
-> exact localeSet
-> one exact-SHA per-locale acceptance
-> aggregate
```

当前operational surface是qB 5.2.3的61 locales；数量随Frozen LKG演进，不是长期常量。

普通push的skipped/conditional Locale run不能作为release-grade evidence。

## 8. Real qB Full Frozen Matrix（G-FM）

`.github/workflows/real-qb-full.yml` 是发布前重型真实qB gate，只在 final/release-stage显式运行，不是日常CI。

Expected versions必须从target exact-SHA Frozen LKG派生。当前operational surface是65 stable runtimes，但数量不是长期硬编码。

每个runtime必须验证：

```text
same WeiG exact SHA
requested qB == runtime self-report
ReleaseProfile/exact source identity consistent
runtime image/source-build immutable identity
capability/product acceptance PASS
```

Aggregate必须证明expected == executed，`FAIL=0`、`BLOCKED=0`，无missing/duplicate/unexpected version。

手工启动必须有branch/ref、exact candidate SHA和显式确认词等fail-closed guard。Final dev SHA未冻结前不要运行Full Matrix；普通dev push、docs、tests、中间checkpoint都不运行。

## 9. Exact-SHA promotion gate

正式 authority：

```text
Promote validated dev to main
```

Promotion前必须证明同一个final dev SHA至少拥有：

```text
current dev HEAD == candidate SHA
normal CI success
candidate full chain success
release-candidate exact artifact
candidate-deployment exact evidence
Dev Pages exact required evidence
manual Current Stable Locale aggregate all PASS
manual G-FM aggregate all PASS
central release-compat-evidence verifier PASS
main is ancestor and safe fast-forward is possible
```

最终只能：

```text
<current main> -> <validated final dev exact SHA>
```

并显式 `force:false`。

Candidate PASS、Pages PASS、main==dev或Actions顶层绿色状态任一单项都不能替代formal promotion permission。未经用户明确授权，不执行promotion。

## 10. Tag / Release

Formal promotion成功、main Pages exact reuse/live identity确认后，才允许创建：

```text
v<VERSION>
```

必须满足：

```text
tag SHA == current main SHA == validated final dev SHA
```

Release坚持 `build once / validate once / promote same bytes`：复用已验证candidate artifact，不在main/tag后重新构建另一份ZIP。

Release workflow重新验证tag/version/main SHA identity、candidate run/artifacts、candidate deployment、manual G-FM、manual Locale、central evidence、CANDIDATE_SHA、SHA256SUMS、installer bytes、ZIP embedded GIT_SHA/VERSION及generated catalog/LKG identity。

未经用户明确授权，不创建tag或GitHub Release。

## 11. 推荐正式顺序

只有用户明确进入发布阶段时：

```text
1. all planned changes -> dev
2. sync current docs/tests/workflows; no heavy G-FM yet
3. freeze final dev exact SHA
4. normal CI PASS
5. CI candidate PASS on same SHA
6. Dev Pages exact required evidence PASS on same SHA
7. manual Current Stable Locale Matrix PASS on same SHA
8. manual Real qB Full Frozen Matrix PASS on same SHA
9. central release-compat-evidence PASS
10. user explicitly authorizes promotion/release
11. Promote validated dev -> main safe fast-forward
12. main Pages exact reuse/live verify
13. tag v<VERSION> on exact main SHA
14. Release reuses validated candidate bytes
15. verify final assets/digests/identities
```

Candidate、Pages、Locale、G-FM在final SHA冻结后可按workflow能力并行；但G-FM应尽量留到开发彻底停止后的最后重型验证阶段。

## 12. Docs-only 规则

Docs-only coherent change：

```text
must go to dev
must not bump Product VERSION
must not direct-sync main
must not be used as excuse for Candidate/no-op trigger commits
```

当前用户已明确禁止未经批准触发Candidate，因此 docs-only handoff/finalization 只走 ordinary classifier；不能自行添加 `[candidate]`。

Docs-only SHA若被classifier判定public-payload-irrelevant，可以复用已验证materialized product payload，但这种复用不是新SHA的release-grade exact Pages evidence。

## 13. Red gate discipline

红灯先分类：

```text
product bug
source/profile misunderstanding
stale test/fixture/simulator/docs
workflow choreography bug
runtime infrastructure problem
artifact/evidence identity problem
promotion/ref race
```

处理规则：

```text
读完整失败日志
确定性bug修root cause
source/canonical runtime truth优先
不降低assertion/provenance/exact-SHA gate
不把FAIL改SKIP
不吞runtime/source error
只对明确transient runner/CDN/infrastructure fault做same-SHA rerun
```
