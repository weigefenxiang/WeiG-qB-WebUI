# 006. 发布与晋级流程

Status: **v0.3.7 release contract**

稳定分支不能被当成第二套完整测试/构建环境。Release 是对一个已经在 `dev` 完整验证、已经生成可复用 artifact、并通过真实服务器 gate 的精确 commit 的晋级与发布。

## 1. Candidate validation

完整 CI 只在 `dev` candidate 上跑一次：

```text
dev commit SHA
  -> smoke / syntax
  -> compatibility contracts
  -> Chromium regressions
  -> package exact-SHA release candidate
  -> upload release-candidate-<SHA>
  -> exact candidate SHA is green
```

可复用 candidate 包含：

```text
WeiG-qB-WebUI.zip
SHA256SUMS
CANDIDATE_SHA
```

WebUI payload 在上传前写入精确 `dev` Git SHA；artifact 名称也带同一个 SHA。后续 main 晋级与 Release 只验证和复用，不重新构建。

PR 的 synthetic `refs/pull/*/merge` commit 不是发布身份，不应因为 PR 更新再次跑完整 browser matrix。

## 2. Live gate

fixture success 不等于生产认证。稳定晋级前必须把 exact SHA candidate 部署到真实 qBittorrent 环境并进行交互验收。

真实环境的 URL、凭据、Docker container 名、宿主机路径只属于 runtime input / operator notes，不能写进公开源码。

## 3. Stable promotion

`.github/workflows/promote.yml` 需要：

```text
candidate_sha = exact current dev HEAD
live_gate     = LIVE-PASS
confirmation  = PROMOTE-VALIDATED-DEV
```

workflow 必须验证：

1. 从 `dev` 执行；
2. candidate SHA 等于当前 `dev` HEAD；
3. `main` 可以 fast-forward 到同一个 SHA；
4. 该 exact SHA 存在成功的完整 dev push CI；
5. CI run 仍包含未过期 `release-candidate-<SHA>`；
6. operator 明确确认真实服务器 gate 已通过。

通过后仅执行：

```text
main -> exact validated dev SHA
```

不创建 merge commit，不在 main 重跑完整浏览器测试，不重新构建发布包。

## 4. Tag release 复用 dev artifact

`v*` tag 启动 `.github/workflows/release.yml`，但 Release workflow 是 publish-only。

禁止：

```text
checkout source
npm test
Playwright
re-package WebUI from source
```

Release workflow 验证：

1. tag SHA 等于当前 `main` SHA；
2. exact SHA 存在成功的完整 `dev` push CI；
3. CI run 含未过期 `release-candidate-<SHA>`；
4. artifact 内 `CANDIDATE_SHA` 等于 tag SHA；
5. `SHA256SUMS` 验证 ZIP；
6. ZIP 内 `WeiG-qB-WebUI/GIT_SHA` 等于 tag SHA。

只有全部通过后才发布已经验证过的 ZIP 与 checksum。

artifact 丢失、过期、SHA 不匹配或 checksum 错误时必须 fail closed，Release 阶段不允许临时重新构建替代品。

## 5. 稳定分发唯一事实源

普通用户稳定安装只认 GitHub Release：

```text
Latest Release page
https://github.com/weigefenxiang/WeiG-qB-WebUI/releases/latest

Payload
https://github.com/weigefenxiang/WeiG-qB-WebUI/releases/latest/download/WeiG-qB-WebUI.zip

Checksum
https://github.com/weigefenxiang/WeiG-qB-WebUI/releases/latest/download/SHA256SUMS
```

`dev` 和 `main` branch source archive 不作为稳定下载入口。没有 Release 时，代表没有正式稳定版，而不是自动把某个 branch 当 Release。

Linux/Windows installer 可以从 `main/installers/*` 作为 bootstrap 获取，因为 bootstrap 本身不是 WebUI payload；稳定安装最终必须落到 Release asset + exact `GIT_SHA` + checksum identity。

当前第一版 Release 尚未正式发布前，installer 中保留的 `main` fallback 仅属于预发布兼容路径。**首次稳定 Release 发布前应改为稳定模式 fail closed：Release 不存在就明确报错，不静默把 main 当稳定版。**

## 6. 为什么 main / Release 必须复用 dev

Release artifact 由 Git commit 定义，而不是 branch 名定义。

如果 dev commit `X`：

```text
完整 CI PASS
-> artifact release-candidate-X
-> LIVE PASS
-> main fast-forward 到 X
-> tag 指向 X
```

那么 source tree、Git SHA、cache identity 和 deployable payload 都一致。

merge commit 会产生新 SHA；tag 后重构建也会形成第二条未经 candidate 环境验证的生产路径。因此 canonical 流程固定为：

```text
dev exact SHA
  -> full CI once
  -> reusable exact-SHA artifact
  -> live validation
  -> fast-forward main to same SHA
  -> tag same SHA
  -> verify + publish same artifact
```

## 7. README / 安装文档发布规则

README 必须简洁，只做：

```text
产品一句话
Latest Release
Linux/Docker/NAS 一键安装
Windows 一键安装
手动安装
兼容范围
详细 docs 链接
```

完整平台差异、Docker path、NAS、更新、回滚和 checksum 放在 `007.安装升级与手动部署.md`。

README 不展示 `dev` candidate artifact 给普通用户，也不把 GitHub Actions 临时 artifact 当稳定下载链接。

## 8. Failure policy

任一自动 gate 或 live gate 失败：

```text
Do not promote main
-> fix dev
-> produce a new candidate SHA
-> run full dev CI again
-> create a new exact-SHA artifact
-> repeat affected live validation
```

失败 candidate 不能因为旧 SHA 曾经 green 就被晋级；Release workflow 也不能用重测/重构建补偿 missing validated artifact。
