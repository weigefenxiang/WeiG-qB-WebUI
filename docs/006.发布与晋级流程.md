# 006. 发布与晋级流程

Status: **current CI / promotion / release authority**

本文档只描述长期有效的执行流程和门禁，不维护历史 Phase checkpoint。

## 1. 正式 workflow

仓库正式 GitHub Actions workflow：

```text
CI
Promote validated dev to main
Real qB Full Frozen Matrix
Release
Virtual qB Pages
Virtual qB Pages Source
```

删除或新增 workflow 时，必须同步检查 tests/contracts/docs 中的引用。

## 2. 分支职责：绝不跳过 dev

```text
dev   唯一开发/修复/文档/验证入口
main  稳定晋级分支，只接收 validated dev fast-forward
```

永久规则：

```text
产品改动 -> dev
installer 改动 -> dev
workflow 改动 -> dev
test/fixture 改动 -> dev
docs 改动 -> dev
红灯修复 -> dev
```

**禁止直接修改 main。** 包括：

```text
不要在 main 直接 update_file/create_file/delete_file
不要在 main 创建修复 commit
不要 cherry-pick 独立 main-only 产品修复
不要 force push main
不要用 connector update_ref 手工跳过 promotion gate
```

即使 `main == dev`，下一次修改仍然先进入 `dev`。

main 只允许从一个已经完成正式门禁的 final dev exact SHA 做 fast-forward promotion。

## 3. Normal CI

`.github/workflows/ci.yml` 在 dev push 上执行 normal/smoke 验证；candidate 模式负责发布候选的重型 source/product/browser/deployment 链。

普通 docs/tests/tooling 维护不应无理由触发 65-version real-qB Full Frozen Matrix。

任何新 commit 都产生新的 exact SHA。旧 evidence 只能证明旧 SHA。

## 4. Release candidate

准备发布时，先完成所有计划改动，再冻结一个 **final dev exact SHA**。

Candidate 必须至少覆盖：

```text
smoke
exact stable source catalog generation
all admitted stable source audit
12-way locale/source enrichment
merged exact catalog
Settings translation LKG
full stable PRODUCT compatibility
Linux hosted Chrome candidate
Windows hosted Chrome candidate
release candidate package
candidate deployment/rehearsal evidence
```

关键 artifact 绑定 exact SHA：

```text
qb-release-catalog-<SHA>
release-candidate-<SHA>
candidate-deployment-<SHA>
```

Candidate artifact 当前必须包含：

```text
WeiG-qB-WebUI.zip
weigg-install.sh
weigg-install.ps1
SHA256SUMS
CANDIDATE_SHA
```

checksums 覆盖 ZIP 与两个 installer。

## 5. Candidate deployment acceptance

最终 candidate acceptance 必须在 official qB 上真实验证，不允许只做 fixture/simulator：

```text
qB 4.6.7
qB 5.2.3
```

至少证明：

```text
Release tag -> exact commit identity
checksum PASS
package VERSION == resolved tag version
package GIT_SHA == resolved tag commit
installer syntax PASS
real app/preferences PASS
locale write/read/reload PASS
canonical Settings PASS
promotion/release rehearsal PASS
remoteWrites = 0
```

生产 installer identity gate 不得因为 candidate test harness 问题而放松。测试桩必须模拟真实 GitHub API shape，而不是修改生产 parser 去迁就错误 mock。

## 6. Full Frozen Matrix（G-FM）

`.github/workflows/real-qb-full.yml` 是发布前重型真实 qB 门禁。

```text
workflow_dispatch only
65 exact stable versions
1 version / matrix job
fail-fast: false
max-parallel: 16
per-version exact-SHA evidence
aggregate exact-SHA evidence
```

发布前同一个 final dev exact SHA 必须取得：

```text
expected_stable_count = 65
executed_runtime_count = 65
PASS = 65
FAIL = 0
BLOCKED = 0
missing_versions = []
duplicate_versions = []
unexpected_runtime_versions = []
```

Candidate 与 G-FM 可以并行，但 promotion 必须等待两者都成功。

**Candidate 的 `Full qB Release compatibility audit` 不等于 G-FM。** 前者是 source/product aggregate，后者是真实 65-version runtime matrix。不能混淆。

## 7. Virtual qB Pages exact-SHA 规则

Pages 两层：

```text
Virtual qB Pages Source
-> ref-bound workflow_dispatch
-> Virtual qB Pages
```

`Virtual qB Pages` 是唯一 build/deploy/verify owner。

禁止恢复 default-branch `workflow_run` deployment trigger。final validated SHA 上 `event=workflow_run` 应为 0。

### dev

```text
checkout exact dev SHA
-> materialize exact runtime/source/locale evidence
-> validate contracts
-> publish virtual-qb-pages-site-<SHA>
-> fresh-head gate
-> deploy pages_build_version == exact SHA
-> live browser verify
```

Concurrency：

```text
group: virtual-qb-pages-dispatch
cancel-in-progress: false
```

原因：不能取消已经可能进入 deploy-pages 外部写入阶段的旧 owner。旧 owner 必须在 deploy 前通过 fresh-head gate 自己 fail closed。

### main

main 不重建：

```text
find successful dev artifact virtual-qb-pages-site-<SHA>
-> reuse/repackage main alias
-> fresh-main gate
-> deploy
-> verify live metadata/main/dev alias == exact SHA
```

如果同 SHA dev artifact 不存在，main Pages 必须失败。

## 8. Pages live readiness

`catalogReady` 与 `catalogBusy` 独立。允许短暂：

```text
catalogReady = true
catalogBusy  = true
```

Live acceptance 正确等待：

```text
catalogError || (catalogReady && !catalogBusy)
```

不能删除 busy 断言，也不能为了测试绿灯改变正确产品 lifecycle。

## 9. 正式 promotion

正式 promotion authority：

```text
Promote validated dev to main
```

输入：

```text
candidate_sha = current final dev 40-char SHA
confirmation = PROMOTE-VALIDATED-DEV
```

Promotion 必须自己验证：

```text
candidate_sha == current dev HEAD
main can fast-forward safely
successful exact dev candidate exists
release-candidate-<SHA> exists and not expired
candidate-deployment-<SHA> exists and not expired
same-SHA G-FM exists
real-qb-full-aggregate-<SHA> == 65/65 exact PASS
```

最终只允许 fast-forward：

```text
<current main> -> <validated dev exact SHA>
```

禁止 merge commit、cherry-pick rebuild、force push。

## 10. Tag / Release

只有 formal promotion 与 main Pages exact reuse 都确认成功后，才允许创建：

```text
v<VERSION>
```

必须满足：

```text
tag SHA == current main SHA == validated dev candidate SHA
```

Release workflow 会：

```text
verify tag/version identity
verify release SHA == current main SHA
find exact successful dev candidate run
reuse release-candidate-<SHA>
reuse candidate-deployment-<SHA>
verify CANDIDATE_SHA
verify SHA256SUMS
verify installer bytes == exact source tree
verify ZIP embedded GIT_SHA / VERSION
publish existing validated assets
```

Release 不得重新 build 产品。

正式 assets：

```text
WeiG-qB-WebUI.zip
weigg-install.sh
weigg-install.ps1
SHA256SUMS
```

## 11. 推荐发布顺序

```text
1. all changes go to dev
2. freeze final dev exact SHA
3. normal CI PASS
4. run CI candidate on that exact SHA
5. ensure dev Pages exact artifact/live verify PASS
6. run G-FM 65/65 on the same exact SHA
7. run Promote validated dev to main
8. verify main == dev == exact SHA
9. verify main Pages exact reuse/live identity PASS
10. create tag v<VERSION> on exact main SHA
11. let Release workflow reuse validated candidate artifact
12. verify 4 Release assets + digests + identities
```

4、5、6 可并行；7 以后不能跨 SHA。

## 12. Docs-only 规则

Docs-only 改动：

```text
先 dev
不 bump VERSION
不直接同步 main
不需要立即跑 G-FM/candidate
```

等待下一次正式 release 时，把 docs commit 作为 final dev history 的一部分，再对最终 SHA 建立完整 evidence。

不要因为“只是文档”就直接提交 main；这会破坏分支职责，并制造 main-only history。

## 13. Red gate discipline

红灯分类：

```text
product bug
source/profile misunderstanding
stale test/fixture/simulator
workflow choreography bug
runtime infrastructure problem
artifact identity problem
promotion/ref race
```

规则：

```text
完整日志优先
确定性 bug 修代码/contract
不降低断言
不放松 exact-SHA identity
不把 FAIL 改成 SKIP
仅明确瞬时基础设施故障才考虑同 SHA rerun
```
