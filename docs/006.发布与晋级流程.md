# 006. Release and Promotion Flow

Status: **v0.3.7 release contract**

The stable branch must not be used as a second full-test or second-build environment. A release is a promotion of one exact `dev` commit that has already passed the complete automated gate, produced a reusable release artifact, and passed the required real-server gate.

## 1. Candidate validation

Full CI runs on `dev` pushes only:

```text
dev commit SHA
  -> smoke / syntax
  -> compatibility contracts
  -> Chromium regressions
  -> package exact-SHA release candidate
  -> upload release-candidate-<SHA>
  -> exact candidate SHA is green
```

The reusable candidate contains:

```text
WeiG-qB-WebUI.zip
SHA256SUMS
CANDIDATE_SHA
```

The WebUI payload is stamped with the exact `dev` Git SHA before upload. The artifact name also carries that same SHA, so later promotion and release can verify identity without rebuilding.

Opening or updating a pull request must not run the complete browser matrix again against GitHub's synthetic `refs/pull/*/merge` commit. That merge commit is not the release artifact and can create a different SHA even when the source tree is identical.

`workflow_dispatch` remains available for an explicit manual rerun of the complete `dev` candidate gate.

## 2. Live gate

Automated fixture success is not production certification. Before stable promotion, the candidate must be deployed by exact SHA to the required real qBittorrent generations and validated interactively.

The live helper must remain environment-neutral. Deployment URLs, credentials, container names and machine-specific host paths are runtime inputs and must never be committed into the open-source project.

## 3. Stable promotion

Stable promotion uses `.github/workflows/promote.yml` and requires all three explicit inputs:

```text
candidate_sha = exact current dev HEAD
live_gate     = LIVE-PASS
confirmation  = PROMOTE-VALIDATED-DEV
```

The workflow verifies:

1. it is executed from `dev`;
2. `candidate_sha` is exactly the current `dev` HEAD;
3. `main` can be fast-forwarded to that SHA without history divergence;
4. a successful full `CI` push run exists for that exact `dev` SHA;
5. that successful CI run still contains the non-expired `release-candidate-<SHA>` artifact;
6. the operator explicitly confirms that the real-server gate passed.

Only after all guards pass does it execute a fast-forward:

```text
main -> exact validated dev SHA
```

No merge commit is created. No second full browser matrix is run on `main`. No release artifact is rebuilt during promotion.

## 4. Tag release reuses the dev artifact

A `v*` tag starts `.github/workflows/release.yml`, but release is publish-only. It must not checkout source, run `npm test`, run Playwright, or package WebUI again.

The release workflow verifies:

1. the tag SHA is exactly the current `main` SHA;
2. a successful full `dev` push CI exists for that exact SHA;
3. that CI run contains the non-expired artifact named `release-candidate-<SHA>`;
4. `CANDIDATE_SHA` inside the artifact equals the tag SHA;
5. `SHA256SUMS` verifies the downloaded ZIP;
6. `WeiG-qB-WebUI/GIT_SHA` inside the ZIP equals the tag SHA.

Only after these checks does it publish the already-validated ZIP and checksum as the GitHub Release assets.

If the reusable artifact is missing, expired, has the wrong SHA, or fails checksum validation, release fails closed. It must not silently rebuild a replacement during the tag workflow.

## 5. Why main and Release reuse dev

The release artifact is defined by the Git commit, not the branch name. If `dev` commit `X` passed all gates, produced artifact `release-candidate-X`, and `main` is moved directly to the same commit `X`, the source tree, Git SHA, cache identity and deployable payload are identical.

Creating a merge commit would produce a new SHA and invalidate that exact-SHA guarantee. Rebuilding after tagging would also create a second production path that was not the artifact exercised by the candidate pipeline. Therefore the canonical path is:

```text
dev exact SHA
  -> full CI once
  -> reusable exact-SHA artifact
  -> live validation
  -> fast-forward main to same SHA
  -> tag same SHA
  -> verify + publish same artifact
```

## 6. Failure policy

If any automated or live gate fails:

```text
Do not promote main
-> fix dev
-> produce a new candidate SHA
-> run full dev CI again
-> create a new exact-SHA release artifact
-> repeat real-server validation when the changed surface requires it
```

A failed candidate is never promoted merely because an earlier SHA was green. A release workflow must never compensate for a missing validated artifact by retesting or rebuilding on `main`.
