# 006. 发布与晋级流程

Status: **current product validation / promotion / release contract**

本文件以 `webui/**` 产品兼容为中心。Source audit、Full Stable Product Matrix、Virtual qB 与 browser fixtures 都是开发/发布证据的一部分，但职责不同，不能互相替代。

当前兼容路线检查点：

```text
Phase A — Source Facts Expansion                    DONE
Phase B — qB4.1+ Product Compatibility Core         DONE
Phase C — Full Stable Product Compatibility Matrix DONE
Phase D — Future Stable Discovery / Automation      NEXT
qB4.0.x / WebAPI v1                                FUTURE OPTIONAL
```

## 1. Version discipline

只有正式 `webui/**` 产品内容变化才 bump patch VERSION。

一旦 `webui/**` 变化，以下四处同一最终 tree 同步：

```text
VERSION
webui/VERSION
package.json.version
package-lock.json root package version
```

仅 simulator/tests/tools/workflow/docs/DESIGN/installer/CI 变化时保持产品 VERSION。

Exact Git SHA 始终是 code/cache/test/Pages/LIVE/candidate/artifact evidence identity；新 SHA 不继承旧 SHA 证据。

## 2. Validation tiers

不同改动使用不同深度验证，禁止所有 push 都跑最重矩阵。

### Tier 1 — normal dev / docs / tests / tooling-neutral changes

普通 `dev` push 运行：

```text
smoke
-> npm test
-> JavaScript / installer / script syntax
```

`docs/**`、README、纯文档/说明更新不触发 Full qB stable WebAPI evolution audit，也不触发 candidate browser/full-stable jobs。

### Tier 2 — product/UI compatibility batch

正式 `webui/**` compatibility 修改至少需要：

```text
smoke
-> direct product compatibility contracts
-> relevant browser/Virtual qB evidence
```

需要完整 candidate 证明时使用 `[candidate]` 或对应手动 candidate validation：

```text
exact all-stable catalog
-> all-stable source audit
-> Full Stable PRODUCT Compatibility Matrix
-> Linux browser
-> Windows browser
-> exact-SHA candidate package
```

### Tier 3 — upstream source / WebAPI evolution audit

`Full qB stable WebAPI evolution audit` 是重型上游事实审计，不是普通 CI。

它用于验证：

```text
qB stable tag history
WebAPI revision history
source-derived API/actions/parameters/fields/filters/preferences
release-to-release surface evolution
WebAPI evolution ledger / changelog evidence
```

只有真正影响这些事实的输入变化时自动运行；也保留 `workflow_dispatch` 手动运行。

当前自动触发范围以 `.github/workflows/upstream-compat.yml` 为 source of truth，核心包括：

```text
.github/workflows/upstream-compat.yml
tools/qb-*.mjs
tools/data/qb-webapi-evolution-ledger.json
tests/upstream-release-audit.mjs
webui/private/scripts/qb-client.js
webui/private/scripts/settings-schema.js
```

明确不因为以下内容自动跑重型 audit：

```text
docs/**
README
CSS / 图片 / 翻译
普通 UI 布局
普通 tests
VERSION-only
installers
与 qB source/WebAPI evolution 无关的文件
```

普通 CI 已负责 `npm test`，因此 Upstream Compatibility Audit 不重复执行整套 `npm test`。

## 3. Product compatibility contracts

新增/修改产品兼容逻辑必须直接测试正式 product owner，例如：

```text
historical qB source facts / request / response
-> W.ReleaseProfile / W.QBClient / W.TorrentSemantics / W.SettingsSchema / W.CapabilityRegistry
-> canonical WeiG result

modern/future qB source facts
-> same product owners
-> same canonical WeiG semantics
```

测试重点：

- endpoint/action naming 与 parameter differences；
- response normalization；
- status/error behavior；
- native / normalized / derived / unavailable；
- read/write capability 分离；
- unsupported dangerous write 在 HTTP 前 fail closed；
- UI final state where relevant。

## 4. Upstream compatibility evidence

当前 WebAPI v2 source-derived stable matrix：

```text
qBittorrent 4.1.0 -> latest official stable
```

当前已验证 qB 4.1.0 -> 5.2.3，共 65 个 official stable profiles；stable 数量由 tooling 动态发现，不在文档硬编码为长期上限。

Source/evolution audit 证明的是：

```text
“上游是什么、发生了什么变化”
```

Full Stable PRODUCT Compatibility Matrix 证明的是：

```text
“正式 WeiG 产品 owner 是否正确消费这些事实”
```

两者职责不同；source audit PASS 不自动等于产品兼容 PASS。

## 5. Full Stable Product Compatibility Matrix

Phase C 已建立正式 all-stable product gate。

Candidate 流程：

```text
qB upstream stable source
-> generate exact qb-releases.json
-> upstream release audit
-> Full Stable PRODUCT Compatibility Matrix
-> upload exact catalog artifact
-> browser candidate jobs
-> release candidate reuses the same catalog artifact
```

每个 stable 至少验证：

```text
Filters
Category / Tags / Tracker / Path facets
Torrent actions
current column prerequisites
Settings Preference provenance
Search / RSS / Logs gating
```

不得用少数 representative fixture PASS 代替 formal full-stable matrix。

## 6. Virtual qB Pages — auxiliary product acceptance

Virtual qB Pages 的正确定位：

```text
same formal webui/**
-> Virtual qB historical profiles
-> Hosted Chrome real UI flows
```

它适合快速覆盖多 stable profile、normalization、filters/facets/columns/settings/search/rss/logs 的 capability presentation。

它不能替代真实 qB binary/server LIVE。

Workflow `head_sha` 可能显示 default branch main；source identity 仍以 triggering source SHA、exact checkout、`WEIGG_PAGES_SOURCE_SHA`、`WEIGG_EXPECTED_SIMULATOR_SHA`、deployed metadata 为准。

## 7. Representative real-qB validation during development

对于高风险产品兼容批次，应尽早增加 representative real-qB evidence，例如：

```text
minimum supported historical qB4
modern qB4
qB5 generation
latest official stable
```

具体 patch 不在文档硬编码；每次证据必须记录 exact qB version + WebAPI version + WeiG SHA。

如果某项兼容逻辑只能在 source/Virtual qB/browser fixture 中证明、尚无真实 qB binary evidence，汇报时必须明确标注。

## 9. Promotion-time frozen real-qB LIVE

准备晋级 `main` 时，冻结 final dev SHA，执行要求的真实 qB LIVE / operator validation。

统一脚本当前包括：

```text
tests/live.sh
tests/live-api.sh
```

LIVE 后 tree 变化，旧 evidence 作废。

## 10. Promote dev to main

必须满足：

- exact validated dev SHA；
- normal CI / relevant upstream / full-stable product evidence；
- relevant browser / Virtual Pages；
- required real-qB LIVE/operator confirmation；
- 用户/maintainer 显式授权；
- safe fast-forward。

只允许：

```text
main -> exact validated dev SHA
```

禁止 merge commit / force overwrite 未知 main-only commit。

## 11. Main-only candidate / Release

main 指向 validated SHA 后运行正式 candidate：

```text
full stable source/product audit
Linux Hosted Chrome representative matrix
Windows Hosted Chrome representative matrix
required real-qB evidence
exact-SHA candidate artifact
```

Artifact 必须携带 source-derived `qb-releases.json` 并绑定 candidate SHA/checksum。

Tag/Release 只发布同一 candidate artifact，不重新 build 不同产物。

## 12. Canonical chain

```text
normal dev push
-> smoke

product compatibility batch
-> product contracts
-> relevant browser / Virtual qB
-> candidate when full proof is needed

source/evolution-sensitive change
-> Full qB stable WebAPI evolution audit

when promoting
-> freeze dev SHA
-> final required real-qB LIVE
-> explicit authorization
-> safe fast-forward main
-> full candidate
-> artifact
-> tag/release same SHA
```

## 13. Red gate discipline

看到红灯先判定：

```text
real product bug?
upstream misunderstanding?
stale product test?
stale simulator/browser fixture?
source parser / profile problem?
CI trigger policy problem?
```

Real upstream/real-qB truth 优先。禁止为了旧 test/simulator expectation 回退正确产品兼容行为。

## 14. SAFE-REF

正式开发使用 `dev`；未经授权不动 `main`。

每次写入：

```text
fresh-read dev
-> build candidate
-> compare expected paths
-> validate
-> fresh-read dev again
-> force:false fast-forward
-> final SHA validation
```
