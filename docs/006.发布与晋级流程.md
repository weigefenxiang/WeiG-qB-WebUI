# 006. 发布与晋级流程

Status: **v0.3.7 release contract**

本项目把日常开发验证与正式 Release 候选验证分开。昂贵的完整 Linux / Windows Browser Matrix **只允许在 `main` 准备 Release 时手动运行**；普通 `dev` 提交、PR 和普通 `main` 状态不得自动消耗这两套 runner。

## 1. Dev validation

### 1.1 普通 dev push 只跑快速 gate

```text
dev push
  -> smoke
  -> npm/static contracts
  -> JavaScript / Shell / PowerShell syntax
  -> compatibility/platform/release contracts
  -> Upstream Compatibility Audit
```

普通 CSS、JS、测试和文档修改不会自动启动完整 Linux / Windows Chromium matrix。

GitHub UI 中仍可能看到 `Linux browser matrix`、`Windows browser matrix`、`release candidate` 为 `skipped`。`skipped` 不会启动对应 runner，也不会下载安装 Chromium。

### 1.2 开发阶段的 focused UI gate

需要真实浏览器确认响应式布局或共享 UI contract 时，只运行一个 Linux focused gate：

```text
dev commit message contains [ui]
  -> smoke
  -> Linux shared UI regression
```

也可以从 `dev` 手动运行：

```text
workflow_dispatch validation_mode=ui
```

这个 focused gate 只运行 `tests/browser-ui-system-v037.mjs`，用于快速确认 About、Settings viewport、StatusDock、Transfer editor 等共享几何/交互 contract；它不是完整 Linux Browser Matrix。

开发阶段不再提供 `[linux]` 或 `[candidate]` 提交 marker。提交这些字符串也不能启动完整 Linux / Windows matrix。

## 2. Ubuntu Actions 软件源

所有需要 `apt` 安装 Playwright 依赖的 Linux browser job，在安装前必须把 Ubuntu archive 归一化到：

```text
http://archive.ubuntu.com/ubuntu
```

兼容 GitHub-hosted Ubuntu runner 的：

```text
/etc/apt/apt-mirrors.txt
/etc/apt/sources.list
/etc/apt/sources.list.d/ubuntu.sources
```

不得把 Azure Ubuntu archive mirror 作为项目 Actions 的 apt 软件源。

这条规则只约束 Ubuntu apt archive。GitHub runner 自身的 Azure Region 元数据、第三方 action/CDN 内部实现或 Microsoft 自有软件仓库不等同于项目配置的 Ubuntu archive mirror。

## 3. Exact-SHA live gate

fixture / browser success 不等于生产认证。晋级到 `main` 前，当前最终 `dev` SHA 必须完成真实 qBittorrent 交互验收。

真实环境的 URL、凭据、Docker container 名、宿主机路径只属于 runtime input / operator notes，不能写进公开源码。

至少保留两个真实边界：

```text
Legacy LIVE: qBittorrent 4.1.9.1 / WebAPI 2.2.1
Modern LIVE: qBittorrent 5.2.x   / WebAPI 2.15.x
```

Live gate 必须明确对应当前 exact `dev` SHA。代码变化后旧 SHA 的 LIVE PASS 不能继承给新 SHA。

## 4. Promote dev to main for Release preparation

`.github/workflows/promote.yml` 需要：

```text
candidate_sha = exact current dev HEAD
live_gate     = LIVE-PASS
confirmation  = PROMOTE-VALIDATED-DEV
```

workflow 必须验证：

1. 从 `dev` 执行；
2. candidate SHA 等于当前 `dev` HEAD；
3. `main` 可以 fast-forward 到同一个 SHA；
4. 该 exact SHA 存在成功的 `dev` CI；
5. 该 exact SHA 的 `Upstream Compatibility Audit` 成功；
6. operator 明确确认 exact-SHA 真实服务器 gate 已通过。

通过后只允许：

```text
main -> exact validated dev SHA
```

禁止 merge commit，禁止 force-overwrite 未知的 main-only commit。

**Promotion 本身不运行完整 Linux / Windows Browser Matrix，也不要求 dev 先生成 Release artifact。** 完整双平台候选 gate 被明确后移到 `main` 的 Release 准备阶段。

## 5. Main-only Release candidate gate

当 `main` 已指向准备发布的 exact SHA 后，从 GitHub Actions 的 `CI` workflow 中选择 `main`，手动运行：

```text
workflow_dispatch
validation_mode=candidate
```

只有这一种路径允许启动完整候选：

```text
main exact SHA
  -> smoke
  -> Main release candidate guard
  -> Linux browser matrix
  -> Windows browser matrix
  -> package exact-SHA release candidate
  -> upload release-candidate-<SHA>
```

`Main release candidate guard` 会拒绝在 `dev` 或其它 ref 上运行 `candidate`。因此：

```text
dev push                         -> 不跑完整矩阵
PR                               -> 不跑完整矩阵
普通 main 状态                   -> 不跑完整矩阵
dev [ui]                         -> 只跑 focused Linux shared UI
main workflow_dispatch candidate -> 跑 Linux + Windows + RC
```

可复用 candidate artifact 包含：

```text
WeiG-qB-WebUI.zip
SHA256SUMS
CANDIDATE_SHA
```

WebUI payload 写入 exact `main` Git SHA；artifact 名称也带同一个 SHA。

完整 candidate 成功后，Release 阶段只复用这个 artifact，不重新构建。

## 6. Tag release 复用 main candidate artifact

`v*` tag 启动 `.github/workflows/release.yml`，但 Release workflow 是 publish-only。

禁止：

```text
checkout source to rebuild payload
npm test
Playwright
re-package WebUI from source
```

Release workflow 必须验证：

1. tag SHA 等于当前 `main` SHA；
2. exact SHA 存在成功的 `main` `workflow_dispatch` candidate CI；
3. 该 CI run 含未过期 `release-candidate-<SHA>`；
4. exact SHA 的 `dev` Upstream Compatibility Audit 成功；
5. artifact 内 `CANDIDATE_SHA` 等于 tag SHA；
6. `SHA256SUMS` 验证 ZIP；
7. ZIP 内 `WeiG-qB-WebUI/GIT_SHA` 等于 tag SHA。

Release workflow 不能把一个普通 main `smoke` workflow_dispatch 错认成 candidate：只有含 exact `release-candidate-<SHA>` artifact 的成功 main run 才是发布证据。

artifact 丢失、过期、SHA 不匹配或 checksum 错误时必须 fail closed，Release 阶段不允许临时重新构建替代品。

## 7. 稳定分发唯一事实源

普通用户稳定安装只认 GitHub Release：

```text
Latest Release page
https://github.com/weigefenxiang/WeiG-qB-WebUI/releases/latest

Payload
https://github.com/weigefenxiang/WeiG-qB-WebUI/releases/latest/download/WeiG-qB-WebUI.zip

Checksum
https://github.com/weigefenxiang/WeiG-qB-WebUI/releases/latest/download/SHA256SUMS
```

`dev` 和 `main` branch source archive 不作为稳定下载入口。没有 Release 时，代表没有正式稳定版，而不是自动把某个 branch 当 Release。

Linux/Windows installer 可以从 `main/installers/*` 作为 bootstrap 获取，因为 bootstrap 本身不是 WebUI payload；稳定安装最终只接受：

```text
latest GitHub Release asset
+ published SHA256SUMS
+ ZIP 内 exact GIT_SHA
+ complete Alternate WebUI entry points
```

当前 installer 采用稳定模式 **fail closed**：Release 不存在、checksum 缺失/错误、`GIT_SHA` 无效、`public/index.html` / `public/login.html` / `private/index.html` 任一缺失都会拒绝安装，且不会回退 `main` payload。

## 8. Canonical Release chain

Release identity 由 Git commit 定义，而不是 branch 名定义。

如果最终 dev commit 为 `X`：

```text
dev X
  -> cheap smoke PASS
  -> focused [ui] when needed PASS
  -> upstream compatibility audit PASS
  -> exact-SHA LIVE PASS
  -> fast-forward main to X

main X
  -> workflow_dispatch validation_mode=candidate
  -> Linux Browser Matrix PASS
  -> Windows Browser Matrix PASS
  -> artifact release-candidate-X
  -> tag points to X
  -> Release verifies and publishes artifact release-candidate-X
```

因此 canonical 流程固定为：

```text
dev exact SHA
  -> cheap/focused validation
  -> upstream audit
  -> live validation
  -> fast-forward main to same SHA
  -> one main-only full cross-platform candidate gate
  -> reusable exact-SHA artifact
  -> tag same SHA
  -> verify + publish same artifact
```

这满足两个目标：

- 日常开发不反复消耗 Linux / Windows Browser Matrix；
- 正式 Release 仍然必须经过完整双平台浏览器验证。

## 9. README / 安装文档发布规则

README 必须简洁，只做：

```text
产品一句话
Latest Release
Linux/Docker/NAS 一键安装
Windows 一键安装
手动安装
兼容范围
详细 docs 链接
```

完整平台差异、Docker path、NAS、更新、回滚和 checksum 放在 `007.安装升级与手动部署.md`。

README 不展示 Actions candidate artifact 给普通用户，也不把 GitHub Actions 临时 artifact 当稳定下载链接。

## 10. Failure policy

普通开发：

```text
smoke failure
-> fix dev
-> ordinary push again
-> do not spend browser runner minutes
```

Focused UI：

```text
[ui] failure
-> fix dev
-> keep using smoke while iterating
-> rerun focused Linux UI only when ready
```

Promotion / live gate：

```text
LIVE failure or dev validation failure
-> do not promote main
-> fix dev
-> validate the new exact SHA again
```

Main Release candidate：

```text
main candidate failure
-> do not tag / do not Release
-> return fixes to dev
-> cheap/focused validation
-> upstream + exact-SHA live gate again as required
-> fast-forward main to the new SHA
-> run one new main candidate
```

失败的 main candidate 不能因为旧 SHA 曾经 green 就被发布；Release workflow 也不能用 tag 阶段重测/重构建补偿 missing validated artifact。
