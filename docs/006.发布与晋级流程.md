## 1. Version discipline

只有正式 `webui/**` 产品内容变化才 bump patch VERSION。

一旦 `webui/**` 变化，以下四处同一最终 tree 同步：

```text
VERSION
webui/VERSION
package.json.version
package-lock.json root package version
```

仅 simulator/tests/tools/workflow/docs/DESIGN/installer/CI 变化时保持产品 VERSION。

Exact Git SHA 始终是 code/cache/test/Pages/LIVE/candidate/artifact evidence identity；任何新 SHA 不自动继承旧 SHA 的 runtime/candidate/LIVE evidence。Docs-only SHA 不要求重跑 runtime Pages 或重型 compatibility evidence，除非对应 workflow/gate 明确需要。

## 2. Validation tiers

不同改动使用不同深度验证，禁止所有 push 都跑最重矩阵。

### Tier 1 — normal dev / docs / tests / tooling-neutral changes

普通 `dev` push 运行：

```text
smoke
-> npm test
-> JavaScript / installer / script syntax
```

`docs/**`、README、纯文档/说明更新不触发 Full qB stable WebAPI evolution audit，也不触发 candidate browser/full-stable jobs。

### Tier 2 — product/UI compatibility batch

正式 `webui/**` compatibility 修改至少需要：

```text
smoke
-> direct product compatibility contracts
-> relevant browser/Virtual qB evidence
```

当通用 compatibility owners / formal product matrix 改变时，必须使用 frozen LKG 做历史 product regression：

```text
verify frozen LKG identity
-> architecture guard
-> Full Stable PRODUCT Compatibility Matrix on frozen profiles
```

该 regression 不 checkout qB upstream，不重新 source-extract verified historical profiles。

需要完整 candidate 证明时使用 `[candidate]` 或对应手动 candidate validation：

```text
exact catalog
-> all-stable source audit
-> Full Stable PRODUCT Compatibility Matrix
-> Linux browser
-> Windows browser
-> exact-SHA candidate package
```

### Tier 2.5 — future stable incremental admission

Future Stable Watch 必须先做最轻量的 official stable tag 集合比较：

```text
verify frozen LKG
-> fetch remote release-* tag names only
-> compare against admitted stable prefix
```

无新 stable：

```text
exit immediately
no upstream source checkout
no historical product regression
no source extraction
no repository write
```

有新 stable：

```text
checkout upstream source only then
-> source-extract only new stable profiles onto frozen LKG
-> reject retroactive history drift / frozen profile mutation
-> source audit support floor + newly discovered refs
-> product gate: support floor + previous admitted stable + new profiles
-> repository contracts / architecture guard
-> upstream + product capability diff
-> all gates PASS
-> fresh-check dev exact SHA
-> safe fast-forward catalog + manifest admission only
```

任一 parser/source/product/write-semantics/admission gate 失败：

```text
PENDING_REVIEW
candidate rejected
Last Known Good unchanged
```

仅新增 verified stable profile、且通用 runtime compatibility code 未变时，不要求重跑全部 frozen historical product matrix，也不得重新 source-extract 历史 profiles。

### Tier 3 — upstream source / stable discovery / WebAPI evolution audit

`Full qB stable WebAPI evolution audit` 是重型上游事实审计，不是普通 CI。

它用于验证：

```text
qB stable tag history / discovery logic
WebAPI revision history
source-derived API/actions/parameters/fields/filters/preferences
release-to-release surface evolution
WebAPI evolution ledger / changelog evidence
```

只有真正影响这些 source/discovery/evolution facts 的输入变化时自动运行；也保留 `workflow_dispatch` 手动运行。

当前自动触发范围以 `.github/workflows/upstream-compat.yml` 为 source of truth，核心包括：

```text
.github/workflows/upstream-compat.yml
tools/qb-release-catalog.mjs
tools/qb-release-tags.mjs
tools/qb-stable-admission.mjs
tools/qb-source-parsers.mjs
tools/qb-preference-semantics.mjs
tools/qb-torrent-surface-parsers.mjs
tools/qb-torrent-fields-parser.mjs
tools/qb-detail-surface-parsers.mjs
tools/qb-action-surface-parsers.mjs
tools/qb-catalog-evolution.mjs
tools/qb-catalog-quality.mjs
tools/qb-webapi-evolution*.mjs
tools/data/qb-webapi-evolution-ledger.json
tests/upstream-release-audit.mjs
```

明确不因为以下内容自动跑重型 audit：

```text
docs/**
README
普通 UI / CSS / 图片 / 翻译
webui runtime compatibility owner changes alone
普通 tests
VERSION-only
installers
与 qB source/stable-discovery/WebAPI evolution 无关的文件
```

普通 CI 已负责 `npm test`，因此 Upstream Compatibility Audit 不重复执行整套 `npm test`。

## 3. Product compatibility contracts

新增/修改产品兼容逻辑必须直接测试正式 product owner，例如：

```text
historical qB source facts / request / response
-> W.ReleaseProfile / W.QBClient / W.TorrentSemantics / W.SettingsSchema / W.CapabilityRegistry
-> canonical WeiG result

modern/future qB source facts
-> same product owners
-> same canonical WeiG semantics
```

测试重点：

- endpoint/action naming 与 parameter differences；
- response normalization；
- status/error behavior；
- native / normalized / adapter / composition / derived / read-only / unavailable；
- read/write capability 分离；
- unsupported/unknown dangerous write 在 HTTP 前 fail closed；
- UI final state where relevant。

## 6. Virtual qB Pages — auxiliary product acceptance

Virtual qB Pages 的定位：

```text
same formal webui/**
-> Virtual qB historical profiles
-> Hosted Chrome real UI flows
```

它适合快速覆盖 normalization、filters/facets/columns/settings/search/rss/logs 的 capability presentation，但不能替代正式 product compatibility 或真实 qB binary/server LIVE。

Workflow `head_sha` 可能显示 default branch main；source identity 仍以 triggering source SHA、exact checkout、`WEIGG_PAGES_SOURCE_SHA`、`WEIGG_EXPECTED_SIMULATOR_SHA`、deployed metadata 为准。

## 7. Representative real-qB validation during development

对于高风险产品兼容批次，应尽早增加 representative real-qB evidence，例如：


具体 patch 不在文档硬编码；每次 evidence 必须记录 exact qB version + WebAPI version + WeiG SHA。

如果某项兼容逻辑只能在 source/Virtual qB/browser fixture 中证明、尚无真实 qB binary evidence，汇报时必须明确标注。

## 10. Promote dev to main

未经用户明确授权，禁止修改 `main`、晋级、发布或执行任何可能改变 main 的操作。

授权后仍必须满足：

- exact validated dev SHA；
- normal CI / relevant upstream / product evidence；
- relevant browser / Virtual Pages；
- required real-qB LIVE/operator confirmation；
- safe fast-forward。

只允许：

```text
main -> exact validated dev SHA
```

禁止 merge commit / force overwrite 未知 main-only commit。

## 11. Main-only candidate / Release

main 指向 validated SHA 后运行正式 candidate：

```text
full stable source/product audit
Linux Hosted Chrome representative matrix
Windows Hosted Chrome representative matrix
required real-qB evidence
exact-SHA candidate artifact
```

Artifact 必须绑定 exact candidate SHA/checksum。Tag/Release 只发布同一 candidate artifact，不重新 build 不同产物。

## 12. Canonical chain

```text

-> smoke

general product compatibility change
-> frozen historical product regression
-> relevant browser / Virtual qB
-> candidate when full proof is needed

stable watch
-> lightweight tag compare
-> no new stable: stop

when promoting

```

## 13. Red gate discipline

看到红灯必须先读完整失败日志并判定：

```text
real product bug?
upstream/source misunderstanding?
owner/caller migration gap?
stale implementation-shape test?
stale simulator/browser fixture?
profile/evidence problem?
source parser problem?
CI trigger policy problem?
```

Real upstream/real-qB/canonical runtime truth 优先。正确 gate 抓到真实遗漏时修真正问题；stale test 则修 test。禁止为了旧 expectation 回退正确产品行为、放宽正确 gate、恢复旧 owner 或增加 compat hack。

## 14. SAFE-REF / proof discipline

正式开发使用 `dev`；未经授权不动 `main`。

每次正式写入：

```text
fresh-read dev exact HEAD
-> candidate uses that SHA as only parent
-> compare exact expected paths
-> validate
-> fresh-read dev again
-> if moved: candidate invalid, rebuild
-> force:false safe fast-forward
-> final exact-SHA validation
```

Repo-wide ownership/absence/uniqueness proof 必须使用目标 exact SHA 的完整 tree/blob/file 内容。Code search/snippet 只能用于发现，不可作为“全仓不存在”的最终证明。
