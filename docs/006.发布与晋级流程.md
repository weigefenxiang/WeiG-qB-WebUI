# 006. 发布与晋级流程

Status: **current release contract**

当前仓库只维护现行开发/发布链。历史 WeiG 版本的 runtime、tests、deploy scripts 不保留兼容副本；历史恢复使用 Git commits / tags / Releases。qBittorrent / WebAPI 的当前兼容版本门槛继续作为产品事实保留。

## Version discipline

产品 patch VERSION 的唯一 bump trigger 是正式 `webui/**` 产品内容变化。仅修改 tests、fixtures、workflow、docs、DESIGN、installer、CI/gate、package test tooling、test dependency 或 lockfile 时保持当前产品 VERSION。

一旦 `webui/**` 发生正式产品变化，Canonical version sources 必须在同一个最终 tree 中同步递增并完全一致：

```text
VERSION
webui/VERSION
package.json -> version
package-lock.json -> root package version
```

禁止只更新其中一处造成版本漂移。Browser/test fixture 需要产品版本时读取 canonical `VERSION`，禁止硬编码产品 patch 版本。

VERSION 是人类可读的产品状态标识；**exact Git SHA 始终是 code/cache/test/Pages/LIVE/candidate/artifact 的证据身份**。任何新 commit 都产生新的 exact SHA，哪怕是正确保持 VERSION 不变的 CI/docs/test-only change，旧 SHA 的 CI / Pages / LIVE / candidate / artifact 证据也一律作废。

Current semantic identifier 使用稳定职责名；`FOO-001/FOO-002` 这类 revision suffix 不进入现行架构。Git history/tags/Releases 承担 revision history。qB/WebAPI/Playwright 版本号属于 upstream/protocol/dependency facts，不受该命名规则影响。

## 1. Normal dev validation

普通 `dev` 开发不使用 `[candidate]`，也不依赖 `[ui]` 之类 commit-message prefix 才获得正常验证。

标准链：

```text
formal dev change
  -> exact dev SHA
  -> CI smoke / contracts / syntax
  -> Upstream Compatibility Audit
       qB 4.1.9.1 representative floor
       qB 5.2.x representative modern generation
  -> Virtual qB Pages Source when relevant
  -> default-branch Virtual qB Pages
       exact triggering source checkout
       simulator contracts
       exact dev/main snapshots
       build
       deploy
       real Chrome verify
  -> normal dev delivery
```

UI、UX、responsive、browser-visible、Virtual Lab/Pages 相关改动应由 normal Pages 做设计/浏览器验收。普通 dev 不因为“UI 变更”就改用 candidate commit message，也不在 `main` 前创建 release-candidate artifact。

Gate ownership 使用稳定职责边界：

```text
runtime-contract.mjs          global runtime invariants only
feature *-contract.mjs        feature semantic/Current Owner rules
naming-contract.mjs           stable filenames + revision-neutral semantic identifiers
syntax-contract.mjs           runtime/test JavaScript syntax only
ci-contract.mjs               browser-runtime / CI architecture
browser-driver.mjs            Playwright browser launch policy
browser-*.mjs                 real interaction + final semantic/visible state
pages-live-*.mjs              deployed Virtual qB Pages exact-source/final-state validation
workflow if                   main-only candidate source admission
```

禁止让总 gate 重复拥有 Theme/Feedback/Capability/Torrent 等专属实现形状；禁止为了同一条件再增加只做重复判断的 guard job。Private/PT semantics 属于 Torrent contract，不保留第二个 standalone semantics gate。

当前测试文件只用稳定职责名；禁止 `*-vNNN.mjs`、`live-vNNN.sh`、`live-qbNN.sh`。

## 2. Browser runtime ownership

Playwright JS dependency 由 repository exact pin：

```text
package.json + package-lock.json
→ playwright 1.62.1
```

`tests/browser-driver.mjs` 是唯一 browser launch-policy Current Owner。六套 `browser-*.mjs` 不直接 import Playwright，不选择 `channel` / `executablePath`，不实现 fallback。

三个 CI Browser path 全部复用 GitHub-hosted runner 已提供的 Google Chrome Stable：

```text
Linux semantic UI regression -> ubuntu-24.04 Hosted Chrome
Linux browser candidate       -> ubuntu-24.04 Hosted Chrome
Windows browser candidate     -> windows-2025 Hosted Chrome
```

其中名称包含 candidate 的 Browser jobs 只属于 main-promotion/release candidate 流程；普通 dev push 可以按 workflow policy skip 它们，不代表缺少 normal dev validation。

CI Browser path 禁止：

```text
npm install --no-save playwright@...
npx playwright install
npx playwright install-deps
manual Chromium download
browser-specific apt provisioning
silent fallback to Playwright-managed browser
```

Hosted Chrome 缺失直接 FAIL。每个实际执行的 Browser job 必须记录 runner image、Node、Playwright、Google Chrome exact version 和 `GITHUB_SHA`。

Hosted Chrome 可随 runner image 更新，因此 Browser 证据是：

```text
exact Git SHA
+ package-lock
+ runner image
+ exact logged Chrome version
```

它提供真实当前 Chrome 的跨平台 compatibility evidence 与可追溯性，但不声称同一个 SHA 在未来重跑时仍使用相同 browser binary。Release source/artifact reproducibility 继续由 exact SHA、candidate artifact 和 checksum 链负责。

Browser qB compatibility coverage 是 representative generation coverage：Linux 与 Windows各验证 qB 4.1.9.1 floor + qB 5.2.x modern path 的语义/UI 行为；不在每个平台启动 55 个 qB binary。全部 supported stable tags 由 Full qB Release compatibility audit 统一验证。

## 3. Upstream compatibility

普通 dev 代表性 audit：

```text
release-4.1.9.1
current representative qB 5.2.x generation
node tests/upstream-release-audit.mjs upstream-qb --refs=<representative refs>
```

Full candidate audit 动态枚举从 `release-4.1.9.1` 起所有官方 stable 4.x/5.x tags。当前 stable range 到 5.2.3，共 **55 个 supported stable releases = 40 qB 4.x + 15 qB 5.x**。

qB/WebAPI 版本号是当前兼容事实。例如 Private/PT 的 `qBittorrent 5.0.0+`、Tags 的 `WebAPI 2.3.0+` 必须继续保留。

## 4. Virtual qB Pages validation

Virtual qB Pages 是 normal dev 的持续浏览器/模拟后端验证面，不是 release candidate artifact。

流程：

```text
dev/main relevant push
→ Virtual qB Pages Source
→ default-branch Virtual qB Pages workflow
→ use workflow_run triggering exact source SHA
→ checkout exact source
→ validate simulator contracts
→ build exact dev/main WebUI snapshots
→ deploy GitHub Pages
→ wait for metadata/site.json exact simulator/source identity
→ real Hosted Chrome acceptance
```

Formal Pages workflow 是 `workflow_run` 时，GitHub UI 的 run-level `head_sha` 可能显示默认分支 `main`。实际被验证的 source identity 必须以 triggering workflow source SHA、`WEIGG_PAGES_SOURCE_SHA`、exact checkout 和 deployed metadata 为准。

Pages green 证明 Virtual qB / exact snapshot / real Chrome 的 normal dev state；它不能冒充真实 qBittorrent LIVE。

## 5. Exact-SHA Real LIVE gate

**只有准备晋级 `main` 时**，current final `dev` SHA 才必须真实验证：

```text
Legacy LIVE: qBittorrent 4.1.9.1
Modern LIVE: current qBittorrent 5.2.x
```

普通 dev 小步提交不要求每次重复 real qB4/qB5 部署；normal CI + Upstream + relevant Pages 是其自身交付证据。

部署脚本永久使用：

```text
tests/live.sh
```

它接收 exact SHA + target path，从该 SHA 自身 `webui/VERSION` 读取实际产品版本；不硬编码 WeiG release version，不创建 version-named staging/backup path。

无本地仓库：

```sh
SHA=<40-char-current-dev-sha>
curl -fL "https://raw.githubusercontent.com/weigefenxiang/WeiG-qB-WebUI/${SHA}/tests/live.sh" -o /tmp/weigg-live.sh
sh /tmp/weigg-live.sh --sha "$SHA" --target /path/to/weigg-qb-webui
```

Modern qB API regression 使用 `tests/live-api.sh`。脚本正文可以验证 qB 5.2.x/WebAPI capability；文件名不编码版本。

任何 code/test/docs/workflow 变化都会产生新 SHA；只有 `webui/**` 产品变化才同时产生新产品 VERSION。无论 VERSION 是否变化，旧 LIVE-PASS 都不得继承给新 SHA。

## 6. Promote dev to main

此时 final dev exact SHA 正式进入 candidate/promotion 语义。

`.github/workflows/promote.yml` 需要：

```text
candidate_sha = exact current dev HEAD
live_gate     = LIVE-PASS
confirmation  = PROMOTE-VALIDATED-DEV
```

必须验证 current dev、safe fast-forward、exact-SHA successful CI、exact-SHA upstream audit、operator LIVE confirmation。

通过后只允许：

```text
main -> exact validated dev SHA
```

禁止 merge commit / force-overwrite 未知 main-only commit。

## 7. Main-only Release candidate

`main` 指向已验证 exact SHA 后手动运行：

```text
workflow_dispatch
validation_mode=candidate
```

完整候选：

```text
main exact SHA
  -> smoke
  -> release-compat.mjs (18 real fixture releases + upstream/sentinel nodes)
  -> upstream-release-audit.mjs (all supported stable tags from 4.1.9.1 through current stable)
  -> Linux Hosted Chrome representative qB4/qB5 browser matrix
  -> Windows Hosted Chrome representative qB4/qB5 browser matrix
  -> package exact-SHA release candidate
  -> release-candidate-<SHA>
```

Candidate source eligibility 由各 candidate job 的 workflow `if` 直接拥有，不再创建重复 qualification guard job。

Artifact：`WeiG-qB-WebUI.zip + SHA256SUMS + CANDIDATE_SHA`。

## 8. Tag Release

`v*` tag 启动 publish-only Release workflow。必须验证 tag SHA=current main、successful exact main candidate、candidate artifact、dev upstream audit、CANDIDATE_SHA、SHA256SUMS、ZIP GIT_SHA。

Tag 阶段禁止重新测试、重新 build 或重新 package source。

## 9. Canonical release chain

```text
formal dev change
→ if webui/** changed: patch VERSION +1 in all four canonical sources
→ otherwise: preserve current product VERSION
→ dev exact SHA
→ normal contracts/naming/syntax
→ representative upstream audit
→ relevant Virtual qB Pages build/deploy/real Chrome verify
→ normal dev delivery

when maintainer decides to promote:
→ freeze current final dev exact SHA
→ exact-SHA real qB4 + qB5 LIVE
→ explicit maintainer authorization
→ safe fast-forward main same SHA
→ main-only full stable-tag audit
→ Linux representative Hosted Chrome candidate
→ Windows representative Hosted Chrome candidate
→ reusable candidate artifact
→ tag same SHA
→ verify + publish same artifact
```

旧 SHA 曾 green 不能为新 SHA 提供发布豁免。任何新 SHA 都必须取得自己的阶段对应证据；但不要把普通 dev validation 与 main-only candidate gate 混为一谈。
