# 006. Release and Promotion Flow

Status: **v0.3.7 release contract**

The stable branch must not be used as a second full-test environment. A release is a promotion of one exact `dev` commit that has already passed the complete automated gate and the required real-server gate.

## 1. Candidate validation

Full CI runs on `dev` pushes only:

```text
dev commit SHA
  -> smoke / syntax
  -> compatibility contracts
  -> Chromium regressions
  -> exact candidate SHA is green
```

Opening or updating a pull request must not run the complete browser matrix again against GitHub's synthetic `refs/pull/*/merge` commit. That merge commit is not the release artifact and can create a different SHA even when the source tree is identical.

`workflow_dispatch` remains available for an explicit manual rerun of the complete `dev` candidate gate.

## 2. Live gate

Automated fixture success is not production certification. Before stable promotion, the candidate must be deployed by exact SHA to the required real qBittorrent generations and validated interactively.

The live helper must remain environment-neutral. Deployment URLs, credentials, container names and machine-specific host paths are runtime inputs and must never be committed into the open-source project.

## 3. Stable promotion

Stable promotion uses `.github/workflows/promote.yml` and requires all three explicit inputs:

```text
candidate_sha = exact current dev HEAD
live_gate     = LIVE-PASS
confirmation  = PROMOTE-VALIDATED-DEV
```

The workflow verifies:

1. it is executed from `dev`;
2. `candidate_sha` is exactly the current `dev` HEAD;
3. `main` can be fast-forwarded to that SHA without history divergence;
4. a successful full `CI` push run exists for that exact `dev` SHA;
5. the operator explicitly confirms that the real-server gate passed.

Only after all guards pass does it execute a fast-forward:

```text
main -> exact validated dev SHA
```

No merge commit is created. No second full browser matrix is run on `main`.

## 4. Why main reuses dev CI

The release artifact is the Git commit, not the branch name. If `dev` commit `X` passed all gates and `main` is moved directly to the same commit `X`, the source tree, Git SHA, cache identity and deployable payload are identical.

Creating a new merge commit would produce a new SHA and would invalidate that exact-SHA guarantee. Therefore the canonical release path is fast-forward promotion, not a GitHub merge commit.

## 5. Failure policy

If any automated or live gate fails:

```text
Do not promote main
-> fix dev
-> produce a new candidate SHA
-> run full dev CI again
-> repeat real-server validation when the changed surface requires it
```

A failed candidate is never promoted merely because an earlier SHA was green.
