# 006. 发布与晋级流程

Status: **current CI / promotion / release authority**

本文档只描述长期有效的执行流程和门禁，不维护历史 Phase A–G checkpoint。

## 1. 正式 workflow

仓库只保留以下 6 个正式 GitHub Actions workflow：

```text
CI
Promote validated dev to main
Real qB Full Frozen Matrix
Release
Virtual qB Pages
Virtual qB Pages Source
```

删除或新增 workflow 时，必须同步检查 tests/contracts/docs 中的引用。

## 2. 分支职责

```text
dev   normal development / validation source
main  stable promoted branch
```

普通开发提交进入 `dev`。`main` 不作为第二开发分支，不接受独立产品修改。

稳定状态只保留 `main` 与 `dev`；临时 fix/tmp 分支完成后删除。

本轮 0.3.71 排障只允许修改 `dev`；未经用户明确授权，不修改 `main`、tag 或 GitHub Release。

## 3. Normal CI

`.github/workflows/ci.yml` 在 `dev` push 时自动运行 smoke：

```text
npm test
Linux installer syntax
live scripts syntax
PowerShell installer syntax
```

手动 `workflow_dispatch` 提供：

```text
validation_mode = smoke | ui | candidate
```

普通 docs/tests/tooling 维护以 smoke 为默认，不应自动触发 65-version real-qB heavy matrix。

## 4. Release candidate

准备发布时，先完成所有计划改动，再冻结一个 **final dev exact SHA**。

对这个 SHA 手动运行：

```text
Actions -> CI -> Run workflow
branch: dev
Validation depth: candidate
```

Candidate 至少必须通过：

```text
smoke
exact stable source catalog generation
all admitted stable source audit
full stable PRODUCT compatibility matrix
Linux hosted Chrome candidate
Windows hosted Chrome candidate
release candidate package
candidate deployment/rehearsal evidence
```

关键 artifact 绑定 exact SHA：

```text
qb-release-catalog-<SHA>
release-candidate-<SHA>
candidate-deployment-<SHA>
```

任何新 commit 都使旧 candidate evidence 失去对“当前 final SHA”的证明资格。

## 5. Full Frozen Matrix（G-FM）

`.github/workflows/real-qb-full.yml` 是发布前重型真实 qB 门禁。

触发方式：

```text
workflow_dispatch only
```

它**不跟随普通 dev push 自动运行**。

执行模型：

```text
Frozen LKG -> 65 exact stable versions
1 version / matrix job
fail-fast: false
max-parallel: 16
per-version exact-SHA evidence
aggregate exact-SHA evidence
```

发布前必须在同一个 final dev exact SHA 上取得：

```text
real-qb-full-aggregate-<SHA>
```

Aggregate 必须证明：

```text
expected_stable_count = 65
executed_runtime_count = 65
PASS = 65
FAIL = 0
BLOCKED = 0
missing_versions = []
duplicate_versions = []
unexpected_runtime_versions = []
```

Candidate 和 G-FM 可以并行运行以节省时间，但 promotion 必须等待二者都成功。

## 6. Virtual qB Pages exact-SHA 规则

Pages 分成两层：

```text
Virtual qB Pages Source
-> workflow_dispatch on the same dev/main ref
-> Virtual qB Pages
```

`Virtual qB Pages Source` 只负责 source/trigger choreography；`Virtual qB Pages` 才是唯一 build/deploy/verify owner。

必须使用 ref-bound `workflow_dispatch`，不要恢复 `workflow_run` deployment trigger。原因是 `actions/deploy-pages` 使用运行时 `GITHUB_SHA` 作为 Pages `pages_build_version`；`workflow_run` 的顶层 `GITHUB_SHA` 可能是默认分支 SHA，而不是真正的 triggering dev SHA。

Source relay 在 dispatch 前检查：

```text
triggering source SHA == current dev/main branch HEAD
```

如果 branch 已前进，该 source signal 视为 stale 并退出，让更新的 source run 接管。

对 dev exact SHA：

```text
workflow_dispatch on dev
-> checkout exact SHA
-> archive exact dev webui/**
-> verify Frozen LKG
-> materialize exact source/locale evidence
-> validate simulator contracts
-> upload virtual-qb-pages-site-<SHA>
-> deploy pages_build_version == exact dev SHA
-> Hosted Chrome live exact-SHA verify
```

对 main exact SHA：

```text
workflow_dispatch on main
-> DO NOT rebuild
-> find successful dev artifact virtual-qb-pages-site-<SHA>
-> validate/repackage main alias
-> deploy
-> verify live metadata/main alias == exact SHA
```

如果 main 对应 exact dev artifact 不存在，或 deploy success 后线上仍不是 exact SHA，必须 fail closed。

### 6.1 Pages live readiness contract

`catalogReady` 与 `catalogBusy` 是两个不同状态。大 catalog / 5000-torrent 场景可出现：

```text
catalogReady = true
catalogBusy  = true   # brief transition
```

因此 live acceptance 不应在 `catalogReady` 首次为 true 时立刻断言 busy=false。正确等待条件是：

```text
catalogReady === true && catalogBusy === false
```

必须保留合理 timeout 与最终 busy=false 断言；不能简单删除 busy 检查，也不能为了测试绿灯修改产品 state lifecycle。

## 7. Promotion

正式 promotion 使用：

```text
Promote validated dev to main
```

输入：

```text
candidate_sha = current final dev 40-char SHA
confirmation = PROMOTE-VALIDATED-DEV
```

Promotion 必须检查：

```text
candidate_sha == current dev HEAD
main can fast-forward safely to candidate_sha
successful exact dev candidate exists
release-candidate-<SHA> exists and not expired
candidate-deployment-<SHA> exists and not expired
successful manually-dispatched G-FM exists for same SHA
real-qb-full-aggregate-<SHA> exists and is 65/65 exact PASS
```

随后再次下载并验证 candidate、deployment evidence 和 G-FM aggregate。

最终只允许：

```text
git push origin <exact SHA>:refs/heads/main
```

必须是 fast-forward；禁止 merge commit、cherry-pick rebuild、force push。

## 8. Tag / Release

Promotion 和 main Pages exact reuse 都确认成功后，才能创建稳定 tag：

```text
v<VERSION>
```

Tag 必须满足：

```text
tag SHA == current main SHA == validated dev candidate SHA
```

Tag push 触发 `Release` workflow。

Release workflow 必须：

```text
verify tag/version identity
verify release SHA == current main SHA
find exact successful dev candidate run
reuse release-candidate-<SHA>
verify CANDIDATE_SHA
verify SHA256SUMS
verify ZIP embedded GIT_SHA / VERSION
publish existing validated artifact
```

Release workflow **不得重新 build 产品或重新生成一份 ZIP**。

正式 assets：

```text
WeiG-qB-WebUI.zip
SHA256SUMS
```

## 9. 推荐发布顺序

```text
1. finish all changes on dev
2. freeze final dev exact SHA
3. normal CI PASS
4. manually run G-FM on that exact SHA
5. manually run CI candidate on that exact SHA
6. ensure dev Pages exact artifact exists and live verify PASS
7. run Promote validated dev to main
8. verify main == dev == exact SHA
9. confirm main Pages exact reuse/live identity PASS
10. create tag v<VERSION> on exact main SHA
11. let Release workflow publish validated candidate artifact
12. verify Release assets/digests
13. clean temporary branches / obsolete workflow history if any
```

步骤 4、5、6 可以在同一 final SHA 上并行；7 以后不能跨 SHA。

## 10. Docs-only / maintenance 规则

纯 docs 变更不 bump VERSION，不运行 G-FM/candidate。

由于 `main` 是 stable promoted branch，而 promotion 强制 exact candidate + G-FM，普通 docs-only 提交可以只留在 dev，等待下一次正式 promotion 一并进入 main。

但必须记住：docs commit 仍会推进 Git SHA。旧 candidate evidence 只证明旧 SHA；真正准备 promotion 时必须基于新的 final exact SHA 重新建立所需 evidence。

## 11. Red gate discipline

红灯先分类再处理：

```text
product bug
source/profile misunderstanding
stale test / fixture / simulator
workflow trigger/choreography bug
runtime infrastructure problem
artifact identity problem
promotion/ref race
```

规则：

```text
完整日志优先
确定性 bug 必须修代码/contract
不降低断言
不放松 exact-SHA identity
不把 FAIL 改成 SKIP 伪造通过
仅明确瞬时基础设施故障才考虑同 SHA rerun
```

## 14. 本次维护复盘形成的永久规则

1. **重型矩阵低频化**：65-version G-FM 只在发布前/需要重新建立全版本 evidence 时手动运行，保留 `max-parallel: 16`。
2. **防忘跑**：promotion 自己强制查找同 SHA G-FM aggregate，不能依赖人工记忆。
3. **Pages 先 dev artifact 后 main**：main 的 exact reuse 前必须已有同 SHA dev artifact。
4. **deploy success 不是 identity success**：live exact-SHA verification 必须通过。
5. **删除 workflow 要同时退役 contract**。
6. **Release identity 不回写**：已发布 tag/release 视为历史 identity；后续维护不移动它们。
7. **Windows config mutation 是发布安全面**：外部安装器修改 qB INI 时必须 encoding-preserving、fail-closed、temp-verify、atomic-replace；详见 `docs/013.Windows配置编码事故复盘.md`。
