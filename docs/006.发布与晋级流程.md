## 1. 正式 workflow 职责

仓库正式 GitHub Actions workflow：

```text
CI
Virtual qB Pages Source
Virtual qB Pages
Real qB Current Stable Locale Matrix
Real qB Full Frozen Matrix
Promote validated dev to main
Release
```

Workflow 名称/职责/permissions/concurrency 是发布架构的一部分；改变时必须同步 contracts 与 docs。

## 2. 分支职责

```text
dev   唯一开发 / 修复 / docs / validation 入口
main  validated promotion result
```

所有产品、installer、workflow、tests、fixtures、docs、CI 修复先进入 `dev`。未经用户明确授权禁止直接修改 `main`、promotion、tag 或 GitHub Release；禁止 force push。

每个 mutation batch前 fresh-read `dev`；任何 ref update前再次 fresh-read做 race check。main只能从已经完成正式门禁的 final dev exact SHA safe fast-forward，`force:false`。

用户明确要求暂停/等待新方案时，任何已知 FAIL、TODO 或未来批次都不得自动开工；暂停不是 release permission，也不是 COMPLETED。

## 3. Ordinary CI

普通 `dev` push先由 classifier决定实际执行范围：

```text
product/source/runtime change -> relevant smoke/contracts/browser/source lanes
repository-only/docs change    -> classifier may skip product lanes
```

Top-level workflow `SUCCESS` 只能说明其实际执行的 jobs符合 workflow逻辑；每个 `SKIPPED` job仍然是 `SKIPPED`，不能记录成 PASS。

Docs/tests/tooling-only change不应为了制造“更完整绿色”而创建 no-op commit、添加 `[candidate]` 或主动触发 release-grade matrix。

Browser semantic lane 如果失败，即使 smoke SUCCESS，也表示该 exact checkpoint 的 ordinary CI 未闭环。先读完整日志；不要只看 workflow 标题颜色，也不要用另一次 bootstrap 内的 browser PASS覆盖当前 external FAIL。

## 3.1 Validation 时间预算、可观察性与并发

验证不能以“只要还在跑就继续等”为默认策略。单一步骤/单一 job 的时间预算：

```text
<= 60 s      正常
> 60 s       记录耗时并优先判断是否由可独立命令串行组成；可安全拆分时优先多 runner matrix/shard
3–5 min      必须说明不能拆分的依赖，或完成并行化/算法优化
> 5 min      必须有阶段性 progress/timing；天然独立任务应优先 matrix/shard
> 10 min     天然可分片的全量任务原则上不得继续单 runner 串行
> 30 min     若没有明确合理原因和持续可观察进度，视为验证设计异常，停止继续烧 runner并查根因
```

长任务首先提高可观察性，而不是先加 timeout。至少输出当前 shard/release、阶段、已完成/总数与阶段耗时；如果一个命令数分钟没有任何可解释进度，应能从日志定位其所处阶段。**当一个 step 稳定超过约 60 秒且内部是彼此独立的测试/命令时，默认优先拆成 job-level matrix，让每个 runner 独立报告结果；不要为了减少日志行数把独立测试重新串成一个长 step。** 若单个不可再安全拆分的测试本身略超 60 秒，可暂时独立保留，但必须成为可观察的独立 job，并继续 profile 是否存在可拆阶段。

对 browser/release/locale/fixture 等可以独立执行且最后可严格 aggregate 的验证，默认优先使用 bounded matrix/shard。普通 representative browser suite 可按独立脚本拆 job-level matrix；全版本任务优先采用 **最多 16-way 并发**，65-release任务通常优先拆成约16个 shard、每 shard 4–5 个版本，避免65个 runner各自重复 checkout/setup。具体 shard 数可因成本和任务形态调整，但不得为了追求并发破坏 source identity、顺序依赖或 aggregate完整性。

所有 shard必须绑定**同一个 exact Git SHA + 同一个 Frozen expected set/catalog identity**。Aggregate必须至少证明：

```text
executed == expected
missing == []
duplicate == []
unexpected == []
FAIL == 0
BLOCKED == 0
```

禁止把不同 SHA 的 shard结果拼成一个“全版本 PASS”。失败 shard可以用于定位；修复产生新 SHA 后，正式 full evidence必须在新 SHA 上重新闭环。对无法安全分片的任务，保留单 owner执行，但必须提供 bounded progress/timing并解释为什么不能并发。

## 4. Product commit / validation checkpoint / workflow-generated push

必须区分三种身份：

```text
product commit               真正改变 webui/** bytes
validation checkpoint        可只改 docs/tests，用于建立新的 external evidence
workflow-internal final tree CI job 内临时解包/验证的工作树
```

它们不能互相冒充。

当 workflow 使用 repository `GITHUB_TOKEN` 自己 push 新 commit 时，GitHub 的递归保护通常不会让该 push再次触发普通 push workflows。于是“workflow 里测试通过 + bot push成功”不自动等于“新 product commit 已获得 external ordinary CI/Pages evidence”。如果需要 external evidence，应使用仓库现有合法 dispatch/choreography，或由用户/正常授权主体产生明确 validation checkpoint；不得为了触发 Actions 随意改产品 bytes。

Docs-only `[ui]` checkpoint 只有在明确证明 `product commit -> checkpoint` 不改变任何 product bytes时，才可以用来为同一产品 bytes触发 external browser/Pages evidence。即使如此，evidence identity仍属于 checkpoint exact SHA；文档必须同时记录它代表哪个 product commit/bytes。

## 5. Candidate

只有用户明确进入最终验证/准备发布阶段，并且计划内产品/workflow/tests/docs已经完成后，才冻结 final dev exact SHA并建立 Candidate。

Candidate应在同一 exact SHA覆盖适用的：

```text
normal smoke/contracts
representative compatibility
exact stable source catalog/audit
source/locale enrichment + certified LKG
formal product compatibility
Linux/Windows hosted browser acceptance
release-candidate package
candidate deployment / official-qB rehearsal
```

Candidate package至少验证：

```text
VERSION
CANDIDATE_SHA / embedded GIT_SHA
SHA256SUMS
installer/package identity
```

`Full qB Release compatibility audit` 不等于 Real qB Full Frozen Matrix。

## 6. Virtual qB Pages

Canonical chain：

```text
Virtual qB Pages Source
-> classify/source/materialization evidence
-> dispatch exact-ref Virtual qB Pages when required
-> build exact materialized site
-> deploy
-> hosted browser/live identity verification
```

### 6.1 Dev materialization / representability

Dev Pages source classifier不能只看“本次 push before -> current”。当当前 push本身看起来 Pages-irrelevant时，还要比较：

```text
published downloads/dev/GIT_SHA
-> current dev SHA
```

只有 workflow明确证明中间全部 changes都不会改变 materialized public payload时，已发布 payload才可以代表 current dev runtime bytes。

这只是 Dev distribution/materialization优化：

```text
old product payload may represent unchanged runtime bytes
!=
new docs SHA automatically拥有 release-grade exact Pages evidence
```

Unknown/invalid/truncated compare或任何 Pages-relevant变化都应 fail closed并重新 materialize。

### 6.2 Build/deploy/live 三层必须分开

Pages `build` SUCCESS 只证明 exact source/materialization可以生成 site；`deploy` SUCCESS 只证明该 artifact已部署。最终 Pages PASS 还要求所有 required hosted-browser/live verify lanes PASS。

因此：

```text
build PASS + deploy PASS + any required live lane FAIL
=> Pages overall NOT CLOSED
```

Locale bootstrap、Settings anchor、release-profile、core/mobile/services等 live lanes各自拥有独立 acceptance 语义；一个 lane PASS不能覆盖另一个 lane FAIL。

### 6.3 Main Pages

Promotion后 main 应复用同一个已验证 final-dev artifact/bytes，不重新 full-build另一份产品。若 required exact artifact不存在，必须 fail closed。

## 7. Current Stable Locale Matrix

`.github/workflows/real-qb-locale.yml` 是 current latest admitted stable 的 focused real-qB language acceptance。

Release-grade Locale evidence必须来自 final dev exact SHA 的显式 manual dispatch，并由 target exact-SHA LKG派生：

```text
latest admitted stable
-> exact source/runtime identity
-> exact locale set
-> per-locale acceptance
-> aggregate
```

Locale count随 LKG演进，不是永久常量。普通 push中的 skipped/conditional Locale job不能作为 release evidence。

## 8. Real qB Full Frozen Matrix

`.github/workflows/real-qb-full.yml` 是发布前重型真实 qB gate，不属于日常开发反馈环。

Expected versions必须从 target exact-SHA Frozen LKG派生。每个 runtime至少证明：

```text
same WeiG exact SHA
requested qB == runtime self-report
exact release/source profile identity
runtime image/source-build identity auditable
capability/product acceptance PASS
cleanup PASS
```

Aggregate必须证明 expected == executed、无 missing/duplicate/unexpected runtime、FAIL=0、BLOCKED=0。

Final dev SHA未冻结前不要运行 Full Frozen Matrix；用户未明确授权时更不能运行。

## 9. Promotion gate

Promotion前必须证明**同一个 final dev SHA**拥有所有适用 release-grade evidence，例如：

```text
current dev HEAD == candidate SHA
normal CI success
candidate full chain success
release-candidate exact artifact
candidate deployment acceptance
required exact Dev Pages evidence
manual Current Stable Locale aggregate PASS
manual Real qB Full Frozen aggregate PASS
central release-compat evidence verifier PASS
main is ancestor / safe fast-forward possible
```

最终只允许：

```text
<current main> -> <validated final dev exact SHA>
```

并显式 `force:false`。

Candidate PASS、Pages PASS、main==dev、Actions顶层绿色任一单项都不能代替 formal promotion permission。

## 10. Tag / Release

Promotion成功、main Pages exact reuse/live identity确认后，才允许创建：

```text
v<VERSION>
```

必须满足：

```text
tag SHA == current main SHA == validated final dev SHA
```

Release坚持：

```text
build once
validate once
promote same bytes
release same validated bytes
```

Release workflow重新验证 tag/version/main SHA、candidate artifacts、deployment、Locale/G-FM exact evidence、checksums、ZIP embedded identity与必要 generated facts。

未经用户明确授权，不创建 tag 或 GitHub Release。

## 11. 推荐正式顺序

只有用户明确进入发布阶段时：

```text
all planned changes -> dev
-> freeze final dev exact SHA
-> normal CI
-> Candidate
-> required exact Dev Pages
-> manual Current Stable Locale Matrix
-> manual Real qB Full Frozen Matrix
-> central evidence verifier
-> user explicit promotion/release approval
-> safe-fast-forward main
-> main Pages exact reuse/live verify
-> tag
-> Release same validated bytes
```

Candidate、Pages、Locale、G-FM在 final SHA冻结后可按 workflow能力并行，但 Full Frozen应尽量留到开发彻底停止后的最终重型验证。

## 12. Red gate discipline

失败先分类：

```text
product bug
source/profile misunderstanding
stale test/fixture/docs/simulator
workflow choreography bug
runtime infrastructure issue
artifact/evidence identity issue
ref race
```

处理原则：读完整失败日志、修 root cause、source/runtime truth优先；不降低 assertion/provenance/exact-SHA gate，不把 FAIL改成 SKIP，不吞 runtime/source error。

Timeout不是自动等于“多等几秒”。Browser/Pages timeout必须先检查 semantic owner、readiness、selector、session/bootstrap顺序与可见状态；只有证据证明是合理慢路径时才调整 timeout。

只有明确 transient infrastructure failure才适合同 SHA rerun；确定性修复产生新 SHA 后，旧 evidence仍只属于旧 SHA。
