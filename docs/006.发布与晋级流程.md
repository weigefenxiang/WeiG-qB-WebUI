# 006. 发布与晋级流程

Status: **v0.3.7 release contract**

本项目把日常开发验证与正式 Release 候选验证分开。昂贵的完整 qB stable-tag、Linux/Windows Browser Matrix 和 Release candidate 只允许在 `main` 准备 Release 时手动运行；普通 `dev` 不反复消耗这些 runner。

## 1. Dev validation

### 1.1 普通 dev push：便宜 gate

```text
dev push
  -> CI smoke/static/platform
  -> JavaScript / Shell / PowerShell syntax
  -> Upstream Compatibility Audit
       qB 4.1.9.1
       qB 5.2.0
       current master WebAPI monotonic sentinel
```

`upstream-compat.yml` 只浅拉取 `release-4.1.9.1` 和 `release-5.2.0`，不在普通 dev 上获取完整 qB 历史和全部 tags。

GitHub UI 中可能看到 `Linux browser matrix`、`Windows browser matrix`、`Full qB Release compatibility audit`、`release candidate` 为 `skipped`。`skipped` 不启动对应昂贵任务。

### 1.2 开发阶段 focused UI gate

UI/响应式修改需要真实浏览器时，只运行一个 Linux Chromium focused gate：

```text
dev commit message contains [ui]
  -> smoke
  -> Linux shared UI regression
```

也可从 `dev` 手动运行：

```text
workflow_dispatch
validation_mode=ui
```

`tests/browser-ui-system-v037.mjs` 在同一次 Chromium 中固定使用：

```text
qB 4.1.9.1 -> mobile 390×844
qB 5.2.0   -> desktop 1440×900
```

它锁定共享 Settings/Brand/About/StatusDock/Transfer 等 contract，但不是 full browser matrix。

开发阶段不提供 `[linux]` 或 `[candidate]` commit marker 来启动完整矩阵。

## 2. Ubuntu Actions 软件源

所有需要 `apt` 安装 Playwright 依赖的 Linux browser job，在安装前把 Ubuntu archive 归一化到：

```text
http://archive.ubuntu.com/ubuntu
```

兼容：

```text
/etc/apt/apt-mirrors.txt
/etc/apt/sources.list
/etc/apt/sources.list.d/ubuntu.sources
```

不得把 Azure Ubuntu archive mirror 作为项目 Actions 的 apt 源。GitHub runner 显示的 Azure Region、Playwright CDN 或 Microsoft 自有仓库不等同于项目配置的 Ubuntu archive mirror。

## 3. Exact-SHA LIVE gate

Fixture/browser success 不等于真实 qB 认证。晋级 `main` 前，当前最终 `dev` SHA 至少必须完成：

```text
Legacy LIVE: qBittorrent 4.1.9.1 / WebAPI 2.2.1
Modern LIVE: qBittorrent 5.2.x   / WebAPI 2.15.x
```

真实 URL、凭据、container 名、宿主机路径只属于 runtime input/operator notes，不写入公开源码。

LIVE gate 必须对应 exact current `dev` SHA。任何代码/文档影响 candidate identity 的提交都会产生新 SHA，旧 SHA 的 `LIVE-PASS` 不自动继承。

## 4. Promote dev to main：只做同 SHA fast-forward

`.github/workflows/promote.yml` 需要：

```text
candidate_sha = exact current dev HEAD
live_gate     = LIVE-PASS
confirmation  = PROMOTE-VALIDATED-DEV
```

必须验证：

1. 从 `dev` 执行；
2. candidate SHA 等于当前 `dev` HEAD；
3. `main` 可以 fast-forward 到同一个 SHA；
4. exact SHA 存在成功的 dev CI；
5. exact SHA 的代表性 `Upstream Compatibility Audit` 成功；
6. operator 明确确认 exact-SHA LIVE gate 已通过。

通过后只允许：

```text
main -> exact validated dev SHA
```

禁止 merge commit，禁止 force-overwrite 未知 main-only commit。

Promotion 本身**不跑**完整 stable-tag/Linux/Windows candidate，也不要求 dev 先生成 Release artifact。

## 5. Main-only Release candidate gate

`main` 已指向准备发布的 exact SHA 后，从 CI workflow 选择 `main`，手动运行：

```text
workflow_dispatch
validation_mode=candidate
```

这是唯一允许完整候选的路径：

```text
main exact SHA
  -> smoke
  -> Main release candidate guard
  -> Full qB Release compatibility audit
       full fixture compatibility matrix
       all official stable 4.x/5.x tags from 4.1.9.1
       current upstream master WebAPI check
  -> Linux browser matrix
  -> Windows browser matrix
  -> package exact-SHA release candidate
  -> upload release-candidate-<SHA>
```

因此：

```text
dev normal push                    -> no full matrices
dev [ui]                           -> one focused Linux Chromium only
PR / ordinary state                -> no full matrices
main workflow_dispatch candidate   -> full qB + Linux + Windows + RC
```

Candidate artifact：

```text
WeiG-qB-WebUI.zip
SHA256SUMS
CANDIDATE_SHA
```

ZIP 内静态资源和 `GIT_SHA` 都写入 exact main SHA。完整 candidate 成功后，Release 阶段只复用这个 artifact，不重新构建。

## 6. Tag Release：verify + publish，同一个 artifact

`v*` tag 启动 `.github/workflows/release.yml`，Release workflow 是 publish-only。

禁止：

```text
checkout source to rebuild payload
npm test
Playwright
re-package WebUI from source
```

Release workflow 必须验证：

1. tag SHA 等于当前 `main` SHA；
2. exact SHA 存在成功的 main `workflow_dispatch candidate`；
3. 该 run 含未过期 `release-candidate-<SHA>`；
4. exact SHA 的 dev Upstream Compatibility Audit 成功；
5. artifact `CANDIDATE_SHA` 等于 tag SHA；
6. `SHA256SUMS` 验证 ZIP；
7. ZIP 内 `WeiG-qB-WebUI/GIT_SHA` 等于 tag SHA。

Artifact 丢失、过期、SHA/checksum 不匹配时 fail closed；tag 阶段不能临时重建替代品。

## 7. 分发频道

### Release — 默认稳定频道

稳定事实源仍然只有 GitHub Release：

```text
Latest Release
https://github.com/weigefenxiang/WeiG-qB-WebUI/releases/latest

Payload
https://github.com/weigefenxiang/WeiG-qB-WebUI/releases/latest/download/WeiG-qB-WebUI.zip

Checksum
https://github.com/weigefenxiang/WeiG-qB-WebUI/releases/latest/download/SHA256SUMS
```

Release installer 必须：

```text
Release ZIP
+ SHA256SUMS verification
+ valid exact GIT_SHA
+ complete Alternate WebUI entry points
```

Release 缺失或校验失败时 fail closed，**不会**自动退回 branch archive。

### dev — 显式开发频道

安装器允许用户明确选择 `dev`：

```text
Linux:   --channel=dev
Windows: -Channel Dev
```

dev installer 先解析当前 `dev` exact SHA，再下载该 SHA 的 source archive，只部署其中 `webui/`，并把 exact SHA 写入部署 identity。它明确标注 development channel，不冒充 Release，也没有 Release `SHA256SUMS` 证明。

`main` source archive 不作为稳定 payload fallback。

## 8. Canonical Release chain

如果最终 dev commit 为 `X`：

```text
dev X
  -> cheap smoke/static PASS
  -> qB 4.1.9.1 + 5.2.0 upstream audit PASS
  -> focused [ui] when needed PASS
  -> exact-SHA legacy + modern LIVE PASS
  -> fast-forward main to X

main X
  -> workflow_dispatch validation_mode=candidate
  -> full official stable-tag audit PASS
  -> full fixture compatibility PASS
  -> Linux Browser Matrix PASS
  -> Windows Browser Matrix PASS
  -> artifact release-candidate-X
  -> tag points to X
  -> Release verifies and publishes release-candidate-X
```

Canonical chain：

```text
dev exact SHA
→ cheap/focused validation
→ representative upstream audit
→ live validation
→ fast-forward main same SHA
→ one main-only full cross-platform candidate
→ reusable exact-SHA artifact
→ tag same SHA
→ verify + publish same artifact
```

## 9. README / 用户文档规则

README 保持面向用户：

```text
产品简介
Release/default install
explicit dev install
Linux/Docker/NAS
Windows
manual/browser download
更新/回滚/停用
兼容范围
详细 docs link
```

完整 CI、candidate artifact、LIVE/晋级工程细节放在 `docs/`，不把 README 写成 Actions 说明书。

## 10. Failure policy

普通开发：

```text
smoke/upstream failure
-> fix dev
-> cheap push again
-> do not spend browser matrix minutes
```

Focused UI：

```text
[ui] failure
-> diagnose/fix on dev
-> use static/smoke while iterating
-> rerun one focused Linux UI when ready
```

LIVE/Promotion：

```text
LIVE or exact-SHA dev gate failure
-> do not promote
-> fix dev
-> new SHA requires fresh validation
```

Main candidate：

```text
candidate failure
-> do not tag/release
-> fix on dev
-> repeat required dev/live gates for new SHA
-> fast-forward main to new SHA
-> run one new main candidate
```

旧 SHA 曾 green 不能为新 SHA 提供发布豁免。
