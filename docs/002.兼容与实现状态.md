# 002. 兼容与实现状态

> 当前状态文档。兼容真相以 `DESIGN.md`、上游源码生成的 stable release catalog、当前 contracts 与 exact-SHA CI/LIVE 证据为准；Git 历史负责保存旧实现。

## 1. 正式支持范围

- 正式支持下限：**qBittorrent 4.1.0**。
- 上限：**当前上游最新官方 stable**，不在文档中硬编码版本号或 stable 数量。
- Alpha / Beta / RC / master 不属于正式 stable 支持矩阵。
- `tools/qb-release-catalog.mjs` 每次从 qBittorrent 上游 tag/source 重新生成支持矩阵；`tests/upstream-release-audit.mjs` 对 4.1.0 到最新 stable 的每一个官方稳定版做完整审计。
- qB 4.6.1 的 WebAPI 事实固定为 **2.9.3**。

## 2. 单一兼容事实链

```text
qB upstream stable source
  -> tools/qb-source-parsers.mjs
  -> tools/qb-torrent-surface-parsers.mjs
  -> tools/qb-release-catalog.mjs
  -> qb-releases.json
  -> W.ReleaseProfile
  -> W.CapabilityRegistry / W.SettingsSchema / W.QBClient / W.TorrentSemantics
  -> Desktop + Mobile presentation
```

每个 release profile 至少包含：

- qBittorrent version / WebAPI version / tag / source SHA；
- `app/preferences` getter/setter descriptor；
- WebAPI action surface；
- Torrent filter surface；
- `torrents/info` 参数 surface。

运行时不再由各 caller 自己猜某个 patch 是否支持某项能力。

## 3. 能力降级规则

### 3.1 source-bound 能力

对能够从源码直接证明的能力，exact stable release profile 优先于版本区间猜测：

- Tags：以对应 upstream action 是否存在为准；
- Private filter：以 `torrents/info` 是否存在 `private` 参数为准；
- Stalled filter：以该 release 的 Torrent filter surface 是否存在 `stalled` 为准；
- start/resume、stop/pause：由 exact API action surface 决定。

### 3.2 不支持时隐藏

不在当前 upstream surface 中的普通控件/筛选项直接不展示，不保留 disabled + upgrade badge 噪音。确实发生不可用 route/action 尝试时，才由 canonical Capability Dialog 解释。

未知 capability id **fail closed**，不会默认为支持。

## 4. Torrent 状态兼容

`W.TorrentSemantics` 是 Torrent status/filter 的唯一语义 owner；`app.js`、`selection.js` 只调用它。

- qB4 的 `paused/resumed` 在 UI semantic boundary 统一表现为 `stopped/running`，HTTP boundary 再映射回该 release 的真实 upstream 名称；
- qB5 使用 upstream `stopped/running`；
- release source 中不存在的 filter fail closed，不再默认为 All；
- `progress >= 1` 只表示 Completed，不等于 Seeding；Seeding 必须来自 upload/seeding state；
- Private/PT 仍由 `W.TorrentSemantics` 统一分类，Private authoritative metadata 与可选 PT tracker-domain 规则分开处理。

## 5. Settings 兼容

`W.SettingsSchema` 是 Settings semantic owner。Preference routing 保持：

```text
exact schema -> semantic family -> Advanced / Upstream fallback
```

但**可写性不再由“当前值看起来是 scalar”决定**。对 exact stable profile：

1. upstream setter 必须存在；
2. write type 必须可解析；
3. getter/setter type 不得冲突；
4. descriptor 必须标记 writable；
5. arrays/objects 仍保持 read-only，直到存在专用 structured editor contract。

Enum / Boolean / Input 三类 canonical controls 都消费同一个 `editable` 事实；保存时 `S.writableDraft()` 再过滤一次，形成 defense in depth。

## 6. 发布物一致性

同一份 source-derived stable catalog 必须进入两类运行时：

- GitHub Pages Virtual qB artifact：`__source/private/data/qb-releases.json`；
- 正式 Release candidate ZIP：`private/data/qb-releases.json`。

禁止出现 Pages 使用 exact source facts、Release ZIP 却因为 404 回退到 heuristic 的双模式。

## 7. 验证层

- `npm test`：parser / ReleaseProfile / Capability / Settings / Torrent semantic / Simulator contracts；
- Linux + Windows hosted Chrome：代表性 qB4 floor / qB5-modern 真实 UI interaction；
- Upstream Compatibility Audit：4.1.0 → latest stable 全 stable 源码审计；
- Virtual qB Pages LIVE：exact deployed SHA、完整 Preferences stable matrix、source-derived Torrent filter/capability、六个 canonical Settings surfaces、Mobile layout/services。

所有证据绑定 exact Git SHA；新 SHA 会使旧 CI/LIVE 证据失效。
