# 012. qB 原生翻译与国际化复盘

Status: **0.3.71 native-first Settings translation architecture landed on `dev`; 65-stable source audit passed; exact official-TS compatibility bridge retained only where qB Alternative WebUI cannot execute QBT_TR**

本文记录 2026-09-11 对 Locale、qB 官方翻译、Alternative WebUI `QBT_TR`、QM provisioning 与 WeiG Settings 文案所有权的最终复盘。`DESIGN.md` 仍是 Current Owner 最终 authority；本文用于解释翻译链为什么采用 native-first，以及哪些历史 qB 版本必须保留兼容桥。

## 1. 最终产品原则

### 1.1 Locale 只有一个持久 owner

```text
qB app/preferences.locale
-> W.SettingsState / shared app.preferences
-> QBClient.setPreferences()
-> QBClient.getPreferences() verification reread
-> verified prefs.locale
-> W.I18n.applyLocale()
```

`qBittorrent preferences.locale` 是唯一持久语言真值。WeiG 不保存第二份语言设置，也不会在 qB 回读确认之前先切换视觉语言。

两个 UI 入口可以同时存在：

```text
WeiG WebUI -> Interface -> Language
qB Settings -> Advanced -> Locale
```

但它们编辑同一个 `draft.locale`、同一组选项和同一个保存事务。

### 1.2 qB-owned 与 WeiG-owned 文案必须分开

长期硬规则：

> 凡 qB upstream 已拥有且可以证明 exact source/context 的语义，WeiG 不重新拥有其译文；凡 WeiG 自己新增的语义，不能伪装成 qB 官方翻译。

因此：

```text
qB-owned wording
    qB official source/context
    -> QBT_TR
    -> qB translator
    -> official QM-derived translation

WeiG-only wording
    W.I18n minimal WeiG namespace
```

浏览器侧 JSON 不再作为 qB-owned 翻译主体。

## 2. qB 官方 WebUI 的真实翻译机制

qB WebApplication 可在发送文本资源时处理：

```text
QBT_TR(Source text)QBT_TR[CONTEXT=SomeContext]
```

服务器端根据当前 Locale 用 Qt translator 替换 marker。对于 dedicated WebUI translator 的版本，Alternative WebUI 所需语言资源位于 active WebUI root：

```text
translations/webui_<locale>.qm
```

因此“qB 有官方译文”与“Alternative WebUI 一定能执行 `QBT_TR`”是两回事：除了 QM 是否存在，还必须证明 `sendFile()` 会让 Alternative WebUI 进入 `translateDocument()`。

当前没有依赖一个假想的 WebAPI `translate(context, source)`；正式复用点是 qB 自己的 `QBT_TR`/Qt translator。

## 3. 65 个 admitted stable 的 source-derived translator family

已对 `4.1.0 -> 5.2.3` 全部 65 个 admitted stable 按 exact `sourceSha` 审计 `src/webui/webapplication.cpp`：

| qB stable | translation call | Alternative WebUI QBT_TR | translator resource | missing translation |
| --- | --- | --- | --- | --- |
| `4.1.0 -> 4.1.3` | `qApp->translate` | yes | application-installed translator | delegated to Qt application translator |
| `4.1.4` | `m_translator.translate` | yes | `<active-root>/translations/webui_<locale>.qm` | no explicit source fallback |
| `4.1.5 -> 4.4.5` | `m_translator.translate` | yes | `<active-root>/translations/webui_<locale>.qm` | explicit source fallback |
| `4.5.0 -> 4.6.4` | `m_translator.translate` | **no** | active-root QM exists but is ineffective for Alt UI | explicit source fallback |
| `4.6.5 -> 5.2.3` | `m_translator.translate` | yes | `<active-root>/translations/webui_<locale>.qm` | explicit source fallback |

关键边界：

`4.5.0 -> 4.6.4` 是不可通过“多放一个 QM”绕过的硬兼容洞：这些版本的 Alternative WebUI 不执行 document translation。因此这 11 个 stable 必须保留 exact official-TS compatibility bridge。

`4.1.4` 单独保留 strict family，因为其 dedicated translator 尚无明确 source fallback；缺译文时不能乐观猜测。

## 4. Current 0.3.71 的实际架构

0.3.71 延续并完成 Settings 文案 native-first 架构。正式链路是：

```text
candidate exact qB source
-> Preferences control relation
-> official QBT_TR source/context
-> source-SHA-bound translator behavior
-> native Settings registry
-> qB server-side QBT_TR
-> official minimal QM where active-root QM is required
-> W.I18n.qbSetting()
-> Settings.describe()
```

运行时优先级：

```text
1. current profile + locale is native-capable
   -> load data/qb-settings-native.txt
   -> qB server has already translated QBT_TR content

2. native resolution unavailable, but exact profile + locale is explicitly bridge-routed
   -> load only data/qb-settings/<sourceSha>.json
   -> translation body remains exact official qB TS-derived compatibility data

3. neither route is proven
   -> fail closed to generic/source text behavior
```

`W.I18n.qbSetting()` 仍是 Settings 消费接口，但它已经不再等价于“浏览器 JSON 翻译数据库”：它先消费 native QBT_TR 结果，只有 source-proven compatibility gap 才消费 exact shard。

## 5. QM provisioning 已进入正式 packaging

`tools/qb-settings-native-bundle.mjs` 与 `tools/qb-webui-catalog.mjs` 已把 source-derived native bundle 接入 packaging：

```text
qB official source/context + official translation facts
-> canonical minimal locale message set
-> Qt-compatible minimal webui_<locale>.qm
-> package translations/
```

同时生成：

```text
private/data/qb-settings-native.txt
```

其中只有 `QBT_TR(source/context)` registry 与 exact profile/reference mapping，不保存第二份人工译文。

QM 不是 WeiG 人工维护的语言包；它由 qB 官方 source/context 与官方 translation facts 机械生成。

当前 materialized payload 已实际验证存在 `webui_zh_CN.qm`，并且约 96 个 minimal `webui_*.qm` 进入构建输出。

## 6. JSON 的最终职责

### 6.1 translator behavior JSON

`tools/data/qb-translator-behavior-lkg.json` 只保存：

```text
qbVersion
sourceSha
translator behavior family
family structural facts
```

不保存翻译正文，不是语言包。

### 6.2 runtime release catalog

Runtime `qb-releases.json` 现在是 compact index，不再携带 65 个 full profile，也不携带 all-release Settings translation payload。Exact profile 独立位于：

```text
private/data/qb-release-profiles/<sourceSha>.json
```

Runtime index/profile 只保留 compatibility/source facts 与 translation routing facts，例如：

```text
settingsNativeLocales
settingsTranslationLocales
settingsTranslationPath
```

这种 sharding 既避免 qB real static-file size 风险，也让翻译正文退出 release catalog owner。

### 6.3 compatibility shard

`qb-settings/<sourceSha>.json` 没有被“全部删除”，因为 `4.5.0 -> 4.6.4` 的上游行为使纯 native 方案不可能覆盖完整支持范围。它现在是**窄化后的兼容 transport**：只有 source-derived route 明确要求时才允许存在和加载。

译文仍来自 exact qB official TS，而不是 WeiG 自行翻译；JSON 只是坏版本的 transport，不是主翻译库。

## 9. Virtual qB / Pages 的职责

Pages 不能依赖真实 qB 在构建时替换 `QBT_TR`，因此 simulator 层保留 validation-only emulator：

```text
current Virtual qB world
-> exact qbVersion + sourceSha + locale
-> translator behavior evidence
-> official frozen translation facts
-> QBT_TR emulation only when exact source family is native-capable
```

对于 `4.5.0 -> 4.6.4`，emulator 不会伪造 native capability；这些 profile 必须继续表现为 compatibility bridge route。

Pages emulation 只是验证设施，不进入真实产品 runtime。

历史 `catalogReady=true` / `catalogBusy=true` 短暂 transition 造成的 Pages acceptance wait race 已关闭；正确等待规则是：

```text
catalogError || (catalogReady && !catalogBusy)
```

不要重新把 stale assertion 或 browser locale 假设提升为产品 truth。

## 10. 不再采用的设计

以下方案明确不是目标架构：

```text
- 维护一份 WeiG 自有的完整 qB Settings 翻译 JSON
- 根据 qB semver 在浏览器里硬编码 translator 行为
- 假定所有有 m_translator 的版本都支持 Alternative WebUI QBT_TR
- 假定 5.0.x 仍处于 Alt-WebUI translation disabled 区间
- 为 4.5.0–4.6.4 仅复制 QM 然后宣称兼容
- 用人工译文替代 qB official source/context + translation facts
- 把 full translation bodies 重新塞回 monolithic qb-releases.json
```

## 11. 当前完成定义

0.3.71 的 Settings 翻译架构在 `dev` 上满足：

```text
- preferences.locale 是唯一持久语言 owner
- 65 stable translator behavior 由 exact sourceSha 证明
- qB-owned Settings 文案 native QBT_TR/QM 优先
- active-root 所需 minimal QM 进入正式 packaging
- 4.5.0–4.6.4 保留 exact official-TS compatibility bridge
- 4.1.4 继续 strict/fail-closed
- runtime catalog 不携带 all-release translation bodies
- compatibility shard 仅按 exact sourceSha + locale route 加载
- Virtual qB 不冒充上游不存在的 native capability
- package/file-size budgets 有 contract 保护
- full stable source/translation audit 已在 candidate CI 通过
```

当前结论仍是：

> **翻译主体回归 qB 官方 QBT_TR/QM；JSON 只保留为 source-proven 上游兼容洞的窄化 transport。**

## 12. 当前剩余门禁不是 translation architecture bug

以下历史问题均已关闭：

```text
candidate public-root exact build-SHA exposure
Pages catalogReady/catalogBusy acceptance wait race
Windows installer fail-closed / atomic qB config write hardening
```

当前 `v0.3.71` 仍不能直接 promotion/release 的原因是**发布证据身份**，不是上述功能仍失败：后续 docs/workflow commit 已推进 `dev`，所以真正准备发布时必须冻结新的 final dev exact SHA，并对同一个 SHA 建立：

```text
normal CI PASS
CI candidate PASS
Dev Pages exact-SHA build/deploy/live verify PASS
Real qB Full Frozen Matrix 65/65 PASS
```

这些 evidence 完成前不得把历史 candidate/Pages run 冒充 final SHA release permission。promotion/main/tag/Release 仍由 `docs/006.发布与晋级流程.md` 管理；dev-only 维护阶段不执行这些正式身份变更。
