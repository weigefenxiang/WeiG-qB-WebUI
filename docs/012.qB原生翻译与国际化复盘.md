# 012. qB 原生翻译与国际化复盘

Status: **translator audit + migration scaffolding landed / product cutover not yet started**

本文记录 2026-09-11 对 Locale / qB 官方翻译 / Alternative WebUI 翻译机制的重新复盘，并记录已完成的 admitted-stable translator behavior source audit、qB-owned string inventory scaffolding、QM provisioning plan 与 Pages validation-only QBT_TR emulation。它用于约束下一次产品改动，避免继续扩大临时 JSON translation projection。

`DESIGN.md` 仍是 Current Owner 最终 authority；本文明确区分“当前已经上线的事实”“已经完成的 source evidence”和“下一次产品切换目标”。

## 1. 已确认的产品原则

### 1.1 Locale 持久真值已经完成单 owner cutover

当前 `dev` 已经完成：

```text
qB app/preferences.locale
-> W.SettingsState / shared app.preferences
-> W.I18n.applyLocale(verified locale)
-> shared Desktop/Mobile presentation
```

`qBittorrent preferences.locale` 是唯一持久语言 owner。WeiG 不再保存第二份 `weigg-language`。

两个 UI 入口可以同时存在：

```text
WeiG WebUI -> Interface -> Language
qB Settings -> Advanced -> Locale
```

但它们必须编辑同一个 `draft.locale`、同一组选项、同一个 `QBClient.setPreferences()` 事务。

Locale 保存必须遵守：

```text
draft.locale
-> SettingsSchema writable provenance
-> QBClient.setPreferences()
-> QBClient.getPreferences() verification reread
-> verified prefs.locale
-> W.I18n.applyLocale()
```

不得在 qB 回读确认前先切换视觉语言。

## 2. qB 官方 WebUI 的真实翻译机制

重新核对 qB upstream `src/webui/webapplication.cpp` 后，确认不能把“官方译文存在”和“Alternative WebUI 自动拿到内置译文”混为一件事。

### 2.1 Built-in WebUI

现代 qB 的语言选项来自内置 Qt resource：

```text
:/www/translations/webui_*.qm
```

qB 根据这些 `webui_*.qm` 生成 `${LANGUAGE_OPTIONS}`。因此官方 WebUI 的翻译资源本来就在 qB 构建产物里。

### 2.2 QBT_TR 是 qB 的服务器端翻译抽象

qB WebApplication 在向浏览器发送可翻译文本资源时处理：

```text
QBT_TR(Source text)QBT_TR[CONTEXT=SomeContext]
```

并在服务器端把它替换成当前 Locale 的译文。浏览器收到的已经是替换后的文字。

因此，对于 qB upstream 已经拥有的语义，WeiG 的长期目标不是再建立一份浏览器 translation database，而是尽可能复用：

```text
official source/context
-> QBT_TR
-> qB translator
-> official translation
```

### 2.3 admitted stable 的真实 translator family

2026-09-11 已完成 `4.1.0 -> 5.2.3` 全部 65 个 admitted stable 的轻量 source audit。行为不是一个统一实现，而是四个 source-derived family：

| qB stable | translation call | Alternative WebUI QBT_TR | translator resource | missing translation |
| --- | --- | --- | --- | --- |
| `4.1.0 -> 4.1.3` | `qApp->translate` | yes | application-installed translator | delegated to Qt application translator |
| `4.1.4` | `m_translator.translate` | yes | `<active-root>/translations/webui_<locale>.qm` | no explicit source fallback |
| `4.1.5 -> 4.4.5` | `m_translator.translate` | yes | `<active-root>/translations/webui_<locale>.qm` | explicit source fallback |
| `4.5.0 -> 4.6.4` | `m_translator.translate` | **no** | `<active-root>/translations/webui_<locale>.qm` | explicit source fallback |
| `4.6.5 -> 5.2.3` | `m_translator.translate` | yes | `<active-root>/translations/webui_<locale>.qm` | explicit source fallback |

关键结论：

1. dedicated WebUI translator 的边界早于此前保守认知：`4.1.4` 已经从 active WebUI root 加载 `translations/webui_<locale>`；
2. `4.1.4` 必须单独保留为 compatibility family，因为它还没有 `loadedText.isEmpty() ? sourceText : loadedText` 这层显式 fallback；
3. `4.5.0 -> 4.6.4` 的 `sendFile()` 使用 `!m_isAltUIUsed && mimeType.inherits(text/plain)`，因此 Alternative WebUI 根本不会进入 `translateDocument()`；
4. `4.6.5` 移除了 Alternative UI guard，server-side translation 恢复；
5. `5.0.x` 已属于恢复后的路径，不需要等到 5.1/5.2。

因此：

> “存在 `m_translator` / active-root QM”不等于“Alternative WebUI 一定会执行 QBT_TR”。

native translation capability 必须同时由 `sendFile()` 的 `isTranslatable` source behavior 证明。

### 2.4 不假设存在“翻译 WebAPI”

当前复盘没有发现一个受支持的 WebAPI action 可以让 Alternative WebUI 请求：

```text
translate(context, source) -> localized string
```

因此不能设计成浏览器运行时逐句调用 WebAPI 获取官方译文。

正确复用点是 qB WebApplication 的 `QBT_TR`/translator 机制；对于要求 Alternative WebUI 自己提供 `.qm` 的 release，需要解决官方 QM provisioning，而不是发明 translation API。

## 3. 第三方 WebUI 的经验怎么用

第三方项目并不只有一种 i18n 方式。

现代 SPA 可以完全自己拥有前端 i18n。例如 `CzBiX/qb-web` 明确包含：

```text
src/locale/en.ts
src/locale/zh-CN.ts
src/locale/zh-TW.ts
src/locale/ru.ts
src/plugins/i18n.ts
```

这证明“第三方自己翻译”是一条可行技术路线，但**不是 WeiG 对 qB-owned 文案的首选路线**。它会重新拥有 qB 已经翻译过的语义，增加措辞漂移和维护成本。

WeiG 应优先复用 qB 官方机制；第三方 SPA 的组件、API、UI 架构可以参考，但不要机械复制它们的 translation ownership。

## 4. Current 0.3.69 的真实状态

当前 `dev` 产品版本仍为 `0.3.69`。Locale owner cutover 已经完成，但 qB-owned Settings 文案仍处于**过渡 transport**：

```text
candidate upstream source
-> exact Preferences control relation / QBT_TR source/context
-> exact official qB TS translation
-> candidate enriched catalog
-> packaging strips translation bodies from qb-releases.json
-> private/data/qb-settings/<sourceSha>.json
-> W.I18n.qbSetting()
```

浏览器只加载当前 exact release 的一个 shard，不再下载 65 个 release 的全部翻译。

这套实现有两个重要性质：

1. 译文本身仍来自 qB 官方 TS，并非 WeiG 人工翻译；
2. 它仍然是浏览器侧的 duplicate translation projection，因此只是过渡方案，不是长期 owner。

当前 candidate 已证明该过渡方案可以通过完整 65-release source/product audit、Linux/Windows browser、release candidate packaging 和 deployment acceptance。它可以作为回退点，但不应继续扩展成永久 translation catalog。

本次 translator behavior audit 与后续 migration scaffolding **没有**删除 shard、修改 `W.I18n.qbSetting()`、修改正式 `webui/**` 或 bump VERSION。Pages emulation 只存在于 Virtual qB simulator 层，不进入正式产品 runtime。

## 5. 最终目标架构

目标 owner 图：

```text
Persisted locale
    qB preferences.locale

Allowed locale set
    running qB ${LANGUAGE_OPTIONS}
    + source-SHA-bound frozen locale facts for simulator/history

qB-owned wording
    qB official source/context
    -> QBT_TR
    -> qB native translator / official QM

WeiG-only wording
    W.I18n minimal WeiG namespace

Compatibility facts
    qb-releases.json / W.ReleaseProfile
    + translator behavior evidence
    (NO translation bodies, NO translation ownership)
```

长期硬规则：

> 凡 qB upstream 已拥有的语义，WeiG 不重新拥有其译文；凡 WeiG 自己新增的语义，不能伪装成 qB 官方翻译。

## 6. `qb-releases.json` 与 translator behavior JSON 的职责

`qb-releases.json` 需要继续存在，是因为它承担 admitted stable 的 WebAPI/Preference/field/action/capability compatibility facts。

它**不需要、也不应该为了翻译**携带：

```text
settingsUi translation bodies
all-release translation sets
all-locale translation payload
```

新增的：

```text
tools/data/qb-translator-behavior-lkg.json
```

也不是语言包。它只保存：

```text
qbVersion
sourceSha
translator behavior family
family structural facts
```

不会保存：

```text
"Download": "下载"
source/context -> localized text
TS message bodies
QM payload
```

因此它是 compatibility evidence，不是第二 translation owner。

当前 0.3.69 的 `settingsTranslationPath` 仍是过渡指针。完成原生 QBT_TR/QM cutover 后，应与 `qb-settings/<sourceSha>.json` runtime projection 同批退休。

不要因为翻译架构调整而删除仍被正式 compatibility owners 使用的 release/source facts。

### 7.3 QM provisioning strategy：source plan 已完成

新增：

```text
tools/qb-qm-provisioning-source.mjs
tests/qb-qm-provisioning-source-contract.mjs
```

它不携带译文，而是从 exact `qbVersion + sourceSha + translator behavior + official TS path` 生成机械 provisioning plan：

- `qapp-native`：继续使用 application-installed translator，不强行塞 active-root QM；
- `dedicated-native-no-explicit-fallback`：生成 `active-root-qm-strict`，因为缺译文时不能假设安全 source fallback；
- `dedicated-native-explicit-fallback`：把 exact official TS 映射成 `translations/webui_<locale>.qm` 的 `lrelease` 输入/输出；
- `dedicated-alt-disabled`：明确生成 `compatibility-bridge-required`，不会假装“复制 QM 就能修复”。

历史 Locale code 到官方 TS 的解析继续复用现有 source-proven `resolveQbTranslationResourcePath()`；ambiguous identity fail closed。任何 `.qm` 都只能来自 qB 官方 translation source 的机械编译/复制，不人工修改 qB-owned 译文。

这个 plan 目前只证明“应该如何 provision”；还没有把 QM 放进正式 `webui/**` 包，也没有测最终 package size / lrelease toolchain，因此仍不是 production cutover。

## 8. 建议的产品 cutover 顺序

完成剩余 inventory/provisioning 后，一次 coherent 产品变更：

```text
1. add/prove native qB translation provisioning
2. define source-fact-driven compatibility transport for non-native families
3. migrate proven qB-owned UI strings to QBT_TR(source/context)
4. keep preferences.locale verification semantics unchanged
5. keep W.I18n only for WeiG-owned text + locale presentation helpers
6. remove W.I18n.qbSetting() browser translation database path where no longer required
7. remove obsolete qb-settings/<sourceSha>.json runtime projection
8. remove obsolete settingsTranslationPath from runtime release profiles
9. stop packing unnecessary translation payload into runtime compatibility artifacts
10. retain source/context and translator-behavior validation tooling as CI evidence
11. update browser/Pages/real-qB acceptance
```

Owner retirement 必须与 caller migration 同批发生，不能新旧两套 qB translation runtime 长期双活。

对于 `4.5.0 -> 4.6.4`，不能通过 `if (qbVersion === '4.x.y')` 一类手写翻译补丁绕过；差异必须来自 source-derived capability facts。

## 9. Pages / Virtual qB 的特殊问题

GitHub Pages 并不经过真正 qB WebApplication，因此它不会天然执行服务器端 `QBT_TR` replacement。

产品迁到 QBT_TR 后，Virtual qB Pages 仍需要**validation-only translation emulation**，否则页面会直接显示 `QBT_TR(...)` marker。该 scaffolding 现已落地：

```text
simulator/build/qbt-tr-emulator.mjs
simulator/service-worker/service-worker.js
simulator/build/build-pages.mjs
```

Pages 不能在 build 时固定翻译成某一个 qB 版本，因为同一静态站点通过 `?qb=...` 动态模拟 65 个 release。正确边界因此调整为：

```text
formal product webui/** remains untouched in this phase
real qB will perform production QBT_TR after product cutover

Virtual qB Service Worker
-> current world.profile.qbVersion + world.preferences.locale
-> exact source-SHA translator behavior LKG
-> frozen/source-derived official translation sets already carried by simulator catalog
-> validation-only QBT_TR emulation
```

`build-pages.mjs` 只复制 emulator 与 translator behavior evidence；真正的选择发生在 Service Worker 请求路径，因此可以按当前 Virtual qB 版本/locale 动态模拟。

关键 fail-closed 规则：

- exact `sourceSha` 对不上 behavior evidence：不翻译；
- `4.1.4` strict family 缺目标 translation：不替换 marker；
- `4.5.0 -> 4.6.4` `dedicated-alt-disabled`：标记 `blocked-by-upstream`，不假装 native QBT_TR 可用；
- native-capable + explicit source fallback family：缺译文时退回官方 source text。

这个 emulator 只用于 simulator/browser evidence，不进入正式 product runtime，也不新建第二份 translation JSON。Pages 仍禁止在每次部署时 clone/parse 整个 qB upstream history；它复用冻结 catalog 与 translator behavior evidence。

## 10. Candidate 性能复盘

前一轮约 20 分钟的 enrichment 主要来自：

```text
65 releases
× many locales
× historical TS blobs
× repeated git show / partial-clone blob fetch
```

不是 WeiG 主 WebUI 文件本身太大。

原始 enriched runtime catalog 一度达到约 29.6 MB，超过 qB Alternative WebUI 单静态文件 10 MiB 限制；0.3.69 用 per-release shard 解决了当前 candidate packaging 红灯。

但原生 QBT_TR cutover 后，正常 candidate 不应继续为了正式 runtime 生成全历史 translation payload。重型翻译 source scan 只应在：

```text
new official stable admission
translator/source parser change
explicit translation evidence refresh
```

等需要时运行。

translator behavior audit 本身只读取每个 admitted release 的一个 `webapplication.cpp`，不需要 release × locale × TS message 的重型扫描。

如果仍需重建历史 translation evidence，应优先 blob-SHA dedupe / `git cat-file --batch` / frozen artifacts，再考虑有限并发；不要单纯用高并发掩盖重复 I/O。

## 11. 必须避免的坑

1. 不恢复 `weigg-language` 或第二 persisted locale owner。
2. 不在 `languagechange` 里反向再写一次 qB。
3. 不在 verification reread 成功前视觉切语言。
4. 两个 Locale 控件不得维护不同 draft/options/save path。
5. 不把 qB-owned 中文/日文/德文重新手写进 WeiG dictionary。
6. 不假设 WebAPI 有逐句 translation endpoint。
7. 不假设所有 4.1.0+ release 的 Alternative WebUI translator 实现完全相同。
8. 不写 `if (qbVersion === '4.x.y')` 翻译补丁；历史差异应来自 source facts。
9. 不把 translator behavior JSON 变成 translation JSON。
10. 不把所有 TS translation bodies 重新塞回 `qb-releases.json`。
11. 不因为翻译解耦而删除 compatibility catalog 的 API/Preference/field/action facts。
12. 不让 Pages 的 translation emulation 进入正式产品 runtime。
13. 不为使旧测试变绿而恢复已经证明错误的架构；修 stale contract。
14. 不在 docs-only/tests-only/tools-only 变更中机械 bump 产品 VERSION。
15. 不主动运行 candidate / Real qB Full Frozen Matrix / promotion / main / tag / Release；这些是明确授权边界。
16. 任何 `webui/**` 产品修改都按仓库规则同步 patch VERSION 五处。
