# 001. 项目总方案

Status: **current project authority / AI handoff entry**

WeiG qB WebUI 是 qBittorrent Alternative WebUI。**`webui/**` 是唯一正式产品**；source catalog、真实 qB harness、Virtual qB、browser/Pages 与 CI 都是发现、验证和发布工具，不能反过来定义产品语义。

本文档不再维护 Phase A–G 等历史阶段。长期维护只记录当前目标、正式边界、执行流程与不可破坏的规则。

## 1. 长期目标

同一份正式 `webui/**` 应覆盖：

```text
qB 4.1.0
-> all admitted official stable releases
-> current latest official stable
-> future official stable / future major
```

兼容策略优先级：

```text
NATIVE
-> NORMALIZED / ADAPTER
-> reliable old-API composition
-> reliable DERIVED
-> READ_ONLY when applicable
-> UNAVAILABLE
```

对未来或未收录版本，无法证明的具体能力标记为 `UNKNOWN`。`UNKNOWN` 只关闭无法证明的能力，尤其危险写操作必须在 HTTP 前 fail closed；不能因为 major/version 更高就自动继承当前 latest 的语义，也不能按 major 整体拒绝。

## 2. 正式支持基线

截至 2026-09-10：

```text
latest stable WeiG release: v0.3.61
support floor: qBittorrent 4.1.0
Frozen LKG: qB 4.1.0 -> 5.2.3
stable profiles: 65
Frozen catalog: tests/fixtures/qb-release-catalog.lkg.json
manifest: tools/data/qb-stable-lkg.json
```

Frozen catalog 是已验收历史事实。新 stable 的 admission 可以扩展它，但不能无理由重写已验证历史。

qB 4.0.x / WebAPI v1 当前不在正式支持范围。如未来实现，只允许集中式 legacy adapter 进入 canonical WeiG semantics，禁止把 v1/v2 分支散落到 UI caller。

## 4. 分支规则

长期只保留：

```text
main   stable / promoted branch
dev    normal development branch
```

普通开发在 `dev`。`main` 只接受已经验证的 exact SHA 的 safe fast-forward promotion。

禁止：

```text
force push main
merge commit 代替 exact-SHA promotion
在 main 单独修改产品再发布
长期保留 fix/tmp/phase 工作分支
```

临时分支如确有需要可以短期使用，但完成后应删除；仓库稳定状态只保留 `main` 与 `dev`。

## 5. Exact-SHA 原则

Git SHA 是以下证据的共同 identity：

```text
source checkout
CI / candidate
real-qB matrix
Pages site artifact
promotion
release package
release tag
```

**任何新 commit 都产生新的 candidate identity。旧 SHA 的 candidate/G-FM/Pages evidence 不自动证明新 SHA。**

发布或 promotion 前必须使用当前 final `dev` exact SHA 重新取得所需门禁证据。

## 6. 兼容实现规则

正式兼容必须由 machine-readable source facts 与 canonical owners 驱动。

禁止：

```text
业务层手写 patch-version compatibility table
major>=5 之类作为最终产品行为 oracle
404/501 after click 作为 capability owner
manual compatibility mode
fake empty data 掩盖 unsupported/error
N items -> N compatibility requests
presentation self-probe
第二套 capability owner
第二套业务状态 / duplicate polling
runtime monkey patch / MutationObserver bridge 修复架构问题
```

允许 version 信息参与 source profile 选择、诊断和 evidence；但最终 feature truth 应来自 exact actions / parameters / fields / Preference provenance 等事实。

## 7. 发布规则摘要

完整 authority 见 `docs/006.发布与晋级流程.md`。长期顺序：

```text
finish changes on dev
-> freeze final dev exact SHA
-> normal CI PASS
-> manually run Real qB Full Frozen Matrix, exact SHA, 65/65 PASS
-> run CI candidate on the same exact SHA
-> ensure exact-SHA Pages dev artifact exists and is verified
-> Promote validated dev to main, fast-forward only
-> verify main Pages reuses the same exact dev artifact
-> tag current main exact SHA as v<VERSION>
-> Release workflow reuses the validated candidate artifact
```

G-FM 是发布前重型门禁，不跟随普通 dev push 自动运行；当前并发上限固定为 16。

## 8. Version 规则

只有正式 `webui/**` 产品行为变化才需要考虑产品版本 bump。纯 docs/tests/tools/workflow/Simulator 维护不应机械 bump 产品 VERSION。

正式 release tag 必须满足：

```text
tag == v<VERSION>
tag SHA == current main SHA == validated release candidate SHA
```

Release workflow 不得重新构建产品；应发布已验证 candidate 中的：

```text
WeiG-qB-WebUI.zip
SHA256SUMS
```

## 9. 维护纪律

修改 workflow、验证 contract、release choreography 时必须同时检查它们之间的依赖。**删除旧 workflow 时，必须同步搜索并退役引用该 workflow 的 tests/contracts/docs。**

Pages 使用 exact-SHA reusable artifact：如果 main 要复用某 SHA，则 dev 必须先为同一 SHA 生成并验证 `virtual-qb-pages-site-<SHA>`；不能先移动 main 再期待旧 artifact 自动适配。

任何 gate 变红时先按日志分类根因，不降低断言、不放宽 exact-SHA identity、不用重跑掩盖确定性 bug。
