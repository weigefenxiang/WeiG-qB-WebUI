# 005. 统一交互与设置系统

> 当前 Settings / capability / interaction contract。详细已落地 semantic ownership 以 `DESIGN.md` 为准；Virtual WebAPI semantic evolution 的目标 owner 见 003/009。

## 1. Canonical controls

Settings 继续复用统一组件：

- `W.Components.selectControl()`；
- `switch-control`；
- `field-input setting-input`；
- canonical Dialog / Feedback；
- shared section/grid/row layout。

不为 qB4/qB5、Desktop/Mobile 或某个 tab 建第二套控件系统。

## 2. 六个 qB Settings surfaces

Canonical qB surfaces：Downloads / Connection / Speed / BitTorrent / Web UI / Advanced。

Preference routing 由 `W.SettingsSchema` 唯一负责：

```text
exact schema -> semantic family -> Advanced / Upstream
```

Speed 独占 global/alternate rate limit、scheduler 与 rate-limit behavior；Advanced 不重复这些 key。

## 3. Exact Preference provenance

每个 official stable release 从 qB upstream getter/setter source 生成 descriptor：

- getter/read type/kind/confidence；
- setter/write type/kind/confidence；
- getter/setter agreement；
- writable；
- enum fallback provenance。

Setter-only key 不得逃出 `app/preferences` surface。

## 4. Editability

Exact stable profile 只有同时满足以下条件才可编辑：

- setter 存在；
- write type 可解析；
- getter/setter type 不冲突；
- descriptor `writable === true`。

否则保持可见但 read-only。Boolean/Enum/Input/Structured control 都消费同一个事实；`onDraft` 拒绝 non-writable，保存时 `writableDraft()` 再过滤。

## 5. Unknown / future Preferences

未来 stable 新 key 不静默丢失：

- family rule 能分类则进入对应 surface；
- 其余进入 Advanced / Upstream；
- scalar 在没有 exact setter provenance 时只读；
- array/object 先只读；
- 不猜 unit / enum / range / startup default。

## 6. 与 Endpoint Contract 的边界

Preferences 继续是独立 canonical truth，不并入新的 Virtual Endpoint Contract。

```text
W.SettingsSchema + Preference descriptors
  -> key/type/getter/setter/editability

Endpoint Contract (planned Virtual owner)
  -> 同一个 HTTP endpoint 在不同 WebAPI revision 的 request/response/status/mutation semantics
```

Endpoint Contract 可以**读取** world preference state 来决定 conditional projection，但不得复制 Preference schema、setter provenance 或 UI editability。

同样：

- CapabilityRegistry 不决定 Preference writable；
- SettingsSchema 不维护 endpoint historical response policy；
- QBClient 不维护产品版本策略；
- simulator router 不重新解释 Settings UI schema。

## 7. Owner cutover discipline

未来若 Settings/Preference 工具被新 canonical owner 真正替代，遵守 `OWNER-CUTOVER`：新接口先 isolated direct-test；验证成功后 atomic cutover 并删除 superseded old owner/helpers/tests。禁止新旧 Settings router/renderer 长期双活。

Endpoint Contract 的引入**不构成** Settings owner 替换，因此不得误删现有 Preference source pipeline。

## 8. 保存流程

```text
user interaction
-> canonical control
-> SettingsState.draft
-> writableDraft()
-> validateBeforeSave()
-> QBClient.setPreferences()
-> QBClient.getPreferences() verification read
-> canonical feedback
```

写成功但 verification read 失败时必须显示“已写入但无法确认”，不能伪装完全验证成功。

## 9. Mobile / acceptance

Mobile 使用同一 Settings DOM/state/controls/save flow。

Contracts 至少覆盖 exact routing、future family routing、missing/getter-only/type-mismatch read-only、source-proven future scalar writable、structured read-only、`writableDraft()` defense-in-depth 与 canonical control reuse。

Pages Real Chrome 使用 source-derived exact profiles验证六个 qB Settings surfaces，不硬编码某个最新 stable patch。
