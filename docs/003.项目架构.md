# 003. 项目架构

> 当前模块边界与产品兼容架构。最高优先级由 `001` / `010` 定义：`webui/**` 是唯一正式产品，真实 qB4/qB5 stable 自动适配是 P0；Virtual qB 是辅助验证层。

## 1. 总体边界

WeiG qB WebUI 是 qBittorrent Alternative WebUI。

正式产品主链：

```text
UI / presentation
-> canonical WeiG state/semantics
-> W.QBClient + product compatibility normalization
-> real qB WebAPI
```

辅助验证链：

```text
same formal webui/**
-> W.QBClient
-> Native Service Worker
-> Virtual qB protocol/runtime
```

Simulator 只能模拟真实 qB 后端，不能替代产品 compatibility layer，也不能要求 `webui/**` 依赖 simulator-only API。

## 2. 产品兼容 Current Owners

```text

```

一个 semantic purpose 只能有一个 Current Owner。UI/presentation 不复制 qB/WebAPI 版本表。

## 3. 产品 Compatibility Layer 的职责

产品 compatibility 需要把真实 qB 的历史差异归一化成 WeiG canonical semantics。

负责的典型内容：

- qB4/qB5 endpoint 名字映射；
- 参数重命名/格式差异；
- response shape normalization；
- status/result normalization；
- qB4/qB5 state/filter canonicalization；
- exact release capability facts；
- 可靠的旧 API 组合/emulation；
- 基于已获取 canonical data 的本地 projection。

原则：

```text
presentation -> canonical product owner -> real qB
```

而不是：

```text
presentation -> if qB4 ... else if qB5 ...
```

## 4. 自动适配策略

### 原生等价能力

直接映射。例如：

```text
WeiG start -> qB4 resume / qB5 start
WeiG stop  -> qB4 pause  / qB5 stop
```

### 同能力不同 shape

归一化。例如 legacy/modern `editTracker`、`torrents/add` response。

### 旧版可组合实现

允许 compatibility emulation。用户已经明确批准“功能尽可能在稳定 qB4/qB5 上都实现”的产品方向。

要求：

- 语义可靠；
- 性能可控；
- 不伪造 unavailable data；
- tests 覆盖 legacy/modern/error；
- 不创建第二业务 owner。

### 本地可可靠推导

允许从当前 canonical torrent/preferences data 推导 filter/facet/column value。

### 真正不可实现

才进入 capability hide/read-only/notice，并记录真实技术原因。

## 5. UI compatibility surface

以下必须由产品兼容层驱动自动适配：

### Torrent filters

全部、下载中、做种中、已完成、已停止、运行中、活动、非活动、停滞、上传停滞、下载停滞、校验中、移动中、错误、Private/PT。

### Facets

Tracker / 路径 / 分类 / 标签。

### Columns

所有正式字段，包括 Name / Size / Progress / Download / Upload / ETA / Status / Ratio / Tracker 等。

字段状态应能区分：

```text
native
normalized
locally-derived
unavailable
```

### Settings

下载 / 连接 / 速度 / BitTorrent / Web UI / 高级。

exact Preference getter/setter/type provenance 决定原生 surface；产品 compatibility 可以映射可靠的旧版等价语义。没有可靠写能力时只读，不存在且不可等价实现时不显示。

### Search / RSS / Logs

入口和 API flow 都按当前真实 release 自动适配，不能让用户点击后才得到 404/501。

### Actions / detail surfaces

Add/Delete/Start/Stop、Files/priorities、Trackers/WebSeeds、Peers、Categories/Tags、Metadata/Torrent Creator、Transfer 等全部正式功能都进入产品矩阵。

## 6. Source-derived structural truth — supporting owner

Build-time：

- `tools/qb-source-parsers.mjs`：Preference getter/setter/type provenance；
- `tools/qb-torrent-surface-parsers.mjs`：Torrent filter 与 `torrents/info` 参数；
- `tools/qb-release-catalog.mjs`：official stable exact release profile。

Runtime：

`W.ReleaseProfile` 消费 exact stable facts。

这层直接服务于产品适配，不只是 simulator metadata。

## 7. Virtual qB architecture — auxiliary only

```text
formal W.QBClient
-> Service Worker transport adapter
-> Transport Contract
-> structural upstream gate
-> protocol router + Endpoint Contract
-> QBSimulatorEngine / Scheduler / Policy / services
-> IndexedDB world
```

### Endpoint Contract

`simulator/protocol/endpoint-contracts.js` 是 **simulator 内部** same-endpoint historical semantics owner。

### Transport Contract

`simulator/protocol/transport-contract.js` 是 **simulator 内部** HTTP/auth/header/proxy historical owner。

这两个 contract 的存在不意味着产品兼容已完成。它们主要用于让 Virtual qB accurately reproduce upstream history，从而验证正式 `webui/**`。

## 9. Phase E — Current product architecture work

当前主工作：

```text
webui/** feature inventory
-> real upstream API dependency graph
-> qB4/qB5 difference analysis
-> product normalization/emulation
-> product tests
-> Virtual qB tests
-> representative real-qB tests
```

第一批：filters/facets/columns/actions/settings/search/rss/logs。

## 10. qB4.0.x / WebAPI v1

当前主 source matrix 从 qB4.1.0 / WebAPI v2 开始。

最终若覆盖全部 qB4 stable：

```text
Legacy WebAPI v1 Adapter
-> canonical W.QBClient semantics
-> same UI
```

禁止在多个 presentation/module 中维护 v1/v2 双路。

## 11. Future stable strategy

```text
new stable discovered
-> source profile
-> product capability/compatibility audit
-> evolution evidence
-> compatibility implementation if product affected
-> tests
```

未知 future semantics 不自动继承最后已知行为；但 fail-close 机制必须服务于产品安全，而不是成为阻止产品兼容开发的目标本身。

## 12. Validation hierarchy

```text
source truth
-> product compatibility contracts
-> Virtual qB browser matrix
-> representative real-qB tests
-> promotion real-qB LIVE
```

Real qB truth > simulator truth。

## 13. OWNER-CUTOVER discipline

所有新 product compatibility owner 仍遵守 single-owner / atomic cutover：

- 可以先 isolated tests；
- 切换后删除 superseded caller version policy；
- 禁止长期 old/new 双活；
- 禁止 presentation 复制 compatibility rule。

## 14. Development discipline

- 正式开发 `dev`；未经明确授权不动 `main`；
- 写前/ref update 前 fresh-read exact dev；
- 只允许 `force:false` fast-forward；
- 每个大阶段完成后停下复盘；
- 正式 `webui/**` 变化必须按版本规则 bump 产品 VERSION；
- simulator/docs/tests-only 变化不 bump；
- red test 先确认真实产品/upstream truth，再修正确层。
