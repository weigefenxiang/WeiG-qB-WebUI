# 010. 真实 qB 产品兼容路线

Status: **current compatibility strategy**

> 本文件描述 WeiG qB WebUI 如何长期兼容真实 qBittorrent，不维护 Phase A–G 历史路线图。

`webui/**` 是唯一正式产品。目标不是把 Simulator 做得更复杂，而是让同一份 WeiG WebUI 在 qBittorrent 4.1.0 起的 admitted official stable、当前 latest stable 与未来 official stable 上保持正确产品语义。

## 1. 长期兼容目标

```text
qB 4.1.0
-> all admitted official stable releases
-> current latest official stable
-> future official stable / future major
```

能力解析顺序：

```text
NATIVE
-> NORMALIZED / ADAPTER
-> reliable old-API composition
-> reliable DERIVED
-> READ_ONLY when applicable
-> UNAVAILABLE
```

未来/未收录版本中无法证明的能力为 `UNKNOWN`；dangerous write 必须 fail closed。

## 2. Source truth first

兼容行为应从 qB official source 与 exact release facts 推导，而不是从版本号猜。

核心链：

```text
qB official source
-> generated exact stable facts
-> admitted Frozen LKG
-> W.ReleaseProfile
-> canonical compatibility owners
-> W.QBClient
-> product UI
```

正式 facts 包括：

```text
qB/WebAPI/source identity
actions
required/optional parameters
Torrent states / filters
Torrent info fields
Details response fields
Preference getter/setter/type provenance
translator behavior / locale routes
```

## 3. Version 信息的正确用途

允许：

```text
选择 exact/equivalent/inherited release profile
source catalog indexing
diagnostics / evidence
runtime identity verification
```

不允许把版本条件当最终产品 truth：

```text
if major >= 5 then feature=true
if version >= x then blindly send write
nearest version wins across hard boundary
unknown future version gains new dangerous capability by assumption
```

如果存在历史 API shape transition，应在 source-backed normalize/adapter 层解决，不把 patch-version 分支散落到 presentation。

## 4. Release profile resolution

当前 runtime resolution mode：

```text
EXACT
EQUIVALENT
INHERITED
FALLBACK
```

### EXACT

官方 stable tag/canonical version 已在 Frozen/admitted catalog 中，加载对应 exact profile。

### EQUIVALENT

版本只是 canonical suffix/packaging variation，能够证明语义等价，例如：

```text
5.2.3-r1 -> 5.2.3
```

### INHERITED

尚未 admission 的未来 patch/四段版本，可在**同 major.minor** 范围内临时解析到最近较低且已认证的 profile，例如：

```text
5.2.3.1 -> 5.2.3
5.2.4   -> 5.2.3
```

但 inheritance 只复用“最后已证明的事实”，不能 invent 新 facts。必须同时满足 runtime WebAPI/source contract 没有证据表明比 base 更旧或跨越 hard boundary。

### FALLBACK

不存在安全 exact/equivalent/inherited relation 时进入 fallback。危险写操作保持 UNKNOWN/fail closed。

Runtime diagnostics 必须保留：

```text
detectedVersion
resolvedFrom
resolutionMode
```

## 5. Inheritance 不是 nearest-wins

允许“5.2.4 暂时使用 5.2.3 profile”不意味着可以任意找最近版本。

必须避免：

```text
跨 major.minor 盲继承
跨 source-proven translator/API hard boundary
把 inherited profile 当成新版本能力证明
因为 server 接受请求就补写 capability=true
```

已知硬边界例：

```text
qB Alternative WebUI translation behavior:
4.6.4 -> 4.6.5
```

`4.5.0-4.6.4` 的 Alternative WebUI 不执行 document translation，`4.6.5+` 恢复 native path。不能用简单“距离最近”跨这个边界路由翻译。

## 6. Capability 粒度

兼容必须按能力而不是按页面粗粒度判定。

```text
Category: read/filter/list/create/delete/assign independent
Tags: read/filter/list/create/delete/assign independent
Tracker: read/add/remove/edit/reannounce independent
Settings: endpoint read/write + per-Preference writable independent
Details: properties/files/trackers/peers/webseeds independent
Actions: action presence + parameter contract independent
```

这样旧 qB 可以保留真实拥有的功能，而未来 qB 的未知 write 也可以安全关闭。

## 7. Normalize / Derived 原则

当历史版本返回不同 shape，但语义可可靠归一化时允许 `NORMALIZED`。

当新能力可以由旧 API 的稳定组合可靠推导时允许 `DERIVED`。

必须满足：

```text
semantics are deterministic
cost is bounded
no N->N compatibility requests
no hidden second state
no fake data
```

如果推导不可靠，应降级为 `READ_ONLY` / `UNAVAILABLE` / `UNKNOWN`，不能为了 UI 一致性伪造支持。

## 8. Fail-closed 写操作

任何 destructive/mutating action 都必须在 transport 前证明：

```text
endpoint/action exists
required parameter contract is known
current capability owner allows it
payload semantics are validated
```

Settings 还要求 per-Preference setter/type agreement。

以下情况不得发送 HTTP：

```text
unknown action
unknown required parameter
missing setter
preference type mismatch
unproven structured value
inherited/future profile without write provenance
```

## 9. Frozen LKG 与新 stable admission

当前基线：

```text
qB 4.1.0 -> 5.2.3
65 official stable profiles
```

Frozen LKG 代表已经验收的历史 source facts，保持完整、可审计、不可随意重写。

发现新 official stable 时：

```text
verify current Frozen LKG
-> discover exact new tag/source identity
-> extract new source facts
-> preserve historical prefix
-> audit source semantics
-> run product compatibility contracts
-> inspect compatibility diff
-> admit after review
```

在正式 admission 完成前，受约束的 same-series `INHERITED` 可以作为临时 runtime fallback；admission 完成后应切到新版本自己的 `EXACT` profile。

禁止把 inheritance 当作“不需要新 stable source audit”。

## 10. Runtime catalog

真实 qB 4.6.7 已证明 production runtime 不应加载一个接近 10 MiB 的 monolithic all-profile catalog。

当前 runtime：

```text
private/data/qb-releases.json                     # compact index
private/data/qb-release-profiles/<sourceSha>.json # exact profile shard
```

运行时只加载当前 resolved profile shard。完整 65-profile evidence 留在 build/audit 层。

Catalog/profile HTTP load failure 必须显式报错，不允许吞成空 catalog 后伪装成普通 unsupported。

## 11. Real-qB 证明层

Source facts 与 formal product matrix 是必要条件，但最终仍需要真实 qB runtime 证明关键语义。

全版本规则见 `docs/011.全版本真实qB验证规则.md`。

核心要求：

```text
exact qB version/runtime identity
same formal webui/**
capability-driven harness
isolated environment
safe writes only
per-version evidence
complete aggregate
```

找不到真实 runtime、版本 identity 不匹配、harness crash、cleanup failure 都不能伪装成 PASS。

历史 `Candidate qB public root did not expose exact build SHA` 红灯已经关闭；对 `ba8ee49886fad159e76014514b5a0a4ba803bc29` 的 qB 4.6.7 / 5.2.3 candidate deployment acceptance 均 PASS，并验证 exact build identity、Settings/locale round trip 与 `remoteWrites = 0` rehearsal。

当前未完成的不是该历史 candidate bug，而是**新的 final dev exact SHA 尚未建立完整发布证据**。正式 release-grade compatibility evidence 必须在同一个 final SHA 上同时拥有：

```text
candidate / deployment evidence
exact Pages evidence
manual Current Stable Locale Matrix aggregate
manual Real qB Full Frozen Matrix aggregate
central release compatibility verifier PASS
```

Current Stable Locale Matrix 证明 latest admitted stable 的全语言行为；Full Frozen Matrix 证明整个 Frozen stable 区间的真实 runtime compatibility。两者职责不同，不能互相替代。

**Full Frozen Matrix 不属于日常开发反馈环。** 普通 dev push、中间 checkpoint、普通修复或 docs/tests/tooling 维护都不应运行 65-version Full。先完成所有计划改动、冻结 final dev exact SHA，再在最终验证/准备发布阶段手工执行；如果 Full 之后又产生新的最终发布 commit，旧 aggregate 只证明旧 SHA，真正发布时对新的 final SHA 再做最后一次即可。

## 12. Virtual qB 的定位

Virtual qB 用于快速、可重复地覆盖 UI/transport/semantic scenario，但它是 auxiliary evidence。

原则：

```text
real source/runtime truth > simulator expectation
```

如果 Virtual qB 与正确 qB source truth 冲突，应修 Virtual qB/fixture，而不是修改正式产品去迎合模拟器。

Pages relevance / exact-SHA choreography 允许日常 docs-only commit 不重建重型 Pages；这不改变正式 release final SHA 必须拥有自己的 exact Pages evidence。

## 13. 性能约束

兼容层不应让正常运行付出明显额外成本。

禁止：

```text
per-row capability HTTP
per-item feature probe
重复拉取同一业务状态
高频 upstream/source discovery
presentation 自行探测 capability
```

优先在 build/admission 时生成 source facts，在 runtime 只消费 compact index + active profile/owner state。

## 14. 当前正式支持之外

qB 4.0.x / WebAPI v1 目前是 future optional，不在正式 CI/G-FM 范围。

未来如支持：

```text
Legacy WebAPI v1 Adapter
-> canonical WeiG semantics
```

必须集中实现，不允许 v1/v2 分支散落各个 UI caller。

## 15. 兼容改动验收原则

任何正式 compatibility 改动至少回答：

```text
source truth 是什么？
哪个 Current Owner 消费这个 truth？
read/write/action/field 是否需要拆分？
UNKNOWN 如何 fail closed？
EXACT/EQUIVALENT/INHERITED/FALLBACK 如何解析？
是否跨 hard boundary？
旧 stable 是否回归？
future stable 是否避免错误能力继承？
真实 qB evidence 是否需要重跑？
```

发布前最终 exact SHA 的完整门禁由 `docs/006.发布与晋级流程.md` 定义。日常开发继续只进入 `dev`；在 dev-only 维护阶段不移动 `main`、不建 tag、不开 Release，也不提前机械运行 Full Frozen Matrix。
