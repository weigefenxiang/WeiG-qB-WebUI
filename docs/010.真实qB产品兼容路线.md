# 010. 真实 qB 产品兼容路线

Status: **P0 product roadmap / Phase A DONE / Phase B NEXT**

> 本文件定义 WeiG qB WebUI 当前最高优先级。`webui/**` 是唯一正式产品；真实 qBittorrent 4.x / 5.x 稳定版兼容是产品目标。Virtual qB、WebAPI evolution ledger、source catalog、Endpoint/Transport Contract 都是为了发现、实现或验证 `webui/**` 兼容性的辅助基础设施，本身不是产品目标。

## 1. 最终产品目标

同一份：

```text
weig-qb-webui/webui/*
```

应该能够直接放到受支持的真实 qBittorrent 实例上使用，不要求用户：

- 选择 qB4/qB5 专用包；
- 手工选择 WebAPI 版本；
- 修改 WeiG 配置来适配具体 patch；
- 更换另一套 WebUI。

产品应自动检测真实 qBittorrent / WebAPI / source capability，并把版本差异消化在产品兼容层内。

目标范围是 **qBittorrent 4.x / 5.x official stable**。当前已经建立并自动审计的 WebAPI v2 structural matrix 从 **qB 4.1.0 -> latest official stable**；qB 4.0.x 属于旧 WebAPI v1，当前仍是明确产品缺口。如果目标要求覆盖全部 qB4 stable，则必须实现独立 Legacy WebAPI v1 Adapter，而不是在 v2 caller 中散落 fallback。

## 2. 主次关系

正确优先级：

```text
P0  webui/** 在真实 qB4/qB5 上正确运行
P1  产品 QBClient / ReleaseProfile / compatibility normalization
P2  产品 feature capability / emulation / graceful unavoidable gap
P3  真实 qB representative / matrix validation
P4  Simulator / source catalog / ledger 辅助验证
P5  Simulator 自身 fidelity
```

禁止反转成：

```text
Simulator fidelity -> 主项目
webui/**            -> 很少修改
```

一个 simulator MISSING 如果 WeiG 产品根本不消费，不应自动成为产品优先级。

## 3. 产品兼容链

目标产品架构：

```text
UI / presentation
      |
      | only canonical WeiG semantics
      v
W.QBClient + product compatibility normalization
      |
      +-> W.ReleaseProfile / exact release facts
      +-> W.CapabilityRegistry / feature availability strategy
      +-> W.SettingsSchema / Preference semantics
      +-> W.TorrentSemantics / qB4-qB5 state/filter normalization
      |
      v
real qB WebAPI
```

UI 不应到处判断：

```text
qB 4.1 / 4.6 / 5.0 / 5.2
WebAPI 2.x
```

版本差异应尽可能截止在产品 compatibility owner。

## 4. 自动适配原则

对每个 WeiG 功能，按以下顺序处理：

### A. 原生等价 API 存在

自动映射 endpoint / 参数 / response。

例如：

```text
WeiG Start -> qB4 resume / qB5 start
WeiG Stop  -> qB4 pause  / qB5 stop
WeiG stopped filter -> qB4 paused / qB5 stopped
```

### B. API 存在但 request/response 形状不同

在 `W.QBClient` 或明确的产品 normalization owner 中归一化，UI 只看到 canonical WeiG object/result。

例如：

```text
editTracker legacy origUrl -> modern url
legacy torrents/add Ok./Fails. -> modern structured result
```

### C. 新版没有单一等价 endpoint，但旧 API 可以可靠组合实现

允许实现兼容 emulation。目标是功能尽可能在稳定 qB4/qB5 上都能实现，不是简单遇到旧版本就隐藏。

要求：

- 结果语义可靠；
- 不伪造不存在的数据；
- 不制造危险的 N -> N 网络放大；
- 明确测试性能与错误语义；
- 一个功能只保留一个产品 Current Owner。

### D. 可以从已有 canonical data 可靠本地推导

允许本地 projection/filter/sort，而不是要求上游必须有同名 endpoint。

### E. 真实 qB 根本不提供所需数据/能力，且无法可靠组合或推导

这才是不可避免的 capability gap。此时：

- 不发送必然失败的 API；
- 不伪造功能；
- 可以隐藏/只读/给出明确 capability 说明；
- 在兼容矩阵中记录无法实现的技术原因。

“隐藏”是最后手段，不是默认兼容策略。

## 5. 截图中 UI 的自动适配要求

以下均属于正式产品兼容范围，不是 simulator 专属功能。

### Torrent 状态筛选

包括：

```text
全部
下载中
做种中
已完成
已停止
运行中
活动
非活动
停滞
上传停滞
下载停滞
校验中
移动中
错误
Private / PT
```

要求：

- UI 使用统一 WeiG semantic id；
- qB4/qB5 upstream filter 名差异由 `W.TorrentSemantics + W.ReleaseProfile` 消化；
- upstream 没有直接 filter 但可从已获取 torrent 数据可靠计算时，本地实现；
- 只有真正不可获得时才隐藏。

### Facets

包括：

```text
Tracker
路径
分类
标签
```

要求：根据当前真实 release 的 endpoints/fields 与 canonical torrent data 自动适配。Tags 等历史上不存在的能力先判断能否可靠兼容；不能时才隐藏对应 facet。

### Columns

包括但不限于：

```text
Name
Size
Progress
Download
Upload
ETA
Status
Ratio
Tracker
以及其它列
```

列系统应消费 canonical Torrent field registry。字段可以是：

```text
native
normalized
locally derived
unavailable
```

前三者在可靠时可显示；`unavailable` 才不提供。Columns UI 不应自己保存 qB patch 版本表。

### Settings

包括：

```text
下载
连接
速度
BitTorrent
Web UI
高级
```

要求：

- exact Preference getter/setter/type provenance 驱动当前 release surface；
- 有 getter+可信 setter/type -> 可编辑；
- getter-only -> 只读；
- 不存在 -> 不显示；
- 如果旧版可以通过等价 Preference/组合语义实现统一 WeiG 设置，应在产品 compatibility owner 做映射；
- section 没有任何有效项目时自动隐藏。

### Search / RSS / Logs

这些是正式产品入口，也必须按真实 release 自动适配。

优先顺序：原生 endpoint -> 可靠兼容实现 -> 本地 projection -> 最后才 capability hide。点击入口后才出现 404/501 不算兼容。

### Torrent actions / Details

还包括：

- Add/Delete/Start/Stop/Force Start/Recheck/Reannounce；
- Files / priorities；
- Trackers / WebSeeds；
- Peers / ban；
- Categories / Tags；
- Metadata / Torrent Creator；
- Transfer/global limits；
- RSS/Search/Logs；
- 所有 `webui/**` 暴露给用户的正式功能。

```text

Phase C  qB4.0.x Legacy WebAPI v1 Adapter       SEPARATE TRACK
```

产品功能矩阵继续使用：

```text

-> qB4 behavior
-> qB5 behavior
-> request differences
-> response differences
-> normalization status
-> emulation possible?
-> unavoidable gap?

```

当前优先顺序：

7. qB4.0.x Legacy WebAPI v1 adapter。

每完成一个大阶段必须先复盘、更新 docs、列出已改/待改文件，再进入下一阶段。

## 7. Ledger 的新用途

现有 WebAPI evolution ledger 继续保留，是重要历史 evidence index，但不再以：

```text
MISSING 50 -> 49 -> 48 ...
```

作为产品主进度。

先把每个 MISSING 与 `webui/**` 使用面关联：

```text
PRODUCT_BLOCKER
PRODUCT_NORMALIZATION
PRODUCT_EMULATION
UNAVOIDABLE_PRODUCT_GAP
SIMULATOR_ONLY / UNUSED_BY_PRODUCT
```

只有前四类进入产品 roadmap；最后一类可以留作低优先级 simulator fidelity。

## 8. Simulator 的正确职责

Virtual qB 的职责：

- 模拟历史 request/response/status；
- 给同一份 `webui/**` 提供多 profile browser acceptance；
- 提前暴露 qB4/qB5 差异；
- 验证产品 compatibility normalization；
- 验证 feature capability presentation；
- 绑定 exact SHA Pages evidence。

它不能：

- 代替修改 `webui/**`；
- 让产品依赖 simulator-only API；
- 证明“真实 qB 一定可用”；
- 因为 simulator 更容易实现就让产品兼容逻辑留空。

如果 simulator 与真实 upstream evidence 冲突，真实 upstream/real-qB 是最终裁决。

## 9. 验证层级

### Level 1 — source/evolution evidence

知道每个 stable release 的真实 surface 与历史差异。

### Level 2 — product compatibility contracts

直接验证 `webui/**` compatibility owner：

```text
qB4 input -> canonical WeiG result
qB5 input -> same canonical WeiG result
```

### Level 3 — Virtual qB browser matrix

同一正式 `webui/**` 在多个 stable profile 上跑真实 Chrome UI flow。

### Level 4 — real qB

用真实 qB4/qB5 binary/server 验证核心用户流程。Promotion 前的 frozen real-qB LIVE 仍是强 gate；Phase E 开发期间也应逐渐增加 representative real-qB compatibility evidence，而不是只等最后一天。

Simulator PASS 永远不能单独等价于 real-qB PASS。

## 10. qB4.0.x

当前 source/evolution 主线从 qB 4.1.0 / WebAPI v2 开始。如果产品目标是“所有 qB4 stable”，qB 4.0.x 必须成为显式 Phase E 子项目：

```text
Legacy WebAPI v1 Adapter
-> canonical product semantics
-> same UI
```

禁止把 v1/v2 分支散落在 presentation、settings、torrent view 等多个 caller 中。

## 11. Definition of Done

最终产品 DoD：

```text
same webui/** package
-> install on supported qB4/qB5 stable
-> auto detect release/API capabilities
-> same WeiG canonical UI/semantics
-> endpoint/parameter/response differences normalized
-> old-version equivalent behavior emulated when reliable
-> unavoidable gaps explicitly documented
-> no manual version selection
-> no simulator dependency in product
-> representative real-qB browser flows green
```

Virtual qB 的 DoD 只是支持以上产品 DoD，不是平行产品。

## 13. Phase B scope — qB4.1+ Product Compatibility Core

Phase B 只解决已经确认、且有 Phase A source facts 支撑的 qB 4.1.0+ WebAPI v2 产品缺口。

### B1. Status filter strategy

```text
native upstream filter
-> reliable local derivation from already-fetched canonical Torrent catalog
-> unavailable only as last resort
```

第一批：

```text
downloading
seeding
completed
stopped
running
active
inactive
stalled
stalledUP
stalledDL
checking
moving
errored
```

Private/PT 必须保持语义严谨：tracker PT heuristic 不能被包装成 authoritative private flag。

### B2. Category / Tags facets

```text
native taxonomy endpoint
-> fallback: distinct values derived from canonical Torrent catalog
```

必须拆开：

```text
read/filter capability
```

和：

```text
create/edit/remove capability
```

旧 qB 即使没有 taxonomy/write endpoint，只要 `torrents/info` 已真实返回 `category` / `tags`，就可以可靠提供读/筛选 facet。

### B3. Torrent Action resolution

```text
WeiG semantic action
-> exact source-derived ReleaseProfile action
-> parameter normalization / reliable emulation
-> unsupported before click
```

第一批必须解决：

```text
Reannounce click-to-404
Remove Tracker click-to-404
```

## 14. Phase B expected file plan

### 主要预计修改

`webui/private/scripts/release-profile.js`

- 把 Phase A 的 Action/parameter/field facts变成正式 runtime query；
- 提供 fail-closed 的 action/feature resolver；
- UI 不自己查版本号。

`webui/private/scripts/torrent-semantics.js`

- 定义哪些 status 可由 canonical Torrent row 可靠推导；
- 提供统一 local status matcher/support metadata。

`webui/private/scripts/capabilities.js`

`webui/private/data/capabilities.json`

- 拆开 native endpoint capability 与 product feature capability；
- Category/Tags read/filter 与 write/list capability 分离。

`webui/private/scripts/app.js`

- 状态筛选从“native only”升级为 native/local-derived；
- Category/Tags taxonomy endpoint 不可用时从现有 catalog 推导；
- Tracker detail 的 remove/edit action 在渲染/点击前精确 gate。

`webui/private/scripts/selection.js`

- bulk/action menu 消费统一 action resolver；
- Reannounce 等不支持 action 不再成为可点击请求。

`webui/private/scripts/qb-client.js`

- 仅在需要 Action 参数 normalization 或统一 transport wrapper 时修改；
- **Phase B 禁止在这里顺手加入 qB4.0 WebAPI v1**。
