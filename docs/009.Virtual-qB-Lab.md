# 009. Virtual qB Lab

> Virtual qB Lab 是 WeiG qB WebUI 的**非产品辅助验证工具**。它模拟 qB WebAPI，帮助同一份正式 `webui/**` 在多历史 profile 下接受浏览器测试；它不替换 `W.QBClient`，不建立第二份产品业务 state，也不定义项目最高目标。

Status: **auxiliary validation infrastructure / Phase E supporting tool**

最高产品目标见 [`010.真实qB产品兼容路线.md`](./010.真实qB产品兼容路线.md)。

## 1. 正确定位

Virtual qB 用来：

- 复现 qB/WebAPI 历史 request/response/status 差异；
- 让同一正式 `webui/**` 在多个 stable profile 上跑真实 Chrome；
- 辅助发现 qB4/qB5 product compatibility gap；
- 验证 `W.QBClient` / ReleaseProfile / Settings / TorrentSemantics 等产品 owner 的 normalization；
- 提供 deterministic Torrent/peer/network/disk world；
- 绑定 exact source SHA 的 Pages evidence。

Virtual qB **不用于**：

- 代替修改 `webui/**`；
- 让产品依赖 simulator-only endpoint/data；
- 把 simulator `MISSING` 数量当产品主进度；
- 声称 simulator PASS 等于所有真实 qB binary PASS。

如果 simulator 与 upstream source/真实 qB 行为冲突，真实 upstream / real qB 是最终裁决。

## 2. Product-first workflow

从 Phase E 起，发现一个历史差异后的顺序改成：

```text
upstream difference
-> webui/** 是否消费？

YES
-> 产品 compatibility 是否已 normalize/emulate？
-> 未完成：优先修改 webui/** product owner
-> 再用 Virtual qB 增加对应历史 profile 验证

NO
-> 记录在 ledger
-> simulator fidelity 可低优先级处理
```

不再默认：

```text
发现 MISSING
-> 先把 simulator 做完整
```

## 3. Current stable evidence scope

当前 WebAPI v2 source-derived matrix：

```text

current tested latest: qB 5.2.3

```

qB 4.0.x / WebAPI v1 当前不在 Virtual qB v2 matrix。若 Phase E 产品实现 Legacy WebAPI v1 Adapter，Virtual qB 可以随后增加相应 v1 fixture/adapter validation，但产品设计先于 simulator 扩展。

## 4. Structural truth

```text
qB upstream official stable source
-> source parsers
-> qb-release-catalog.mjs
-> qb-releases.json
```

回答：

- endpoint 是否存在；
- Preference getter/setter/type；
- Torrent filter surface；
- torrents/info parameter surface。

这些 source facts 同时服务于产品 ReleaseProfile 与 simulator；不是 Virtual Lab 私有 truth。

## 5. Simulator protocol architecture

```text
formal W.QBClient
-> Native Service Worker / transport adapter
-> Transport Contract
-> upstream structural gate
-> protocol router + Endpoint Contract
-> QBSimulatorEngine / Scheduler / Policy / services
-> IndexedDB world
```

### Endpoint Contract

`simulator/protocol/endpoint-contracts.js`：模拟 already-existing endpoint 在不同 WebAPI revision 的 request/response/status/mutation semantics。

### Transport Contract

`simulator/protocol/transport-contract.js`：模拟 Basic Auth、header/proxy 等 transport evolution。

### upstream-gates

只负责 structural endpoint existence。

这三个 owner 都属于 simulator/evidence infrastructure。**它们不是正式产品 `W.QBClient` compatibility implementation。**

## 8. Phase E 中 Virtual qB 应重点验证什么

第一批围绕用户可见产品 surface：

### Torrent filters

同一 WeiG filter 在 qB4/qB5 profile 下得到相同 canonical 语义；如果产品使用本地推导，也要验证 final UI count/result。

### Facets

Tracker/Path/Category/Tag 在 endpoint/field 存在与缺失 profile 下表现符合产品 compatibility strategy。

### Columns

验证 native/normalized/locally-derived/unavailable field policy，不允许 stale column 因 API field 缺失而显示错误数据。

### Settings

验证每个 stable Preference surface 的 getter/setter/type、产品映射、只读/隐藏/等价实现策略。

### Search / RSS / Logs

验证入口 capability 和真实 flow，而不是只检查 DOM 节点存在。

### Torrent actions/details

验证 qB4/qB5 action naming、参数、error/result normalization。

## 9. Pages evidence 的含义

Formal Pages：

```text
source signal
-> exact source checkout
-> generate/audit stable catalog
-> build exact dev/main snapshots
-> deploy
-> Hosted Chrome verify
```

`workflow_run` 的 UI `head_sha=main` 不能作为 source identity。真实 identity 以 triggering source SHA、exact checkout、`WEIGG_PAGES_SOURCE_SHA`、`WEIGG_EXPECTED_SIMULATOR_SHA`、deployed metadata 为准。

Pages green 只证明：

```text
formal webui/** + current simulator profiles + current Chrome
```

它不能冒充真实 qB binary/server evidence。

## 10. Simulator realism boundary

Simulator runtime data可以 synthetic，但必须：

- seeded/deterministic；
- internally consistent；
- response shape/status 与 audited upstream 一致；
- modeled setting 真正影响模拟行为；
- 不为了让产品测试绿伪造真实 qB 不可能提供的数据。

## 11. Future stable

新的 official stable：

```text
source catalog discover
-> product compatibility impact check
-> evolution evidence
-> product implementation if affected
-> simulator profile/contract update as needed
```

顺序里“product impact check”必须在 simulator fidelity 扩展之前。

## 12. Current DoD

Virtual qB 的完成标准不是“完整重写 qB daemon”。它只需要足够准确地支持产品验证：

```text
product-consumed historical semantics accurate
multi-profile browser flows deterministic
differences expose product compatibility bugs
no product simulator dependency
exact-SHA evidence traceable
```

最终项目 DoD 仍由 010 定义：同一 `webui/**` 在真实 qB4/qB5 stable 上自动适配并尽可能保持完整功能。
