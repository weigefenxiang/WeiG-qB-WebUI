# WeiG Virtual qB Lab

> 状态：方案已确认，先文档化，再分阶段实施。
>
> 目标：在 **不修改 `webui/**` 产品源码** 的前提下，为 GitHub Pages 提供一个尽可能接近真实 qBittorrent 的浏览器内虚拟服务端，使原始 WeiG WebUI 通过原始 `W.QBClient` 直接连接并操作它。

---

## 1. 项目定位

WeiG Virtual qB Lab 不是截图 Demo，也不是一组固定 JSON fixture，而是一台运行在浏览器中的 **Virtual qBittorrent daemon**。

核心关系：

```text
Real deployment:
WeiG WebUI -> W.QBClient -> qBittorrent WebAPI

Virtual Lab:
WeiG WebUI -> W.QBClient -> Native Service Worker -> QBSimulatorEngine -> IndexedDB
```

必须保持：

- `webui/**` 是真实产品源码，Virtual Lab 不在其中加入 simulator 分支、mock 开关、fetch monkey patch、MutationObserver 或第二 QBClient。
- Virtual Lab 位于产品 HTTP 边界之下，模拟 qBittorrent，而不是修改 WeiG WebUI 来“配合演示”。
- Clean Validation Mode 中，WebUI 必须保持与分支 `webui/**` 字节级来源一致；Lab 控件不能污染产品截图或语义 UI gate。
- Virtual Lab 的目标是高保真可交互体验与兼容验证，不产生真实 BitTorrent 下载、上传、Tracker、Proxy、VPN 或文件系统副作用。

---

## 2. 技术栈

首选且固定的基础方案：

- Native Service Worker：接管 Pages scope 下的 `api/v2/*` 请求。
- IndexedDB：持久化 Virtual qB 的 Session、Preferences、Torrent、Peers、Tracker、日志、RSS、搜索任务与同步日志。
- 原生 ES Modules：避免为了模拟层引入不必要的 runtime 框架。
- Seeded deterministic RNG：所有随机世界均可重现。
- Request-driven Virtual Clock：Service Worker 可随时被浏览器回收，因此禁止依赖永久 `setInterval` 维护世界。
- GitHub Pages：同一 Pages artifact 可承载 dev/main 的 exact WebUI snapshot 与 Virtual Lab runtime。

Service Worker 只是 transport adapter，不拥有业务状态。Virtual qB 世界的唯一 Current Owner 是 `QBSimulatorEngine`。

### 4.1 Virtual Lab coverage


稳定版筛选规则必须 fail closed：

```regex
^release-(4|5)\.\d+\.\d+(\.\d+)?$
```

明确排除：

- alpha
- beta
- rc
- nightly
- master
- synthetic

### 4.2 产品支持范围与 Lab 范围分离

Virtual Lab 可以模拟早于 WeiG 正式兼容 floor 的版本，但不得因此宣称产品正式支持。

```text

```

选择低于正式 floor 的版本时，Lab UI 必须显示明确的 Lab/unsupported 提示。

## 5. Upstream Truth 与自动版本发现

版本事实不随机生成，也不手工维护几十份 profile。

唯一 owner：`QBStableReleaseCatalog`。

构建/维护流程：

```text
qbittorrent/qBittorrent official tags/releases
  -> filter stable numeric releases
  -> read exact release tag source
  -> extract qB version
  -> extract WebAPI API_VERSION
  -> extract preference keys
  -> extract API controller actions
  -> generate version/profile manifest
```

每个 profile 至少记录：

```json
{
  "qbVersion": "5.2.3",
  "webApiVersion": "2.15.1",
  "tag": "release-5.2.3",
  "tagSha": "...",
  "stable": true,
  "protocolGeneration": "qb5"
}
```

现有 upstream release audit 与 Simulator 必须复用同一个 stable-release truth，不允许再出现第二套版本判定逻辑。

## 6. 每周自动发现新稳定版

当 Pages workflow 获得最终确认后，计划加入每周定时检查。

目标行为：

```text
每周 Actions
  -> 拉取 qB upstream stable releases/tags
  -> 若出现 5.2.4 / 5.3.0 / 5.3.1 / 未来 5.x.x
  -> 自动生成新的 Virtual qB profile
  -> 自动提取 WebAPI / Preferences / API actions
  -> 重建 Pages artifact
  -> 新版本自动出现在 Virtual Lab 版本选择器
```

重要约束：

- 每周更新默认 **不自动 commit dev/main**。
- 不因为上游新版本自动修改 `webui/**`。
- 不因为上游新版本自动 bump 产品 VERSION。
- 若上游出现无法安全解析的新 API 形态，workflow 必须 fail closed 并给出报告，而不是猜测。
- workflow、Pages source 与 Actions 设置属于独立阶段，实施到该阶段前必须再次由项目所有者确认。

## 7. 新版本 Settings 的自动发现策略

新稳定版可能新增 Preferences。Virtual Lab 与正式 WeiG Settings 必须分层处理。

### 7.1 Simulator

上游新 Preference 可以自动进入 version manifest，并由 Virtual qB 的 `app/preferences` 返回。

每个设置具有 simulation coverage：

```text
MODELED    = 读写且真正影响 Virtual qB 行为
STATEFUL   = 可保存/读取，但暂未模拟现实副作用
READ_ONLY  = 仅安全展示
UNKNOWN    = 未识别，禁止猜测语义
```

### 7.2 WeiG WebUI Settings

不允许 Actions 自动猜测：

- label
- unit
- min/max
- enum 含义
- section
- 复杂交互

如果现有 SettingsSchema 能通过安全 fallback 展示未知 scalar，则可以先进入 Advanced/Upstream 等安全区域；复杂结构或语义未知的设置应只读或 fail closed。

真正完善新设置的名称、单位、枚举、帮助文本和行为，应作为后续正式 `webui/**` 产品改动处理，并按产品 VERSION 规则升级版本。

## 8. Virtual Lab 登录 / 退出

公开 Demo 要保留真实的登录与退出流程，而不是跳过认证。

### 8.1 登录体验

Virtual qB 的 Demo 认证策略：

- 登录页面可以预填一组公开 Demo 凭据，例如 `demo / demo`，用户打开后只需点击“登录”。
- 用户也可以自行输入任意非空用户名和密码；Virtual qB 一律接受并创建 Session。
- Demo 凭据不代表真实 qBittorrent 默认账号或真实安全配置，只是 Virtual Lab 的体验入口。
- Clean Validation Mode 仍保持分支原始登录页面与原始产品代码，不为了 Demo 便利修改 `webui/**`。

### 8.2 Session 行为

成功登录：

```text
POST /api/v2/auth/login
  -> Ok./版本对应成功响应
  -> Virtual SID/session active
  -> private WebUI APIs 可访问
```

退出：

```text
POST /api/v2/auth/logout
  -> session invalid
  -> 后续 app/preferences 等 private API 返回 403
  -> 原始 WeiG SessionController 验证退出
  -> 返回登录页
```

默认不启用 auth bypass。后续测试场景可单独模拟 bypass/ban/403 等边界，但公开 Demo 保持简单、可进入、可退出。

## 10. 默认 5000 Torrent 世界

默认建议：

```text
count = 5000
scenario = mixed
seed = 固定可重现值
```

不是 5000 个任务全部高速运行，而是接近真实长期运行的 qB：

- 大量 completed/seeding/stalledUP
- 少量 active downloading
- 一部分 queuedDL/queuedUP
- 一部分 paused/stopped
- 少量 checking/metadata/error/missing files
- 活跃数量严格受 Settings、资源与 swarm 条件约束

状态覆盖采用 quota + seeded random，既保证 UI 能看到重要状态，又能保证同一 seed 完全复现。

## 11. 真实感来源：资源约束模型

速度不能是无约束随机数。

每个 Torrent 的最终有效下载速度由多个资源共同约束：

```text
effective download rate = min(
  swarm potential,
  per-torrent download limit,
  global allocated budget,
  alternate-speed budget,
  peer/connection capacity,
  disk write allocation,
  queue/policy eligibility
)
```

上传同理。

需要模拟的资源至少包括：

- Virtual Network
- Virtual Disk
- Virtual Swarm/Peers
- Virtual Tracker
- Queue Scheduler
- Policy Engine
- Connection/Upload Slot budget

速度变化应平滑、有惯性、有小幅波动，而不是每秒独立 `Math.random()` 跳变。

## 12. Settings 必须真正影响世界

所有 Virtual qB 中“保存成功”的重要设置必须有可观察副作用；不能只返回 200/Ok。

至少完整模拟：

| 设置/限制 | Virtual qB 行为 |
|---|---|
| Global Download Limit | 所有下载总速度受全局预算限制 |
| Global Upload Limit | 所有上传总速度受全局预算限制 |
| Alternate Speed | 切换后立即使用备用上下行预算 |
| Per Torrent DL/UL | 单 Torrent 独立封顶 |
| Maximum Active Downloads | 超出任务进入下载队列 |
| Maximum Active Uploads | 超出任务进入上传/做种队列 |
| Maximum Active Torrents | 总 active slot 受限 |
| Queueing | 决定是否按 active slots 调度 |
| Force Start | 可绕过普通 queue eligibility |
| Global Connections | 限制总 Peer connection 数 |
| Connections per Torrent | 限制单 Torrent Peer 数 |
| Upload Slots | 限制活跃上传 Peer |
| Ratio Limit | 达标后执行对应停止/暂停策略 |
| Seeding Time | 达标后执行对应停止策略 |
| DHT / PeX / LSD | 改变 Peer discovery 来源和供应 |
| Disk Free Space | 空间不足可触发错误/停滞 |
| Temp/Save Path | 改变 Virtual filesystem path 状态 |

Settings、Torrent rows、`transfer/info` 与 `sync/maindata.server_state` 必须来自同一 Scheduler snapshot。

## 13. Scheduler 与活动数量

例如用户设置：

```text
max_active_downloads = 5
max_active_uploads = 20
max_active_torrents = 25
```

即使共有 5000 Torrent，Scheduler 也只允许符合条件的有限任务 active，其余为 queued/paused/stalled/idle。

暂停一个 active download 后，下一 eligible queued download 应自动补位。

Force Start 作为明确的调度例外处理，而不是另一套 owner。

---

## 14. Seeds / Peers / Tracker / Rate 必须互相解释

禁止产生明显矛盾数据，例如：

```text
Seeds = 0
Peers = 0
Download speed = 60 MiB/s
```

基本关系：

- 无可用 peer/seed -> 下载可进入 stalled。
- 有 seed 与可用 peer -> 才能形成下载供应。
- 无 interested leecher -> 做种可以 stalledUP/idle。
- Tracker/DHT/PeX/LSD 状态影响 Peer 来源。
- Connection limits 影响可连接 Peer 数。
- Upload slots 影响同时有效上传的 Peer 数。

---

## 15. Progress / ETA / Uploaded / Ratio 必须闭环

Torrent progress 按真实有效速度和 Virtual Clock 推进：

```text
progress += effective_download_rate * elapsed
```

ETA 来自剩余数据和当前有效速度；速度变化后 ETA 随之变化。

达到 100% 后，Torrent 自然从下载态进入完成/做种态。

上传量随有效上传速度累积：

```text
ratio = uploaded / size
```

Ratio limit 与 Seeding time 达标后，由 Policy Engine 自动执行停止策略。

## 18. Virtual Clock

Service Worker 生命周期不可靠，因此不使用永久 timer 作为世界 truth。

每个 Session 持久化：

```text
lastVirtualTimestamp
rngState
worldRevision
```

每次 API 请求时：

```text
elapsed = now - lastVirtualTimestamp
-> advance environment
-> evaluate policy
-> allocate rate
-> update progress/upload/ratio
-> transition state
-> generate sync journal
-> persist changed entities
-> return response
```

浏览器休眠或 Service Worker 被回收后仍能继续一致地推进世界。

## 22. `sync/maindata` 与 5000 Torrent 性能

首次：

```text
rid = 0
-> full_update = true
-> 返回完整世界
```

后续：

```text
rid = N
-> full_update = false
-> 只返回 changed/removed torrents 与 server_state delta
```

禁止每个 poll 都重新发送/重写 5000 条 Torrent。

实现应使用 hash/state/category/tag 索引、批量 IndexedDB transaction 与 bounded mutation。

## 29. Definition of Done

Virtual qB Lab 的最终硬性验收包括：

- `webui/**` 为 0 个 Simulator 产品侵入改动。
- Virtual Lab 从 qB 4.1.0 自动覆盖到未来最新官方稳定 5.x。
- alpha/beta/rc/master 不进入普通版本选择器。
- 每个版本 profile 有真实 WebAPI mapping 与 upstream tag provenance。
- 默认可稳定承载 5000 Torrent。
- same seed + same profile = same initial world。
- Login 可直接使用预填 Demo 凭据，也允许任意用户自定义凭据登录。
- Logout 使 private API 真正返回 403，原始 WeiG SessionController 能完成退出闭环。
- Global/per-torrent limit 真正约束速度。
- Active download/upload/torrent limits 真正约束 Scheduler。
- Queue、Force Start、Ratio、Seeding Time、Alternate Speed 真正执行。
- Seeds/Peers/Tracker/Connections/Rate 数据互相合理。
- Progress、ETA、Uploaded、Ratio、状态转换形成一致闭环。
- Network/Disk/Swarm/Settings 共同决定实际 throughput。
- `transfer/info`、Torrent rows、`sync/maindata.server_state` 来自同一 truth snapshot。
- Add/Delete/Rename/Pause/Start 等操作刷新后仍持久化。
- 多个 Virtual Session 可同时模拟不同 qB 版本。
- 未实现 API fail closed。
- Clean Mode 无 Simulator DOM 污染。
- Pages weekly update 不自动修改产品源码或产品版本。

## 30. 核心原则

Virtual Lab 不应该“配合 WeiG WebUI 演戏”。

正确目标是：

> **模拟一个足够接近真实 qBittorrent 的后端，让同一份 WeiG WebUI 自己去适配它。**

这样该项目同时可以承担三种价值：

1. 公开可交互 Demo，让不了解 qBittorrent 的用户无需安装即可体验其 WebUI、队列、限速、做种、Peers、Tracker 与 Settings。
2. 高保真回归环境，用于验证 WeiG WebUI 在不同 qB/WebAPI 版本下的行为。
3. Upstream 变化探测器，在 qB 新稳定版发布后自动发现版本、Preference 与 API surface 变化，为后续正式兼容工作提供证据。
