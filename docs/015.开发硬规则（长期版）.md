# 015. WeiG-qB-WebUI 开发硬规则（长期版）
Status: **long-term engineering invariants / AI operating constraints**
总原则：`webui/** is the product`；qB 4.1.0+ compatibility first；exact-SHA/source truth first；Single Current Owner；canonical reuse；Source/Product/Simulator separation；fine-grained provenance；Frozen LKG protected；bounded inheritance；future UNKNOWN fail closed；no fake data；real-qB evidence；Light/Dark semantic parity；build once / validate once / promote same bytes。任何旧 prompt、旧实现、旧 test、旧 docs、旧 Simulator expectation 与当前 exact-SHA canonical contract 冲突时，禁止为了兼容旧内容把现行产品方向改回旧状态。
总目标：`webui/**` 是唯一正式产品；正式支持 floor 固定为 qBittorrent 4.1.0。同一份 WeiG WebUI 应尽可能直接运行于 qB 4.1.0 起全部 admitted official stable、当前 stable 及未来 stable/new major，并基于真实 qB release、WebAPI 与 upstream source facts 自动适配 endpoint、parameter、response、state/filter、Preference 与 UI surface，不要求用户选择 compatibility mode。低于 qB 4.1.0 默认不属于正式 compatibility matrix；未来若用户明确扩大 scope，只允许通过集中 Legacy Adapter -> canonical WeiG semantics 接入，禁止把 v1/v2 判断散落到 UI 或业务 caller。Virtual qB、source catalog、evolution ledger、Endpoint/Transport Contract、browser fixture、GitHub Pages 都只是发现、模拟、验证与发布设施，不得反客为主。
Authority：本文只保存长期 invariant、安全边界、ownership、evidence identity 与 acceptance 原则，不是第二套 roadmap。产品目标与长期计划以 `docs/001.项目总方案.md` + `docs/010.真实qB产品兼容路线.md` 为最高计划 authority；当前兼容事实以 `docs/002.兼容与实现状态.md` 为准；Current Owner、UI/UX、design system 以 `DESIGN.md` 为准；模块架构以 `docs/003.项目架构.md` 为准；发布/CI/验证规则以 `docs/006.发布与晋级流程.md` 为准；安装部署以 `docs/007.安装升级与手动部署.md` 为准；Torrent ownership 以 canonical Torrent 文档为准。当前 stable 数量、某次 SHA/run、并发数、迁移/watch/drain 状态等 operational facts 不得被提升为长期硬规则。扩大 scope、改变正式架构、promotion、tag、Release 或出现新的重大 contract 冲突时必须请求用户确认。
[P0-1] 分支纪律：正式开发默认只使用 `dev`；`main` 是稳定晋级结果，不是第二开发分支。产品、installer、workflow、test、fixture、docs、CI 修复都先进入 dev；未经用户明确授权禁止直接修改 main、promotion、tag、GitHub Release 或任何会改变正式发布身份的操作；禁止 force push。main 只能从已经完成正式门禁的 final dev exact SHA safe fast-forward，显式 `force:false`。即使 `main == dev`，下一次修改仍从 dev 开始。canonical long-lived branches 只允许 `main` 与 `dev`；remote temporary branch 只有在已确认存在可靠删除路径时才能创建，必须 bounded、短期存在且用途结束后立即删除。
[P0-2] SAFE-REF：每轮正式写入前必须 fresh-read 当前 `dev` exact HEAD，并以它作为本批次唯一起点。构建、验证、candidate、artifact、Pages 或 ref 更新前后均检查 exact SHA；更新 ref 前再次 fresh-read dev 做 race check。若 dev 已移动，尚未提交的 tree/ref update 必须停止并基于新 HEAD 重建。多文件 coherent write 优先单一 tree/commit；若受工具限制顺序写入，后续每一步必须严格接前一步新 SHA，最终做完整 diff 与 race check。
[P0-3] Repo-wide proof：ownership、absence、uniqueness、identity、proof 必须基于目标 exact SHA 的完整 relevant tree/blob/file 内容；code search、snippet、grep 只用于 discovery，不能作为“全仓不存在”“唯一 owner”“没有其它 caller”的最终证明。旧 SHA、截断结果、缓存、局部片段、推测不能作为 final proof。涉及 Git blob/hash identity 必须使用 canonical Git object/index identity 与 canonical blob bytes，不依赖可能受 CRLF/LF 转换影响的 working-tree bytes。
[P0-4] 历史与提交：提交历史必须最小、coherent、可审计。允许必要 fix/candidate commit，但失败探索、临时 debug、无意义 patch、一次性 scaffolding 不应长期进入正式 dev 历史。Commit message 使用英文。candidate freeze 之前，为整理试验历史，可以把批准后的真实变更通过 coherent reconstructed commit/squash/cherry-pick 落入 dev；一旦形成 final dev exact SHA，promotion 到 main 禁止 cherry-pick、merge rebuild 或重新构造对象，只允许 validated dev SHA 的 safe fast-forward。
[P0-5] VERSION 与 immutable Release：Exact Git SHA 是 code/cache/test/CI/Pages/candidate/artifact/promotion/Release evidence 的真实身份。当前 Product `VERSION` 只在正式 `webui/**` 产品内容变化时递增；docs/tests/CI/workflow/fixture/tooling/simulator-only 变化本身不 bump Product VERSION。已发布 `vX.Y.Z` tag/Release/asset 是 immutable historical identity，禁止移动、覆盖、复用或删除后重打。若非 `webui/**` 的正式 installer/packaging 变更会改变用户可下载的 Release bytes，则不得覆盖既有同版本 Release；在当前单一 Product VERSION 架构下必须等待/形成新的 product version，或先经用户确认引入独立 Release identity，不能偷用旧 tag。
[P0-6] Single Current Owner + atomic cutover：一个 semantic purpose 只能有一个 Current Owner；planned/dormant/test-only implementation 可存在但不得形成第二 active runtime owner。修改 public API、event、shared component/token/state、version source、capability boundary 或其它跨模块公共契约前，必须对 target exact SHA 做 repo-wide impact audit。正式切换必须同一 coherent change 完成新 owner 生效、caller 切换、superseded owner/helper/state/event/polling/compat path 退休、tests 更新，并在 Current Owner/public contract 真正改变时同步 `DESIGN.md`。禁止 old/new 双 active、hidden DOM bridge、第二 polling/state owner、MutationObserver repair、monkey patch、post-render repair、版本化 runtime duplicate 与长期 fallback bridge。
[P0-7] Canonical UI + Light/Dark semantic parity：UI 必须优先复用 `DESIGN.md` 定义的 canonical Select、Dialog、Button、Input、Card、Theme、Feedback、state/controller 与共享 owner，禁止 feature-local 重造轮子。Desktop/Mobile 共享同一 semantic state/component/Current Owner，只允许 responsive presentation 差异。Light/Dark 是同一 semantic UI 的两种 presentation，不要求像素或色值相同，但 text/background/border/hover/active/selected/focus/focus-visible/disabled/read-only/loading/warning/error/success/overlay/dialog/selection/progress 等状态必须具有相同语义、层级与可辨识性；禁止 feature-local hardcoded theme color，禁止只为单张截图或单一主题堆补丁。新增或修改可见 UI 至少验证 affected surface 的 Light + Dark；涉及 shared token/component/theme owner 时验证代表性跨页面 surface。System/Light/Dark 切换只能改变 presentation，不得重置业务 state、selection、route、draft、qB Preference 或其它 canonical state。Reduced Motion 只关闭非必要装饰运动，不得破坏业务语义、真实 progress、loading/error/focus feedback 或最终 visible state。
[P0-8] Source/Product/Simulator 三层边界：Source Truth 属于 `tools/** + generated catalog + evolution ledger`；Formal Product Compatibility 属于 `webui/**` 中明确的 canonical product owners；Virtual qB Simulation 属于 `simulator/**`、Endpoint Contract、Transport Contract 与 Virtual qB services。Simulator/Pages PASS 永远不能单独替代 formal product matrix 或 real-qB evidence。
[P0-9] ReleaseProfile resolution：compatibility 解析必须区分 `EXACT -> EQUIVALENT -> bounded INHERITED -> FALLBACK`。EXACT 是 exact admitted profile；EQUIVALENT 只用于 source/API identity 可证明等价的 canonical version/suffix；INHERITED 只允许在明确边界内临时复用已 admitted 的较低 profile，默认不跨 major.minor，不跨 source-proven hard boundary，且 runtime/API relation 不比 base 更旧；禁止 blind nearest-version-wins、仅因版本号更高就继承 current latest semantics。Inheritance 只能复用 base 已证明的事实，不能为新版本凭空证明新增 endpoint、parameter、field、Preference 或危险 write。FALLBACK 不得伪装成 source-proven support；future UNKNOWN 对无法证明的具体 capability fail closed。
[P0-10] Fine-grained provenance + reliable derivation/no fake data：禁止用单一 true/false 表示整个 feature；至少按 route availability、read、write、action、required/optional parameter、response-field、Preference getter/setter/type 等真实 source/API evidence 独立判断。可靠 normalization、old-API composition、DERIVED 或 canonical product mapping 可用于兼容，但必须语义可靠、错误语义明确、性能有界、不默认制造 `N items -> N requests`、不新增高成本 compatibility polling、不让 presentation caller 自行 probe、不产生第二业务 state/owner。禁止把 unsupported、UNKNOWN、HTTP/load/runtime failure 偷换为 fake empty data；必须区分 `UNAVAILABLE/UNKNOWN`、真实空数据 `[]` 与真实 error。
[P0-11] Settings dangerous write：Settings compatibility 的唯一安全写条件固定为 `setPreferences endpoint proven writable AND specific Preference proven writable`；需要读取/展示时还必须有对应 getter/read provenance。getter + trustworthy setter/type -> editable；getter-only -> read-only；可靠 historical equivalent/composition -> canonical product mapping；完全不存在或 UNKNOWN -> hide/read-only。future UNKNOWN write 必须在 HTTP 前 fail closed。Presentation 不得维护 patch-specific Preference 表，section 无有效项时自动隐藏。
[P0-12] Torrent/filter/field compatibility：historical/current/future upstream differences 应由 `W.ReleaseProfile + W.TorrentSemantics + W.TorrentFieldRegistry + canonical product normalization` 消化。Field modes 至少区分 `NATIVE / NORMALIZED / DERIVED / UNAVAILABLE`，必要时增加 `READ_ONLY / UNKNOWN`；可靠的 NATIVE/NORMALIZED/DERIVED 均可展示。必须保持 `saved preference != effective availability`：field 暂时 UNAVAILABLE/UNKNOWN 时 normal UI 可隐藏，但不得破坏性删除 saved Desktop column order/width、Mobile field preference；未来 exact provenance 恢复时原配置自动生效。Field presence 不等于 server-side sort semantics 已证明，Sort provenance 必须独立确认。Torrent filter ownership 的 canonical contract anchor 必须长期保留。
[P0-13] Frozen LKG + new stable admission + hash-bound auxiliary facts：已验证 stable profile 默认视为 Frozen Historical Facts / LKG；expected set 由 target exact-SHA 的 canonical frozen manifest/catalog 定义，不在长期硬规则写死数量。新 official stable 必须增量 admission：verify Frozen LKG -> lightweight official stable discovery -> 只提取新增 stable facts -> 与上一 admitted stable diff -> focused product/admission gate -> PASS 后 append。parser/API/response/write/product owner semantics 无法证明时必须 `PENDING_REVIEW` / fail closed，candidate rejected、LKG unchanged；INHERITED 只能作为 exact admission 前有界兼容，不能替代正式 admission。Locale overlay、translation facts 或其它辅助 source facts 必须至少绑定 exact `qbVersion + sourceSha` 并验证与 Frozen profile 身份一致；辅助 facts 只能增强 exact profile，禁止因此重写 Frozen Historical Facts。普通 Pages 不得每次重新 clone/re-parse 全历史 upstream。
[P0-14] Locale/i18n owner：`qB preferences.locale` 是唯一持久语言 owner，`W.I18n` 只负责 presentation；禁止恢复独立 `weigg-language` 持久状态、双向 Locale bridge、重复 `setPreferences()` 或 Desktop/Mobile 双语言 state。WeiG Language 与 qB Locale 必须共享同一 value/options/draft/save/verified-reread flow。qB-owned Settings/UI 文案必须来自对应 exact qB release 的官方 source/context/translation facts，禁止把较新 release 文案硬套历史 release。browser/OS locale 只能是环境输入，不能覆盖 persisted truth；测试断言界面语言必须绑定实际 applied application locale，不能由 Playwright/browser locale 推断。
[P0-15] Windows/qB config safety：任何 installer/tool 对 `qBittorrent.ini` 或其它用户 qB config 的外部修改都必须 fail closed。必须保留原编码、BOM、换行与所有无关 Unicode 内容；禁止可能在 Windows PowerShell 5.1 下把 UTF-8 no-BOM 隐式按 ANSI/GBK 解码后再整文件重写的路径。安全写流程必须等价于 `read original bytes -> validate/strict decode -> safety backup -> in-memory minimal mutation -> sibling temp write -> strict reread -> validate encoding/size/target mutation/invariants -> atomic/equivalently safe replace -> failure rollback`。若检测 qB 正在运行、非空 recovery/new file、正式 config 为 0 bytes/异常小/无法安全解析、encoding round-trip 不可靠、目标 config/profile 存在歧义或验证失败，则禁止写入。不得对未知 mojibake 做盲目逆转码。
[P0-16] Dev/runtime distribution identity：任何可实际运行的 Dev/preview 安装物必须来自 target exact-SHA 的 materialized artifact，并验证 embedded `GIT_SHA`/build identity 与目标 SHA 一致。禁止把 raw GitHub source archive 当成 materialized runtime；禁止下载失败后静默 fallback 到另一 SHA、旧 artifact、raw source 或未证明内容。安装/升级成功必须包含“最终运行内容身份可证明”，不能只看 VERSION 相同。
[P0-17] Bounded runtime resources + explicit load failures：runtime generated-data/resource 模型必须适配真实 qB Alternative WebUI 静态服务器，而不是只适配 Pages/普通静态服务器。随历史增长的大型 release/profile/translation 数据必须按 active runtime need 分片、索引、按需加载或采用其它有界方案；禁止恢复已知可能越过真实 qB 静态资源边界的巨大 monolithic runtime catalog。Pages/browser fixture 能加载不能单独证明真实 qB 可加载；涉及 size、namespace、MIME/cache/path 等真实 hosting 行为时必须有 real-qB evidence。HTTP/load/parse/runtime/resource failure 必须保持 failure identity并显式可诊断，不能静默变成 empty catalog、fake `[]`、FALLBACK、UNAVAILABLE 或其它正常业务状态。
[P0-18] Generated artifacts are reproducible, not hand-edited authority：generated catalog/profile/translation/index/manifest/build metadata 必须能由 target exact SHA 的 canonical source/tooling 可重复生成并携带必要 provenance。禁止直接手工改 generated output 来绕过 generator/source truth；若 generated file 需要入库，generator/source/output contract 必须同步验证，generated output 与其 source identity 不一致时 fail closed。
[P0-19] Persistent user state migration：localStorage/IndexedDB/config/preferences 等持久 state 必须有唯一 canonical owner。schema/shape 改变时使用 bounded、可验证、幂等 migration；未知/损坏旧 state fail safe，不得静默整体清空用户设置，也不得把 temporary capability/resource unavailability 当成用户删除。saved preference 与 effective availability 必须保持分离。
[P0-20] Security / secrets / least privilege / external network：源码、commit、artifact、Pages、CI log、fixture、screenshot、debug output 中禁止提交或泄漏真实 token、password、cookie、session、private key、user config secret；测试使用显式 synthetic credentials。发现疑似 secret 时停止传播并按 secret incident 处理，不能认为后续 commit 删除文本就等于历史泄漏消失。GitHub Actions workflow/job permissions 必须 least privilege，普通 build/test 默认 read-only，只给需要外部写入的最小 job 必要权限。第三方 action、downloaded executable、remote script 必须有可审计版本/来源，禁止无边界 `curl|shell` 或依赖可变 latest 内容完成正式 release identity。正式 WebUI runtime 禁止新增未声明 telemetry、analytics、tracking、remote config、动态第三方 script 或后台 external request；如确有产品需求，必须作为 architecture/security change 经用户确认。用户主动点击外部链接与后台 runtime request 必须区分。
[P0-21] Workflow architecture：GitHub Actions canonical workflow set 与职责由 `docs/006` 定义；新增、删除、重命名或改变职责属于显式架构变更，不得因旧 prompt/test/docs 恢复 retired workflow。任何 workflow 变更必须联动检查 `.github/workflows/**`、`tests/**`、`docs/**`、package scripts 与 workflow-to-workflow references，并核对 file path/name/trigger/permissions/concurrency/environment。temporary compatibility/deployment bridge 必须有唯一 owner 与明确 retirement condition，不得成为第二 active path；退休依据 current exact-SHA evidence，不依据旧阶段描述。
[P0-22] Risk-tier CI + root-cause-first：普通 dev push 默认低成本 smoke；涉及 UI/browser/shared component/theme 时运行相应 UI validation；正式 candidate 才运行完整 candidate validation；全历史 real-qB heavy matrix 不得被普通 docs/tests/tooling-neutral maintenance 自动触发。CI 红灯必须先读完整日志并按 root cause 分类修正，优先级固定为 `upstream/source/canonical runtime truth > stale test/fixture/docs/Simulator expectation`。禁止删关键 assertion、扩大 skip、吞错误、放松 exact-SHA/source provenance、恢复旧 owner 或用 patch-version hack 只为绿灯；只有明确瞬时 infrastructure/CDN/runner 问题才考虑 same-SHA rerun。
[P0-23] Real qB Full Frozen Matrix：G-FM 是显式触发的正式验证设施，不用于普通小改动。expected versions 必须从 target exact-SHA canonical Frozen LKG manifest/catalog 派生；每个 admitted stable 独立执行，aggregate 必须证明 expected=executed、`FAIL=0`、`BLOCKED=0`、无 missing/duplicate/unexpected。每个版本绑定同一 exact WeiG SHA，并验证 requested qB、runtime self-reported qB、ReleaseProfile 与 runtime image/source-build identity。旧 SHA 的 G-FM 永远不能证明新 SHA；并发度等纯 operational 参数由 `docs/006` 维护。
[P0-24] Exact-SHA evidence chain：先完成全部计划修改并 freeze final dev exact SHA；随后 candidate、applicable G-FM、dev Pages 等 required evidence 可以按 workflow 允许并行建立，不要求人为串行，但 promotion 必须等待同一 exact SHA 的全部适用 evidence 成功。任一步之后若产生新 commit，新的 exact SHA 必须重新满足全部适用 evidence，禁止先跑 candidate/G-FM/Pages 再补 commit 后继续复用旧证据。Candidate 必须针对 final dev exact SHA，并至少证明适用 smoke、source catalog/audit、formal product matrix、Linux/Windows browser、release package、candidate deployment/real-qB rehearsal；关键 artifact 绑定 exact SHA，并验证 checksum、VERSION、candidate SHA 与 package embedded identity。
[P0-25] Virtual qB Pages exact artifact：Pages 必须以 exact-SHA artifact 为核心身份：目标 dev SHA -> exact-source build/materialization -> exact-SHA Pages artifact -> fresh-head gate -> deploy -> live verify。promotion 后 main 只能复用同一已验证 exact dev Pages artifact，不得重新 full-build 另一份。Pages identity 必须由 workflow target ref、checkout SHA、source SHA metadata、artifact name、site/build metadata、live verify 与 deployment identity 等多证据一致证明，不能只看 Actions UI 顶层 branch/SHA。dev runtime evidence 与 production deployment 必须有隔离的 environment/concurrency 语义，旧 deployment generation 不得覆盖 newer SHA。
[P0-26] Promotion + Release exact-SHA gate：Promotion 前必须证明 `current dev HEAD == validated candidate SHA == applicable G-FM SHA == candidate artifact identity == candidate deployment identity == validated dev Pages SHA`，且 main 是 candidate SHA 的 ancestor，只允许 safe fast-forward `force:false`；禁止 force push、merge commit、promotion-stage cherry-pick/rebuild 或 main-only 产品修改。Release 坚持 `build once / validate once / promote same bytes`：final dev candidate SHA、validated evidence、final main SHA、tag SHA、release package embedded `GIT_SHA` 必须一致；Release workflow 复用已验证 candidate artifact，不得在 main/tag 后重建另一份 package。Release 前再次 fail closed 校验 checksum、VERSION、generated catalog、candidate SHA 与 package identity。
[P1-27] Docs/tests/fixture/Simulator authority：这些设施都必须服务当前 canonical product contract，不能反向定义产品事实。Primary docs 只记录长期 current architecture、compatibility contracts、validation rules 与 SOP，不做流水账或第二 roadmap；bounded 专项设计、source audit、事故复盘、验证说明可以保存事实与教训，但不得覆盖更高 authority、成为第二 Current Owner 或第二 roadmap。测试失败先判断产品违反 current contract 还是 expectation stale；只有前者才修改产品。禁止通过删除 assertion、扩大 skip、吞错误、伪造空数据、降低 exact-SHA/source provenance、隐藏 runtime failure 或恢复旧 owner 制造绿灯。
[P1-28] Hard-rule scope：本文不写死 current stable count/latest version、matrix 并发数、runner/browser 当前版本、某次 SHA/run id、当前 workflow 数量、temporary migration/watch/drain 状态或某个阶段 checkpoint；这些属于对应 authority docs/current evidence。长期规则只保留 invariant、安全边界、ownership、provenance、evidence identity、fail-closed 与 acceptance 原则。凡旧 prompt、旧实现、旧 test、旧 docs、旧 Simulator expectation 与当前 authority 冲突，应先确认 current upstream/source/runtime truth；只有扩大 scope、改变正式架构、promotion、tag、Release 或重大 contract 冲突才请求用户确认。
