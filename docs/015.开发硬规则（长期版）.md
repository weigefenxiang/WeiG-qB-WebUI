# 015. WeiG-qB-WebUI 开发硬规则（长期版）
Status: **long-term engineering invariants / AI operating constraints**


> **Current-work routing**：mutable phase / exact-SHA / TODO只看 `docs/014` STOP 前；当前 A4 Settings 专项见 `docs/017`；A1–A3 历史在 `docs/016`，默认不要读。

总原则：`webui/** is the product`；qB 4.1.0+ compatibility first；exact-SHA/source truth first；Single Current Owner；canonical reuse；Source/Product/Simulator separation；fine-grained provenance；Frozen LKG protected；bounded inheritance；future UNKNOWN fail closed；no fake data；real-qB evidence；Light/Dark semantic parity；build once / validate once / promote same bytes。任何旧 prompt、旧实现、旧 test、旧 docs、旧 Simulator expectation 与当前 exact-SHA canonical contract 冲突时，禁止为了兼容旧内容把现行产品方向改回旧状态。
总目标：`webui/**` 是唯一正式产品；正式支持 floor 固定为 qBittorrent 4.1.0。同一份 WeiG WebUI 应尽可能直接运行于 qB 4.1.0 起全部 admitted official stable、当前 stable 及未来 stable/new major，并基于真实 qB release、WebAPI 与 upstream source facts 自动适配 endpoint、parameter、response、state/filter、Preference 与 UI surface，不要求用户选择 qB generation/WebAPI compatibility mode。低于 qB 4.1.0 默认不属于正式 compatibility matrix；未来若用户明确扩大 scope，只允许通过集中 `Legacy WebAPI v1 Adapter -> canonical WeiG semantics` 接入，禁止把 v1/v2 判断散落到 UI 或业务 caller。Virtual qB、source catalog、WebAPI evolution ledger、Endpoint/Transport Contract、browser fixture、GitHub Pages 都只是正式产品的发现、模拟、验证与发布设施，不得反客为主。
Authority：本硬规则只保存长期 invariant、安全边界、ownership、evidence identity 与 acceptance 原则，不是第二套 roadmap。产品目标与长期原则以 `docs/001 + docs/010` 为最高计划 authority；当前兼容事实以 `docs/002` 为准；Current Owner、UI/UX、design system 以 `DESIGN.md` 为准；模块架构以 `docs/003` 为准；发布/CI/验证规则以 `docs/006` 为准；安装部署以 `docs/007` 为准；Torrent ownership 以相应 canonical Torrent 文档为准；专项 docs 只能解释其负责领域，不得覆盖更高 authority。当前 exact-SHA canonical runtime + upstream/source evidence + real-qB evidence where applicable 是实际行为最终事实。当前 stable 数量、具体 SHA/run、matrix 并发度、某次 migration/watch/drain 状态等 operational facts 不得反向升级为长期硬规则。凡旧 prompt、旧实现、旧 test、旧 docs、旧 Simulator expectation 与当前 authority 冲突，应先确认 current upstream/source/runtime truth；扩大 scope、改变正式架构、promotion、tag、Release 或出现新的重大 contract 冲突时必须请求用户确认。
[P0-1] 分支纪律：正式开发默认只使用 `dev`；`main` 是稳定晋级结果，不是第二开发分支。产品、installer、workflow、test、fixture、docs、CI 修复都必须先进入 dev；未经用户明确授权禁止直接修改 main、promotion、tag、GitHub Release 或任何会改变正式发布身份的操作；禁止 force push。main 只能从已经完成正式门禁的 final dev exact SHA safe fast-forward，显式 `force:false`。即使 `main == dev`，下一次修改仍从 dev 开始。canonical long-lived branches 只允许 `main` 与 `dev`；remote temporary branch 只有在已确认存在可靠删除路径时才能创建，必须 bounded、短期存在且用途结束后立即删除，禁止成为第二开发线。
[P0-2] SAFE-REF：每轮正式写入前必须 fresh-read 当前 `dev` exact HEAD，并以它作为本批次唯一起点。构建、验证、candidate、artifact、Pages 或 ref 更新前后均必须检查 exact SHA；更新 ref 前再次 fresh-read dev 做 race check。若 dev 已移动，本批次尚未提交的 tree/ref update 必须停止并基于新 HEAD 重建。多文件 coherent write 优先单一 tree/commit；若受工具限制使用顺序 Contents API 写入，后续每一步必须严格接前一步新 SHA，最终再做完整 diff 与 race check。旧 SHA evidence 不能自动证明新 SHA。
[P0-3] Repo-wide proof：ownership、absence、uniqueness、identity、proof 必须基于目标 exact SHA 的完整 relevant tree/blob/file 内容；code search、snippet、grep result 只用于 discovery，不能作为“全仓不存在”“唯一 owner”“没有其它 caller”的最终证明。旧 SHA、截断结果、缓存、局部片段、推测不能作为 repo-wide final proof。涉及 Git blob/hash identity 时必须使用 canonical Git object/index identity 与 canonical Git blob bytes，禁止依赖可能受 Windows CRLF/LF 转换影响的 working-tree bytes。
[P0-4] 提交历史：提交历史必须最小、coherent、可审计。允许必要的 fix/candidate commit，但失败探索、临时 debug、无意义 patch、一次性 scaffolding 不应长期进入正式 dev 历史。Commit message 使用英文。candidate freeze 之前，为整理临时试验历史，可以把批准后的真实变更通过 coherent reconstructed commit/squash/cherry-pick 落入 dev；一旦形成 final dev exact SHA，promotion 到 main 禁止 cherry-pick、merge rebuild、重新构造对象或 main-only 修复，只允许 validated dev SHA 的 safe fast-forward。
[P0-5] VERSION 与 immutable Release：Exact Git SHA 是 code、cache、test、CI、Pages、candidate、artifact、promotion 与 Release evidence 的真实身份。当前 Product VERSION 只在正式 `webui/**` 产品内容变化时递增；docs/tests/CI/workflow/fixture/tooling/simulator-only 变化本身不 bump Product VERSION。VERSION bump 时必须在同一最终 tree 同步所有实际存在的 version owner。已发布 `vX.Y.Z` tag、Release 与 assets 是 immutable historical identity，禁止移动、覆盖、复用或删除后重打。若正式 installer/packaging 变化会改变用户实际下载的 Release bytes，不得覆盖既有同版本 Release；在当前单一 Product VERSION 架构下必须等待/形成新的 product version，或先经用户确认引入独立 Release identity，不能偷用旧 tag。
[P0-6] Single Current Owner + atomic cutover：一个 semantic purpose 只能有一个 Current Owner；planned/dormant/test-only implementation 可存在，但不得形成第二 active runtime owner。修改 public API、event、shared component/token/state、version source、capability boundary 或其它跨模块公共契约前，必须对 target exact SHA 做 repo-wide impact audit，覆盖 caller、test、CSS、event、state、compat path、旧 owner/helper/file retirement。正式切换必须同一 coherent change 完成新 owner生效、全部 caller 切换、superseded owner/helper/state/event/polling/compat path 退休、tests 更新，并在 Current Owner/public contract 真正改变时同步 `DESIGN.md`。禁止 old/new 双 active、hidden DOM bridge、第二 polling/state owner、MutationObserver repair、monkey patch、post-render repair、版本化 runtime duplicate 和长期 fallback bridge。
[P0-7] Canonical UI + Light/Dark semantic parity：UI 必须优先复用 `DESIGN.md` 定义的 canonical Select、Dialog、Button、Input、Card、Theme、Feedback、state/controller 与共享 owner，禁止 feature-local 重造轮子。First-party filename/identifier 使用稳定职责命名，禁止 `-001/-002`、`-v2`、`new-`、`old-`、`final-` 等迁移式 runtime 命名。Desktop/Mobile 必须共享同一 semantic state/component/Current Owner，只允许 responsive presentation 差异。Light/Dark 是同一 semantic UI 的两种 presentation，不要求像素或色值相同，但 text、background、border、hover、active、selected、focus、focus-visible、disabled、read-only、loading、warning、error、success、overlay、dialog、selection、progress 等状态必须保持相同语义、层级与可辨识性；禁止 feature-local hardcoded theme color，禁止只为当前截图或单一主题堆补丁。新增或修改可见 UI 至少验证 affected surface 的 Light + Dark；涉及 shared token/component/theme owner 时必须验证代表性跨页面 surface。focus-visible、键盘导航、disabled/read-only/error/loading 等状态不能只依赖颜色表达。System/Light/Dark 切换只能改变 presentation，不得重置业务 state、selection、route、draft、qB Preference 或其它 canonical state。Reduced Motion 只能关闭非必要装饰动画，不得破坏业务语义、真实 progress、loading/error/focus feedback 或最终 visible state。
[P0-8] Source/Product/Simulator 三层边界：Source Truth 属于 `tools/** + generated catalog + evolution ledger`；Formal Product Compatibility 属于 `webui/**` 中的 `W.QBClient`、`W.CapabilityRegistry`、`W.SettingsSchema`、`W.TorrentSemantics`、`W.TorrentFieldRegistry` 或其它明确 canonical product owner，其中 runtime compatibility/current release facts 唯一归 `W.CapabilityRegistry`，`W.QBClient` 只拥有 transport + detected identity；Virtual qB Simulation 属于 `simulator/**`、Endpoint Contract、Transport Contract 与 Virtual qB services。Simulator/Pages PASS 永远不能单独替代 formal product matrix 或 real-qB evidence。
[P0-9] Compatibility resolution：compatibility 解析必须区分 `EXACT -> EQUIVALENT -> bounded INHERITED -> FALLBACK`。EXACT 是 exact admitted source-derived release facts；EQUIVALENT 只用于 source/API identity 可证明等价的 canonical version/suffix；INHERITED 只允许在明确边界内临时复用已 admitted 的较低 facts，默认必须满足同 major.minor、runtime/API relation 不比 base 更旧且未跨越 source-proven hard boundary；禁止 blind nearest-version-wins、跨 major.minor 随意继承、跨 hard boundary、仅因版本号更高就继承 current latest semantics。Inheritance 只能复用 base 已证明的事实，不能为新版本凭空证明新增 endpoint、parameter、field、Preference 或危险 write。FALLBACK 不能伪装成 source-proven support。具体 capability 仍按 `NATIVE -> NORMALIZED/ADAPTER -> reliable old-API composition -> reliable DERIVED -> READ_ONLY -> UNAVAILABLE -> UNKNOWN` 判断；future UNKNOWN 只对无法证明的具体 capability fail closed，尤其危险 write 不得猜测。
[P0-10] Fine-grained provenance + reliable derivation/no fake data：禁止用单一 true/false 表示整个 feature；至少按 route availability、read、write、action、required parameter、optional parameter、response-field availability、Preference getter/setter/type 等真实 source/API evidence 独立判断。例如 Tags read/facet/filter != list/assign/create/delete；Tracker read != add/remove/edit/reannounce；Settings read != Settings write != individual Preference writable。一个 UI 写操作若由多个 upstream action 共同完成，必须要求全部 required action/parameter source-proven 后才可用，禁止用 `any`/部分成功制造半写入；transport 入口仍需重复 fail-closed preflight。可靠 normalization、old-API composition、DERIVED 或 canonical product mapping 可用于兼容，但必须语义可靠、不伪造 qB 不存在的数据、不破坏数据、错误语义明确、性能可控、不默认制造 `N items -> N requests`、不新增高成本 compatibility polling、不让 presentation caller 自行 probe、不产生第二份业务 state/owner。能从已有 canonical bulk data 可靠推导时优先复用。禁止把 unsupported、UNKNOWN、HTTP/load/runtime failure 偷换为 fake empty data；必须明确区分 `UNAVAILABLE/UNKNOWN`、真实空数据 `[]` 与真实 HTTP/runtime error。
[P0-11] Settings dangerous write：Settings compatibility 安全写必须同时满足 `setPreferences endpoint proven writable AND specific Preference setter/type proven writable AND source projection.safeWrite == true AND current runtime app/preferences actually exposes the Preference`；需要读取/展示时还必须有相应 getter/read provenance。完整 identity/scale/inverse可直接证明安全 projection；若 read normalization尚未证明可逆，只允许在 **exact writable string descriptor + text/select/password/textarea native control + source direct identity setter** 的严格交集下用 `writeIdentity:true` 单独证明写回安全。Numeric/structured/composite不得套用这条例外。getter-only -> read-only；存在可靠 historical equivalent/composition -> canonical product mapping；完全不存在且无法可靠替代 -> hide/read-only。future UNKNOWN write 必须在 HTTP 前 fail closed。Presentation 不得维护 patch-specific Preference 表，section 没有任何有效项时自动隐藏。
[P0-11A] Settings source fidelity + interaction completeness：qB-owned Options的formal fidelity不能只以“Preference key/control已映射”判定。Exact-source graph/census必须account实际显示/交互所需的controls、auxiliary gates、source actions、options/adornments/local labels以及note/help/list/hint等source-owned copy；runtime-relevant behavior若仍为unknown，不得同时计为complete并靠runtime disabled静默掩盖，必须在admission/validation中解析、明确reviewed exclusion或使阶段失败。Gate/value projection必须由source证明并使用generic family（boolean、bounded predicate、numeric sentinel、empty-string/presence等），禁止per-key screenshot patch。Getter类型扩展必须来自exact receiver/interface/header declaration，禁止按Preference名称猜类型。所有正式显示的qB-owned graph {source,context}必须进入现有exact-release official copy dependency closure；目标locale有官方翻译时不得因artifact漏ref回退英文。Desktop compact packing和expanded textarea只属于presentation：不得改变source dependency/write semantics；expanded editor必须共享同一Settings draft/save owner，不得形成第二持久状态或立即写回路径。
[P0-11B] Source-proven write-only 例外（仍 fail closed）：当 qB 的 `GET /app/preferences` 有意不返回当前值，但 exact upstream `setPreferencesAction` + Options 保存逻辑证明该键是 setter-only/write-only 时，可不要求“当前响应存在该 key”，但必须同时满足：当前 release certified；`appcontroller.h:setPreferencesAction` 可写 provenance 成立；Control Graph 含 exact `writeOnly { key, writeType, safeWrite:true }`；写入为 source-proven direct identity；若 upstream 仅在非空时提交则必须保持 `omitEmpty`；UI 不得显示、猜测或持久化旧 secret；保存后清空 transient draft，并以 POST 成功 + 可读 preferences 回读成功作为事务验证，绝不能伪造 secret value 回读。任何缺一项继续只读/不提交。
[P0-11C] Real-qB native group / presentation fidelity：source/control/copy ref被exact extractor捕获、compact contract合法、browser fixture或semantic UI自动PASS，都不能单独证明真实 qB Options 最终可用。若真实 qB 人工review稳定复现 missing / uneditable / duplicated / clipped / mistranslated / malformed compound control，当前阶段必须视为FAIL并进入root-cause closure。必须沿 exact source -> compact facts -> SettingsSchema -> SettingsRenderer -> canonical W.Components/CSS -> W.I18n -> draft/write/reread 定位唯一断点；禁止按Preference key、中文字符串、截图坐标逐项补丁。

Native fieldset/row/group关系应由generic structural/family semantics保留；time range、credential pair、watch-folder grouped options、inline helper/action、long-copy row等可以拥有共享layout primitive，但不得成为第二Settings owner。Canonical Select除了事件链正确，还必须保证floating menu在viewport内且option文本足以完整辨识；不能用统一ellipsis隐藏语义后宣称fidelity完成。真实 qB 人工FAIL与fixture自动PASS冲突时，优先补一个能复现真实failure的focused contract，再修产品；禁止为了保住旧绿灯修改expectation、扩大skip或隐藏控件。



[P0-12] Torrent/filter/field compatibility：historical/current/future upstream differences 应由 `W.CapabilityRegistry + W.TorrentSemantics + W.TorrentFieldRegistry + canonical product normalization` 消化。Field modes 至少区分 `NATIVE / NORMALIZED / DERIVED / UNAVAILABLE`，必要时增加 `READ_ONLY / UNKNOWN`；可靠的 NATIVE/NORMALIZED/DERIVED 均可展示。必须保持 `saved preference != effective availability`：某 field 暂时 UNAVAILABLE/UNKNOWN 时 normal UI 可隐藏，但不得破坏性删除 saved Desktop column order、width、Mobile field preference；未来 exact provenance 恢复时原配置应自动生效。Field presence 不等于 server-side sort semantics 已被证明；Sort provenance 必须独立确认。Torrent filter ownership 的 canonical contract anchor 必须长期保留，禁止在 docs 精简时误删。
[P0-13] Frozen LKG + new stable admission + hash-bound auxiliary facts：已验证 stable profile 默认视为 Frozen Historical Facts / Last Known Good；Frozen expected set 由 target exact-SHA 的 canonical frozen manifest/catalog 定义，不在长期硬规则中写死数量。未来 source extractor、辅助事实或 UI 改造不得无理由重新全量改写 historical admitted facts。新 official stable 必须增量 admission：verify Frozen LKG -> lightweight official stable discovery/tag comparison -> 无新 stable 立即退出 -> 有新 stable 只提取新增 stable facts -> 与上一 admitted stable diff -> focused product/admission gate -> PASS 后 append。若 parser/API/response/write/product owner semantics 无法证明，必须 `PENDING_REVIEW` / fail closed，candidate rejected、LKG unchanged。禁止为“最新版必须支持”修改 verified old profile、猜 semantics 或放宽正确 gate。INHERITED 只能作为新 stable exact admission 前的有界兼容策略，不能替代正式 admission。Locale overlay、translation facts 或其它辅助 source facts 必须至少绑定 exact `qbVersion + sourceSha`，并能验证与对应 Frozen profile 身份一致；允许这些辅助 facts 增强 Virtual qB 或 compact-contract/source audit，但禁止因此重新 source-extract、覆盖或重写 Frozen Historical Facts。Pages 只消费 frozen/hash-bound facts；完整 qB upstream 历史解析属于 candidate/new-stable admission，不得让普通 Pages 部署每次重新 clone/re-parse 全部 upstream。
[P0-14] Locale/i18n：`qB preferences.locale` 是唯一持久语言 owner，`W.I18n` 只负责 presentation；禁止恢复独立 `weigg-language` 持久状态、双向 Locale bridge、重复 `setPreferences()` 或 Desktop/Mobile 双语言 state。WeiG Language 与 qB Locale 必须共享同一 value/options/draft/save/verified-reread flow。qB-owned Settings/UI 文案必须来自对应 exact qB release 的官方 source/context/translation facts；不得把某个较新 release 的 qB-owned 文案硬套历史 release。优先走 upstream/native translator/QBT_TR/QM 能力；只有 upstream Alternative WebUI translation path 被 exact source-proven 不可执行或存在明确历史 hard gap 时，才允许 exact-source compatibility bridge。WeiG-owned 文案与 qB-owned 文案必须保持 ownership 分离，禁止人工维护第二套 qB 官方翻译数据库。browser/OS locale 只能作为环境输入；若产品使用一次性 bootstrap，也必须通过 canonical `setPreferences(locale) -> app/preferences verified reread` 把结果写回同一个 qB persisted truth，并在成功后只以 qB 值为准，禁止建立 previousLocale/退出恢复/第二语言 owner。测试断言界面语言必须绑定实际 applied application locale，不能由 Playwright/browser locale 推断。
[P0-15] Windows/qB 配置安全：任何 installer/tool 对 `qBittorrent.ini` 或其它用户 qB config 的外部修改都必须 fail closed。必须保留原编码、BOM 状态、换行与所有无关 Unicode 内容；禁止使用可能在 Windows PowerShell 5.1 下把 UTF-8 no-BOM 隐式按 ANSI/GBK 解码后再整文件重写的 `Get-Content/Set-Content` 路径。安全写流程必须等价于 `read original bytes -> validate/strict decode -> safety backup -> in-memory minimal mutation -> sibling temp write -> strict reread -> validate encoding/size/target mutation/invariants -> atomic replace or equivalently safe replace -> failure rollback`。若检测 qBittorrent 正在运行、非空 `qBittorrent_new.ini`/recovery file、正式 config 为 0 bytes/异常小/无法安全解析、encoding round-trip 不可靠、目标 config/profile 存在歧义或验证失败，则禁止写入。不得为了“帮用户自动修复”而对未知 mojibake 做盲目逆转码；优先使用已知正常备份或用户明确确认的原值。
[P0-16] Dev/runtime distribution identity：任何可实际运行的 Dev/preview 安装物必须来自 target exact-SHA 的 materialized artifact，并能够验证 embedded `GIT_SHA`/build identity 与目标 SHA 一致。禁止把 raw GitHub source archive 当成已 materialize runtime；禁止 source/package 下载失败后静默 fallback 到另一 SHA、旧 artifact、raw source 或未证明内容。安装/升级成功的定义必须包含“最终运行内容身份可证明”，不能只看 VERSION 相同。
[P0-17] Bounded runtime resources + explicit load failures：正式 browser runtime 资源必须适配真实 qB Alternative WebUI 静态服务器，而不是只适配 Pages/普通静态服务器。完整 release history/profile/source/translation catalog 属于 tools/CI/simulator evidence，不得重新进入 formal `webui/**`；formal runtime 应保持为 bounded compact contracts、compact qB-owned copy registry 与必要 official QM。任何随历史版本数量增长的 evidence/runtime projection若确有保留必要，也必须按 active runtime need 分片、索引、按需加载或采用其它有界方案，禁止重新引入已知可能越过真实 qB 静态资源边界的巨大 monolithic runtime catalog。Pages/browser fixture 能加载不能单独证明真实 qB 可加载；涉及静态资源尺寸、public/private namespace、MIME/cache/path 等真实 hosting 行为时必须有 real-qB evidence。Runtime compact contract/copy/QM 资源加载失败必须显式、可诊断并保持错误类型；HTTP/load/parse/runtime failure 不能静默转换成 fake `[]`、普通 FALLBACK、unsupported、UNAVAILABLE 或其它看似正常业务状态。
[P0-18] Generated artifacts：所有 generated catalog/profile/translation/index/manifest/build metadata 必须能由 target exact SHA 的 canonical source/tooling 可重复生成，并携带必要 provenance。禁止直接手工修改 generated output 来绕过 generator/source truth、admission gate 或 compatibility contract。若 generated file 需要入库，generator、source、output、manifest/checksum contract 必须同步验证；generated output 是可重建结果，不是脱离 source/tooling 的第二 authority。
[P0-19] Persistent user state：localStorage、IndexedDB、config、preferences 等持久状态必须有 canonical owner。schema/shape 改变时必须使用 bounded、可验证、幂等 migration；未知、损坏或未来版本状态必须 fail safe，不得静默整体清空用户设置，不得把 temporary unavailability 当成用户删除。必须保持 `saved preference != effective availability`：当前 capability 暂时不可用时可以不展示，但不得破坏用户已保存配置；未来 capability 恢复时应能重新生效。禁止多个 owner 同时读写同一持久状态并靠 reconciliation 维持一致。
[P0-20] Security / secrets / external network：源码、commit、artifact、Pages、CI log、fixture、screenshot、debug output 中禁止提交或泄漏真实 token、password、cookie、session、private key、用户配置 secret 或其它 credential；测试必须使用显式 synthetic credential。发现疑似 secret 时必须停止传播并按 secret incident 处理，不能认为“后续 commit 删除文本”就等于历史中不存在。正式 WebUI runtime 的后台网络访问只能来自产品明确声明的 qB/API/source asset contract；禁止新增 telemetry、analytics、第三方 tracking、隐式远程配置、动态第三方脚本或未声明 background external request。若未来确有产品需要，必须作为显式 architecture/security change 经用户确认。用户主动点击外部链接与后台 runtime request 必须区分。
[P0-21] GitHub Actions least privilege + supply chain：workflow/job permissions 必须 least privilege；普通 build/test 默认 read-only，只给确有外部写入职责的最小 job 必要的 `contents/pages/deployments/actions` 等权限。第三方 action、downloaded executable、remote script 或 release dependency 必须使用可审计的版本与来源；正式 candidate/promotion/release 禁止依赖不可固定、不可验证的 mutable `latest` 内容，禁止无边界 `curl | shell` 或等价远程执行方式。任何 workflow 变更必须联动检查 `.github/workflows/**`、`tests/**`、`docs/**`、package scripts、permissions、trigger、concurrency、environment 与其它 workflow 的职责映射。
[P0-22] Workflow ownership：GitHub Actions workflow 的 canonical set 与职责由 `docs/006` 明确定义；新增、删除、重命名或改变 workflow 职责属于显式架构变更，不得因旧 prompt/test/docs 恢复 retired workflow。尤其禁止 Pages build/source/deploy 等职责路径映射错误。删除 repo workflow 文件与删除 GitHub Actions 历史 run 是两件事；历史侧栏残留不能通过恢复旧 workflow 解决。任何 temporary compatibility/deployment bridge 必须有唯一 owner、明确 retirement condition、不得形成第二 active path；退休只能依据 current exact-SHA evidence，而不能依据旧阶段描述。
[P0-23] CI 按风险分层：普通 `dev` push 默认运行低成本 smoke；涉及 UI/browser/shared component/theme 时运行相应 UI validation；正式 candidate 才运行完整 candidate validation；全历史 real-qB heavy matrix 不得被普通 docs/tests/tooling-neutral maintenance 自动触发。CI 红灯必须先读完整失败日志并按 root cause 修正，核心优先级固定为 `upstream/source/canonical runtime truth > stale test/fixture/docs/Simulator expectation`；禁止放宽正确 gate、恢复旧 owner、删除关键 assertion、扩大 skip、吞掉错误或使用 patch-version compat hack 只为绿灯。只有明确的瞬时 runner/CDN/infrastructure failure 才允许 same-SHA rerun；确定性 bug 必须修根因。
[P0-23A] 方案文件清单 + batched validation/run：任何实施方案在正式修改前必须明确列出“预计修改文件”，至少给出每个预期文件/目录及其职责；若实施中发现必须超出该清单，必须先说明新增文件/范围与原因，再继续修改，禁止无说明 scope creep。对同一 coherent feature/fix，必须先完成该功能计划内的 code/docs/tests/fixture/tooling 等必要修改并形成可验证的 final feature SHA，再触发或等待需要消耗 GitHub Actions 资源的 run；禁止“改一个文件 -> push/run -> 再改一个文件 -> push/run”的逐文件验证节奏。受 Contents API 等工具限制不得不产生连续中间 commit 时，应把它们视为同一 mutation batch；中间自动触发的 run 不是 required evidence，不得逐个等待、逐个 rerun 或据此做 candidate。功能批次完成后只对 final batch SHA 运行适用的 focused/smoke/UI/candidate validation。仅当继续修改前确实需要一个 bounded 安全结论（例如高风险 migration、无法静态判断的 source/runtime contract）、明确的基础设施诊断，或用户显式要求时，才允许中途 focused run；不得借此恢复逐文件跑 CI。
[P0-23B] 单一活状态文档 + 功能状态迁移：`docs/014.AI协作与分支纪律.md` 是唯一 mutable current-work / handoff / TODO authority。014 前半部只保存当前 blocker、正在进行、已实现待人工复核、人工复核后待全版本验证、待完成/未开始事项；已完成内容必须移动到明确的 `STOP — COMPLETED ARCHIVE BELOW` 分界之后，并保持短摘要，详细历史由 Git/Actions/artifacts 保存。下一位 AI 默认只读取 014 的 STOP 之前，除非排查 regression、历史设计原因或用户明确要求才读取完成归档。若用户只发送“继续当前方案”“继续检查并完成”或等价简短续做指令，AI必须把该指令视为授权继续 014 最前方活动项：先读 015 + 014 active区并 fresh-read repository truth，不得要求用户重新粘贴已在 014 中维护的背景。禁止再新增平行 STATUS/TODO/HANDOFF/ROADMAP 文件。功能状态统一为 `PLANNED -> IN_PROGRESS -> IMPLEMENTED_WAITING_HUMAN_REVIEW -> HUMAN_REVIEWED_WAITING_FULL_VALIDATION -> VERIFIED_DONE`，异常使用 `BLOCKED`。代码实现/CI绿色不能冒充人工复核；只有用户明确完成实际人工复核后才能进入 HUMAN_REVIEWED。只有 implementation + applicable focused/browser/source evidence + user human review + 该功能要求的 admitted-version full validation + docs同步全部闭环，才能标记 VERIFIED_DONE并移入完成归档。

[P0-23C] Validation 时间预算 + 可观察性 + bounded并发：验证步骤不得无解释长期运行。单一步骤/单一 job **<=60秒正常；>60秒必须记录耗时并优先判断是否由可独立命令串行组成，能安全拆分时优先 job-level multi-runner matrix/shard**；3–5分钟必须说明不能拆分的依赖或完成并行化/算法优化；>5分钟必须有可观察 progress/timing，并对 browser/release/locale/fixture 等天然独立任务优先考虑 matrix/shard；>10分钟的天然可分片全量任务原则上不得继续单 runner串行；>30分钟若没有明确合理原因与持续进度，默认视为验证设计异常，必须停止继续消耗 runner并定位根因，而不是先加 timeout。单个不可再安全拆分的测试即使略超60秒，也应独立成可观察 job并继续 profile，而不是与其它独立测试串成长 step。长任务至少输出当前 release/shard/suite、阶段、完成数/总数与阶段耗时。全版本独立任务默认优先 bounded **max-parallel 16**；65-release任务通常采用约16个 shard、每 shard 4–5个版本，以减少重复 checkout/setup。并行只改变调度，不改变 evidence标准：所有 shard/suite必须来自同一 exact SHA、同一对应的 expected set/catalog identity，整体 gate必须保证任一 shard/suite失败即失败，并在需要 aggregate 的任务中证明 expected=executed、missing/duplicate/unexpected为空、FAIL=0、BLOCKED=0；禁止跨SHA拼接 evidence。无法安全分片时保持单 owner，但必须说明依赖并提供 bounded progress。遇到异常慢任务先 instrumentation/profile root cause，再决定算法优化、shard或其它验证方案；禁止用盲目延长 timeout、重复 rerun或“再等等”代替诊断。

[P0-24] Real qB Full Frozen Matrix：G-FM 必须是显式触发的正式验证设施，不用于普通小改动。expected versions 必须从 target exact-SHA 的 canonical Frozen LKG manifest/catalog 派生，不在长期规则写死数量；每个 stable 独立执行，最终 aggregate 必须证明 expected=executed、`FAIL=0`、`BLOCKED=0`、无 missing/duplicate/unexpected。每个版本必须绑定同一 exact WeiG SHA，并验证 requested qB、runtime self-reported qB、CapabilityRegistry release identity/source provenance 与 runtime image/source-build identity。旧 SHA 的 G-FM 永远不能证明新 SHA。并发度等纯 operational 参数由 `docs/006` 维护，除非被明确提升为长期 contract。
[P0-25] Candidate / evidence exact-SHA：完成全部计划修改后先 freeze final dev exact SHA。Candidate、applicable G-FM、dev Pages 与其它 required evidence 可以在 workflow 允许时并行建立，不要求人为严格串行；但 promotion 必须等待同一个 final dev exact SHA 的全部适用 evidence 成功。Candidate 必须针对 final dev exact SHA，并至少证明适用的 smoke、source catalog/audit、formal product matrix、Linux/Windows browser、release package、candidate deployment/real-qB rehearsal 等 gate；关键 artifact 必须绑定 exact SHA，candidate package 必须能验证 checksum、VERSION、candidate SHA、ZIP 内 build identity，并确认 retired release-profile runtime/index/shards 不得重新进入正式包。任一 required evidence 建立后只要又产生新 commit，新 exact SHA 就必须重新满足全部适用 evidence；禁止用旧 SHA 的 candidate/G-FM/Pages/browser/runtime evidence证明新 SHA。
[P0-26] Virtual qB Pages exact-SHA：Pages 必须以 exact-SHA artifact 为核心身份：目标 dev SHA -> exact-source build/materialization -> exact-SHA Pages artifact -> build/deploy/live verify；promotion 后 main 只能复用同一已验证 exact artifact，不得偷偷重新 full-build 另一份。Pages exact identity 必须由 workflow target ref、checkout SHA、source SHA metadata、artifact 名、site/build metadata、live verify 与 deployment identity 等多证据一致证明，不能只看 Actions UI 顶层 branch/SHA。dev runtime evidence 与 production deployment 必须使用隔离且防 stale overwrite 的 environment/concurrency 语义。旧 run 若 branch 已前进，必须在 deploy 前通过 fresh-head gate fail closed，不能覆盖 newer SHA。应用 readiness 必须等待真实 terminal-ready 条件，而不能把某个中间 flag 第一次变 true 就等同最终 ready。
[P0-27] Promote 与 Release exact-SHA gate：Promotion 前必须证明 `current dev HEAD == validated candidate SHA == all applicable evidence SHA == candidate artifact identity == candidate deployment identity == validated dev Pages SHA`，同时 main 必须是 candidate SHA 的 ancestor，并只能 safe fast-forward `force:false`；禁止 force push、merge commit、cherry-pick rebuild、main-only 产品修改或重新构造发布对象。Release 坚持 `build once / validate once / promote same bytes`：final dev candidate SHA、验证 evidence、最终 main SHA、tag SHA、发布 ZIP 内 `GIT_SHA` 必须一致；Release workflow 复用已验证 candidate artifact，不得在 main/tag 后重新构建另一份 ZIP。Release 前再次 fail closed 校验 checksum、VERSION、compact-runtime/distribution contract、candidate SHA 与 ZIP identity。Candidate PASS、Pages PASS、main==dev 均不能单独替代正式 promotion/release permission。
[P1-28] Docs/tests/simulator authority：Docs 体系按职责/authority 定义，不以固定编号上限定义。Primary architecture/current-contract docs 只记录长期 current architecture、compatibility contracts、validation rules 与 SOP，不做流水账或第二 roadmap。允许新增 bounded 专项设计、source audit、事故复盘、验证说明等文档保存已验证事实与长期教训，但必须明确 authority 范围，不得成为第二套 roadmap、第二 Current Owner 或覆盖更高层 authority。禁止恢复 Phase A–G roadmap/checkpoint，禁止另建重复 `HANDOFF.md`、`ROADMAP-v2`、`FINAL-PLAN` 等第二套 authority。所有 test、fixture、Simulator、CI、docs 与工具都必须服务于当前 canonical product contract，不能反向定义产品事实。测试失败时首先判断是产品违反 current contract，还是 test/fixture/docs/Simulator expectation 已 stale；只有前者才修改产品。禁止通过删除 assertion、扩大 skip、吞错误、伪造空数据、降低 exact-SHA/source provenance、隐藏 runtime failure 或恢复旧 owner 来制造绿灯。最终接受标准永远回到：目标 exact SHA 上的 canonical runtime 行为与 source/upstream evidence 一致，并在需要真实 hosting/runtime 行为的地方由 real-qB evidence 证明。


[P1-29] A3 identity/materialization lesson：当source-native Settings payload的release set正确但 `sourceCatalogSha256` 与其它compact domains的canonical Frozen catalog不一致时，必须在生成/materialization端统一identity；formal runtime的 `sameCatalogIdentity` fail-closed检查不得为了让CI变绿而放宽。Source-only evidence、Pages Source SUCCESS或临时materializer输出都不能替代committed product bytes在同一exact SHA上的smoke/browser/Pages evidence。
