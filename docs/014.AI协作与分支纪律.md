## 2. 第一原则：所有开发都先 dev

```text
dev   唯一 normal development / fix / docs / validation 入口
main  validated promotion result
```

禁止：

```text
直接在 main update/create/delete file
直接在 main 创建日常 commit
日常 cherry-pick/merge 到 main
force push dev/main
为了省 CI 时间把 fix 只放 main
未经用户批准触发 Candidate
未经用户批准 promotion / tag / GitHub Release
```

正确原则：

```text
fresh-read dev
-> 在 dev 完成 coherent change
-> normal validation
-> 继续在 dev 修 root cause
-> 用户明确决定是否进入最终验证/发布
```

即使某时 `main == dev`，下一次修改仍从 `dev` 开始。

## 6. 写入与 ref 操作纪律

每轮写入：

```text
fresh-read dev exact HEAD
-> 以 exact HEAD为父准备 change
-> validate / exact diff
-> 再 fresh-read dev 做 race check
-> safe fast-forward force:false
```

如果 dev 已移动，停止旧 ref update并基于新 HEAD重建。旧 SHA不能作为新 SHA proof。

不要把 mutation API当 discovery/probe：

```text
不要用 create_branch 测工具
不要用 update_file 测权限
不要创建 no-op VERSION commit
不要为了拿 schema 而执行写动作
```

先用只读 fetch/search/list_resources确认工具语义，再写。

## 8. 红灯处理纪律

遇到 CI/Pages 红灯：

```text
读完整失败 job/log
-> 分类 product bug / source misunderstanding / stale test/docs / workflow / infrastructure / identity
-> 修 root cause
```

优先级：

```text
qB upstream/source truth
-> canonical runtime truth
-> real runtime evidence
-> tests/fixtures/docs/simulator expectation
```

禁止：

```text
删正确 assertion只为绿灯
FAIL改SKIP
扩大skip
吞runtime/source error
把正确产品恢复成旧DOM/旧owner
same-SHA rerun确定性bug
```

只有明确 transient runner/CDN/GitHub infrastructure fault才适合同SHA rerun。

## 9. Pages / Dev installer 注意事项

Dev installer只消费 materialized Pages distribution，并验证 embedded identity；禁止 raw-source fallback。

Pages Source必须同时考虑：

```text
current push diff
published materialized payload SHA -> current dev history
```

如果中间存在 Pages-relevant产品变化，后续docs-only push不能让旧payload永久停留。`pages-source.yml` 的materialization relevance matcher只有一个 canonical owner；不要复制第二份匹配表。
