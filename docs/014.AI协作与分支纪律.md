## 7. 本轮复盘与需要避免的坑

1. **先判断红灯是谁错，不要见 CI 红就改产品。** 本轮曾有 stale `tests/qb-recovery-ci-contract.mjs` / Candidate expectations 仍要求 retired LKG/release-profile materialization。正确顺序是读完整失败日志，再以 `upstream/source/canonical runtime truth > stale test/docs/simulator expectation` 判定 owner；不能为了旧 gate 恢复已经退休的 runtime。
2. **readiness 必须等最终语义收敛。** `releaseIdentity()`、某个 capability flag、DOM attached、`document.readyState==='complete'` 都可能只是中间态；live browser gate 应等待真正影响断言的 semantic owner 与 visible DOM/state 收敛，并保留 bounded timeout/fail closed。
3. **不要把完整 source/release catalog重新塞回产品。** 正式 `webui/**` 只能保留 bounded compact contracts、`qb-settings-native.txt` 与必要 QM；完整 catalog/profile/source facts 属于 tools/CI/simulator。Pages 能加载大文件也不能证明真实 qB Alternative WebUI 静态服务器可安全承载。
4. **Candidate/Pages/CI owner 要和测试一起原子迁移。** 修改 canonical packaging/distribution path 时必须同步 workflow、contract tests、retired-path absence assertions；否则最容易出现“新实现正确、旧 test 仍要求旧架构”的假回归。
5. **证据按适用范围，不为证据制造代码。** 任何真实实现变更都会使旧 exact-SHA evidence 失效；但纯 handoff/docs 更新不是理由去加无意义 test comment 或产品 patch 只为触发 Pages。先看 classifier/diff，再决定哪些 gate 真正适用。
6. **不要继续找任务。** 当前方案已经完成。下一位 AI 的第一职责不是“继续优化”，而是先读完 authority、核对仓库事实，然后等待用户明确提出下一方案。
