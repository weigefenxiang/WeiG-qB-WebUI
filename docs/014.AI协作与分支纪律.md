## 6. 累计复盘：需要避免的坑

### 6.1 Source/runtime truth高于 stale assertion

用户指出的真实交互问题必须先验证 runtime/页面行为，再看 contract是否 stale。旧 test、旧 docs、旧 prompt与已确认 source/runtime truth冲突时更新旧内容，不恢复错误实现。

### 6.2 Files hierarchy只能是 shared table / VirtualList projection

Folder row、sticky parent、expand/collapse和anchor restore都不得形成第二 data/scroll owner。必须保持 qB files response顺序和 exact source file index。

### 6.3 Synthetic folder不是 qB source file

Folder aggregation是只读 presentation。测试不能拿 folder DOM顺序、child DOM顺序或 synthetic row位置推导真正 file write address。真正 file write继续绑定 exact source file index/path。

### 6.4 file Rename 与 folder Rename provenance必须独立

File Rename只消费 exact `renameFileAction`；folder Rename只消费 exact `renameFolderAction`。二者不能互相推断。没有 exact proof就不显示、不发送 HTTP。Folder/file context可以共享 canonical Detail context owner，但 folder不能继承 file Priority等 file-only mutation。

### 6.5 Sticky parent / sticky header不得用 repair architecture

Sticky parent与header都只能在现有 viewport/stacking体系内实现。禁止第二 scroll container、scrollLeft同步、MutationObserver、monkey patch或post-render repair。

### 6.6 General native-like presentation不能变成第二 schema

Parenthetical secondary values、URL link与Progress/Availability omission都只是同一 source-generated `propertyLayout` 的 presentation。Source order、field binding与qB-owned copy不能复制到第二手写 registry。

### 6.7 Local action与transport action必须分开

Local Copy使用 browser clipboard；qB mutation/export进入 `W.QBClient`。没有 source/WebAPI provenance的桌面客户端 action不得因为截图里存在就伪造 Alternative WebUI endpoint。

### 6.8 Torrent-level菜单不能退化为第二 action/taxonomy owner

Native-like Category / Tags / Queue / Copy submenu只是现有 ActionRegistry的 presentation。Category/Tags真值实时来自当前 qB API；不能缓存第二 taxonomy owner。`addTagsAction` 与 `removeTagsAction` 必须独立证明，checked Tag removal必须 exact证明 `removeTagsAction`。

### 6.9 Transfer sidebar只能改变布局优先级

短高度桌面可把 realtime transfer card保留在底部高优先级区域，但数据继续由 existing `transfer/info` + `W.TransferRuntime` 提供；不得增加第二 request/timer/history owner。

### 6.10 Exact Pages/materialization验证不能省略

Focused contracts全绿不等于 materialized hosted runtime正确。涉及 `webui/**` 的正式产品 change必须看 exact Pages build/deploy/live verification和真实distribution identity/size/manifest；0.3.90 的 exact materialized checkpoint是 `fee80e0f...`。

### 6.11 Exact Pages/materialization evidence 与 test/docs-only evidence必须分层

`fee80e0f...` Pages #779证明0.3.90 product bytes；`b474bd3...`只修改browser tests，拥有自己的CI #1721与Pages Source #809 evidence。后续 docs-only SHA也必须单独看 ordinary CI/Pages Source classifier，不能把旧 product Pages PASS写成新 SHA exact Pages PASS。

### 6.12 Contract应锁 semantic requirement，不锁脆弱实现字面

Stale literal regex不能反向迫使正确 runtime/docs退化。测试应锁 source/provenance/ownership/semantic requirement，而不是无意义的单句措辞。

### 6.13 Closure authority不能自指

`docs/014` 可以记录已经稳定验证的 product/test checkpoints，但不要在尚未验证的 docs-only提交里写“本提交 SHA = 永久最终 closure HEAD”。Current docs HEAD必须由接手者 fresh-read。

### 6.14 Docs closure必须做 current-authority 全局一致性审计

不能因为 `docs/002 / 008 / 014`已更新就宣称全部docs收口。交接前至少检查所有 current-authority docs是否仍残留旧 VERSION、旧“当前方案”、旧 checkpoint、已完成事项仍写成pending。重点检查 `docs/001` 高层 current state。

### 6.15 Handoff必须明确“等待用户方案”

“没有 TODO”不是邀请 AI自己找优化点。下一位AI完成docs阅读 + fresh-read后应停在 `dev` 等待用户提出方案。用户给新方案之后，先定义 New Scope / Protected Current State / Must Retire / Must Not Touch，再动代码；不要把已完成模块重新打开。
