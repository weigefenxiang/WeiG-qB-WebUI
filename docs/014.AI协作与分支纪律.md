## 5. 累计复盘：需要避免的坑

### 5.1 真实 materialization优先，不要只信 focused contract

0.3.86 runtime-slimming阶段 focused contracts最初都绿，但真实 Pages materialization曾把 `qb-settings-native.txt` 做成约29.34 MB，超过 qB 10 MiB static-file hard limit。最终通过 bridge leaf-value 全局去重降到3,829,474 B。

教训：runtime slimming/packaging任务必须看真实 materialized bytes、manifest与qB静态文件边界，不能只看“结构上已去重”。0.3.87 local Peer flags同样必须进入真实 materialization owner并由 Pages build验证，而不能只做源码占位。

### 5.2 不要为了过 gate 恢复旧 owner或放宽 assertion

开发过程中出现过 stale docs/CI/Pages assertions。正确处理是先确认 canonical runtime truth，再同步 stale gate；不能恢复 `qb-settings/`、双 loader、旧 translation route字段、独立 Speed owner、外部 flag CDN，也不能把 size/provenance限制调大来掩盖问题。

### 5.3 docs authority必须同步，不要让旧概述误导下一位 AI

`docs/014` 是唯一 mutable handoff/TODO authority；`docs/002` 是 current facts；`docs/001` 只保存高层 current project state；`docs/007` 是 installer/distribution owner。阶段完成后要把长期事实写回对应 owner docs，并清掉旧“下一阶段/尚未实现”描述。

### 5.4 Exact-SHA evidence不能跨提交偷用

旧 SHA 的 CI/Pages PASS 不证明新 SHA。Docs-only/test-only change也要按 classifier和Pages representability判断 current SHA 的适用 evidence。产品 implementation evidence 与后续 docs/authority closure evidence必须明确分层；不要为了追求 `dev HEAD == downloads/dev/GIT_SHA` 而无意义重建产品。

### 5.5 GitHub connector大文件写入要做 blob identity硬校验

历史上 `i18n.js` 大文件通过长 base64参数直接写入时发生过工具层截断，错误 blob没有挂到 branch。大 UTF-8文件不得凭“看起来相同”落库；必须用 canonical Git blob hash/runner验证字节身份。临时验证设施不能进入正式 dev历史。

### 5.6 不要把 translator family数量当最终 runtime route数量

`2908 native / 616 mandatory bridge`描述的是 source-proven translator family hard-boundary层；最终 runtime还可能因为 exact historical TS/QM wording差异把某些 native-capable route降为 exact bridge。不要为了追某个统计数字删 bridge或弱化 exact historical wording。

### 5.7 Source-first修复实际问题，不要固化临时 presentation

0.3.87 Peer flags初版曾使用外部 CDN sprite，但 qB 4.1.0、4.6.7、5.2.3 的 source truth都指向本地 `images/flags/<iso>.svg`。最终方案因此改为 source-pinned local materialization，并让 raw source fail closed到 ISO code。

教训：临时视觉实现与 admitted source truth冲突时，必须修实现，而不是修改 contract来合理化临时方案。

### 5.8 不要把 main installer 当成当前 dev installer

实际 Windows dev 安装暴露了这个坑：用户从 `main/installers/install.ps1` 下载旧稳定 installer，再传 `-dev`。main 当时仍是旧稳定 baseline，旧脚本只接受 `downloads/dev/GIT_SHA == current dev HEAD`；而 current dev 已因 docs-only closure 前移，materialized payload正确停在 final product implementation SHA，于是旧 main installer把合法 representability reuse误报成 stale payload。

正确边界：

```text
Stable install bootstrap -> main/installers/*
Current dev test bootstrap -> dev/installers/*
Dev WebUI payload -> downloads/dev materialized distribution only
```

当前 dev installer会 exact-compare `published materialized SHA -> current dev HEAD`。只有所有变化都能证明 Pages-irrelevant 时才复用已验证 payload；任何 Pages-relevant change、compare异常、非 ahead状态或文件列表不完整都 fail closed。

教训：**installer bootstrap script来自哪个 branch** 与 **最终 WebUI payload来自哪里** 是两个身份问题。dev bootstrap来自 raw `dev/installers/*` 不等于允许 raw `webui/**` fallback；正式 payload仍必须来自 Pages materialized distribution。

### 5.9 用户现场失败是验证证据，不要只看 CI 已绿

这轮产品 CI/Pages/live 全绿后，真实用户执行安装仍发现 main/dev bootstrap代际差异。遇到这种情况要先判断：是产品 bytes失败、distribution失败、installer owner失败，还是入口文档/branch identity失败。不要看到“SHA 不一致”就本能触发新 Pages build或改 product bytes。
