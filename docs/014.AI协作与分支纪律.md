## 6. 累计复盘：需要避免的坑

### 6.1 用户现场失败与实际 UI 问题优先于“旧 gate 绿了”

用户指出的真实交互问题必须先验证 runtime/页面行为，再看 contract 是否 stale。旧 test 与已确认 source/runtime truth冲突时更新 test，不恢复错误实现。

### 6.2 Files hierarchy只能是现有 shared table / VirtualList 的 projection

Folder row、sticky parent、expand/collapse和anchor restore都不得形成第二 data/scroll owner。必须保持 qB files response顺序和 exact source file index；folder aggregation是只读 presentation，不能给folder凭空增加file mutation capability。

### 6.3 Sticky parent / sticky header不得用 repair architecture

Sticky parent与header都只能在现有 viewport/stacking体系内实现。禁止第二 scroll container、scrollLeft同步、MutationObserver、monkey patch或post-render repair。

### 6.4 General native-like presentation不能变成第二 schema

Parenthetical secondary values、URL link与Progress/Availability omission都只是同一 source-generated `propertyLayout` 的 presentation。Source order、field binding与qB-owned copy不能复制到第二手写 registry。

### 6.5 Source-proven local action与transport action要分开

Local Copy使用 browser clipboard；qB mutation/export进入 `W.QBClient`。没有 source/WebAPI provenance的桌面客户端 action（例如当前未证明的 Open/Open containing folder）不得因为截图里存在就伪造 Alternative WebUI endpoint。

### 6.6 Torrent-level菜单不能退化为固定版本菜单

Super Seeding、queue actions、export等必须由 exact/equivalent release source/capability决定是否出现。WeiG可以保持双列presentation，但不能让presentation拥有第二 action truth。

### 6.7 Transfer sidebar只能改变布局优先级

短高度桌面可把 realtime transfer card保留在底部高优先级区域，但数据继续由 existing `transfer/info` + `W.TransferRuntime` 提供；不得增加第二 request/timer/history owner。

### 6.8 Exact Pages/materialization验证不能省略

Focused contracts全绿不等于 materialized hosted runtime正确。涉及 `webui/**` 的正式产品 change必须看 exact Pages build/deploy/live verification和真实distribution identity/size/manifest；0.3.89 已完成这一闭环。

### 6.9 不要为 stale contract改坏正确 runtime

0.3.89 的 CI #1709/#1710 都是 compatibility docs literal regex落后于 canonical wording。正确做法是确认产品/runtime truth后同步 test；禁止为过 gate倒退兼容文档或改变产品 owner。Contract应尽量锁 semantic requirement，而不是脆弱的单句 literal wording。

### 6.10 Closure authority不能自指

`docs/014` 可以记录已经稳定验证的 product/test checkpoints，但不要在尚未验证的 docs-only提交里写“本提交 SHA = 最终 closure SHA”。Current docs HEAD必须由接手者 fresh-read；否则每次更新 closure都会立刻把自己写旧。

### 6.11 Docs closure必须做 current-authority 全局一致性审计

不能因为 `docs/002 / 008 / 014` 已更新就宣称所有 docs 已收口。交接前至少检查所有 current-authority docs 是否仍残留旧 VERSION、旧“当前方案”、旧 checkpoint、已完成事项仍写成 pending。0.3.89 第一次 closure遗漏 `docs/001` 的 0.3.88 baseline，说明“只检查本次编辑文件”不是 repo-wide proof。

### 6.12 Product evidence 与 docs-only evidence必须分层

`aedf659f...` 的 Pages #775证明 0.3.89 product bytes；后续 docs-only SHA可以在 classifier证明 Pages-irrelevant后复用该 payload，但新 docs SHA自己的 ordinary CI / Pages Source classifier仍要单独看。不要把旧 product Pages PASS写成新 docs SHA的 exact Pages PASS，也不要为了 docs-only change强行重复昂贵materialization。

### 6.13 Handoff必须明确“等待用户方案”

“没有 TODO”不是邀请 AI 自己找优化点。下一位 AI完成 docs阅读 + fresh-read 后应停在 `dev` 等待用户提出方案。用户给新方案之后，先定义 New Scope / Protected Current State / Must Retire / Must Not Touch，再动代码；不要把已完成模块重新打开。
