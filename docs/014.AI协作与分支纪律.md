## 2. 第一原则：所有开发都先 dev

```text
dev   唯一 normal development / fix / docs / validation 入口
main  validated promotion result
```

禁止：

```text
直接在 main update/create/delete file
直接在 main 创建日常 commit
日常 cherry-pick/merge 到 main
force push dev/main
为了省 CI 时间把 fix 只放 main
未经用户批准触发 Candidate
未经用户批准触发 Current Stable Locale Matrix / Real qB Full Frozen Matrix
未经用户批准 promotion / tag / GitHub Release
```

正确流程：

```text
fresh-read dev
-> 在 dev 完成 coherent change
-> normal validation
-> 红灯只修 root cause
-> 用户明确决定是否进入最终验证/发布
```

即使某时 `main == dev`，下一次修改仍从 `dev` 开始。

## 7. 写入与 ref 操作纪律

每轮正式 mutation batch：

```text
fresh-read dev exact HEAD
-> 读取相关 exact files/tree
-> 准备 coherent exact diff
-> validate
-> ref更新前再次 fresh-read dev做race check
-> safe fast-forward force:false（使用git-data路径时）
```

若使用 Contents API直接在 `dev` 写单文件，调用本身必须是明确的真实修改而不是 probe；写前仍先 fresh-read dev并确认目标 blob SHA。

如果 dev已移动，停止旧 ref update并基于新 HEAD重建。旧 SHA不能作为新 SHA proof。

### 7.1 Mutation API 绝不能当 probe

```text
不要用 create_branch 测权限/参数
不要用 create_file/update_file 测branch是否存在
不要用 create_tree 测tree schema
不要用 create_commit 测commit schema
不要创建no-op VERSION commit
不要为了拿schema/错误信息制造blob/tree/commit
```

即使对象没有挂到 ref，Git database mutation仍不是只读探测。先用 `list_resources` / read-only fetch/search读取 schema；参数不确定就先确认，不要试写。

## 8. 非 canonical refs / objects

长期 canonical branches只有：

```text
dev
main
```

仓库若仍可见历史/临时/误建 branch或 orphan Git object，它们都不属于 current truth/evidence。不得从它们接着开发，也不得因为看到它们就自行 merge/rebase/main同步。

临时 branch若确实为了一次明确 mutation workflow而创建，必须在该工作完成后删除；它不能成为第二开发线。

## 9. 红灯处理纪律

遇到 CI/Pages 红灯：

```text
读完整失败 job/log
-> 分类 product bug / source misunderstanding / stale test/docs / workflow / infrastructure / identity
-> 修 root cause
```

优先级：

```text
qB upstream/source truth
-> canonical runtime truth
-> real runtime evidence
-> tests/fixtures/docs/simulator expectation
```

禁止：

```text
删正确 assertion只为绿灯
FAIL改SKIP
扩大skip
吞runtime/source error
把正确产品恢复成旧DOM/旧owner
same-SHA rerun确定性bug
```

只有明确 transient runner/CDN/GitHub infrastructure fault才适合同SHA rerun。

## 10. Pages / Dev installer 注意事项

Dev installer只消费 materialized Pages distribution，并验证 embedded identity；禁止 raw-source fallback。

Pages Source必须同时考虑：

```text
current push diff
published materialized payload SHA -> current dev history
```

如果中间存在 Pages-relevant产品变化，后续 docs/test-only push不能让旧payload永久停留。`pages-source.yml` 的 materialization relevance matcher只有一个 canonical owner；不要复制第二份匹配表。

Docs/tests/browser-gate-only follow-up可以由 canonical classifier证明无需重新 materialize，但 representability必须由 workflow输出，不能人工猜。

Installer backup retention当前固定为：

```text
先写 last-backup rollback pointer
-> 只扫描 YYYYMMDD-HHMMSS 目录
-> 同时要求 had-webui + dest-path ownership markers
-> newest-first只保留3份
-> 无关目录/文件不删除
```

不要扩大 pruning ownership boundary；详细规则见 `docs/007` 与 `docs/021`。
