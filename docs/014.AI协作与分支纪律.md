Status: **next-AI handoff authority**

如果你是接手本仓库的下一位 AI，先读 `docs/015.开发硬规则（长期版）.md`，再读本文、`docs/002.兼容与实现状态.md` 和 `docs/006.发布与晋级流程.md`。

## 1. 第一原则：永远先 dev

用户明确要求：**不要跳过 dev，直接改 main。**

任何修改，包括“只是文档”“只是 workflow”“只是测试修复”，都先进入：

```text
dev
```

禁止：

```text
直接在 main update_file/create_file/delete_file
直接在 main 创建 commit
直接 cherry-pick 到 main
直接 update_ref main 作为日常修改方式
force push main
为了省 CI 时间把 fix 只放 main
```

正确流程：

```text
修改 dev
-> 验证 dev
-> 修复仍然在 dev
-> 冻结 final dev exact SHA
-> 建立同 SHA evidence
-> formal promotion
-> main fast-forward 到 validated dev SHA
```

即使某一刻 `main == dev`，下一次改动仍然从 dev 开始。

## 4. 但不要误判为“v0.3.71 已可发布”

`ba8ee498...` **没有同 SHA 的 Real qB Full Frozen Matrix (G-FM) 65/65 run**。

本轮曾直接把 main fast-forward 到 `ba8ee498...`，main Pages 也成功，但这没有经过 `Promote validated dev to main` workflow 对 G-FM 的强制检查。

因此永久记住：

```text
candidate PASS != G-FM PASS
main == dev != formal promotion gate complete
main Pages PASS != tag/release permission
```

而后续 docs/test/workflow commit 已继续推进 dev，所以 future release 应从新的 final dev SHA 重建完整 evidence，不应给旧 `ba8ee498...` 直接补 tag。

## 6. Installer / supply-chain 当前事实

### Stable Release identity

Linux/Windows installer：

```text
resolve Release metadata
-> exact tag
-> tag commit SHA
-> tag-pinned asset URL
-> SHA256SUMS
-> package VERSION == tag version
-> package GIT_SHA == tag commit
```

不要放宽这条链。

### Dev distribution

Linux/Windows Dev 只消费 Pages materialized distribution。payload 自身 identity：

```text
downloads/dev/GIT_SHA
== package GIT_SHA
```

日常 `current dev HEAD` 可以只因为明确的 Pages-irrelevant commit 暂时领先 published Pages SHA。installer 会比较：

```text
published Pages SHA ... current dev HEAD
```

只有 intervening diff 全部属于明确 Pages-irrelevant 集合时才允许复用最后一个 verified payload。任何未知/runtime path 都 fail closed，等待新的 Pages build。

禁止 raw-source fallback。

## 8. Pages 当前架构与坑

唯一部署 owner：

```text
Virtual qB Pages Source
-> relevance classifier
-> workflow_dispatch（仅 Pages-relevant / manual）
-> Virtual qB Pages
```

不要恢复 default-branch `workflow_run` deployment trigger。

### 8.1 Pages relevance

每个 dev/main push 都进入轻量 `Virtual qB Pages Source`，由 checkout 的完整 Git history 做 relevance classifier。不要在这个安全入口使用 GitHub 原生 `paths` / `paths-ignore`：GitHub 对超大 changed-file diff 的 path filter 存在返回文件数量上限，不能让后面的 runtime/unknown 文件因为平台过滤截断而绕过 fail-closed。

明确 Pages-irrelevant：

```text
docs/**
*.md
LICENSE
.github/workflows/ci.yml
.github/workflows/promote.yml
.github/workflows/real-qb-full.yml
.github/workflows/release.yml
```

除此之外**未知路径默认 Pages-relevant**，不能因为想省 CI 就扩大 ignore 范围。

仓库存在中文文件名，diff 必须使用 NUL/raw filename：

```text
git diff --name-only -z
read -d ''
```

不要恢复默认 quoted path 解析；否则 `docs/中文.md` 会被转义为带引号/八进制 escape 的字符串，错误落入 Pages-relevant 分支。

普通 `CI` 的 dev push 同样不使用 GitHub 原生 path filter。先运行轻量 `Classify CI push`：

```text
完整 checkout history
-> git diff --name-only -z BEFORE HEAD
-> 仅 docs/** / *.md / LICENSE => CI-irrelevant
-> 任意未知/代码/workflow/test => CI-relevant
```

纯 docs 时只跳过 heavy `smoke`；`[ui]` / `[candidate]` commit message 仍显式要求完整对应 gate。`workflow_dispatch` 也不经过 docs skip，因此 final freeze 需要 exact-SHA normal CI / candidate evidence 时仍可显式运行。

日常纯文档提交的期望 Actions 形态：

```text
CI
  Classify CI push          -> SUCCESS
  smoke                     -> SKIPPED

Virtual qB Pages Source
  source                    -> SUCCESS
  Dispatch exact-ref Pages  -> SKIPPED

Virtual qB Pages            -> no run
```

也就是纯 docs push 只付两个轻量分类 runner，不运行 Node/npm test、Pages build、deploy 或 live browser verify。

Concurrency：

```text
virtual-qb-pages-dispatch
cancel-in-progress: false
```

不要粗暴 cancel 已进入 deploy-pages 外部写入阶段的 run。

Dev deploy stale gate 当前规则：

```text
current dev HEAD == workflow SHA
=> deploy

current dev HEAD > workflow SHA
AND every intervening path is explicitly Pages-irrelevant
=> deploy remains valid

any unknown / Pages-relevant intervening path
=> fail closed before deploy
```

这样 runtime Pages build 不会因为随后一个 docs-only commit 被永久卡死，同时也不允许真正 stale runtime 覆盖 newer runtime SHA。

main promotion 仍保持 exact main SHA gate；不要把 dev 的 docs-only exception 扩散到 formal promotion identity。

Live catalog 等待：

```text
catalogError || (catalogReady && !catalogBusy)
```

不要在 `catalogReady` 第一次变 true 时立刻要求 busy=false。

### 8.2 应用语言不是浏览器 locale

WeiG 的持久化语言 truth owner 是：

```text
qB app/preferences.locale
```

`browser.newContext({locale:'zh-CN'})` 只改变浏览器 locale，不保证当前 qB preference 已经是 `zh_CN`，也不能作为“页面必须输出中文”的测试依据。

2026-09-12 docs-only Pages 验收曾出现：

```text
actual: Page 1 / 100 · 50 per page
stale assertion: 必须匹配中文 “第 1 / 100 页 · 每页 50”
```

产品 pager 语义是正确的；错误在 acceptance 把浏览器 locale 当成应用 persisted locale。

正确测试规则：读取实际 `W.I18n.getLocale()` / qB preference，再验证对应语言的 pager；不要通过 retry 把这个确定性前置假设跑成偶然绿色，也不要为了测试修改产品语言 ownership。

## 9. Candidate mock 的历史坑

曾出现生产 installer 正确、candidate mock 错误：真实 GitHub commit API 的 pretty JSON 中 `sha` 是独立行，而 mock 返回单行 `{"sha":"..."}`，导致 parser 报：

```text
Release v0.3.71 did not resolve to a valid commit SHA.
```

正确修法是让 mock 模拟真实 API shape；**不要修改生产 identity parser 去迁就错误 mock**。

遇到红灯：

```text

```

```text
删断言

放宽 source-proven dangerous write

恢复 raw-source fallback
把未知 path 默认为 Pages-irrelevant
为了 0 runner 使用会截断 changed-file 判定的原生 path filter
```

## 11. 当前推荐下一步

每次接手：

```text
1. 读取新的 dev/main HEAD。
2. 读取最新 normal CI / Pages / Release 状态。
3. 不移动 main。
4. 继续开发仍然只改 dev。
5. 日常 docs-only push 应只跑轻量 classifier，不运行 CI smoke 或 Virtual qB Pages。
6. 用户明确要发布时，再冻结 final dev SHA 并重新建立 candidate + explicit exact-SHA Pages + G-FM。
7. 用 formal promotion workflow 晋级 main。
8. 只有 formal gate 完成才创建 v0.3.71 tag/Release。
```
